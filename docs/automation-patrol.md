# 每小时巡检：内容稽查 + 数据清洗

> 这条文档讲**为什么这么设计**。具体命令与每轮的步骤清单在定时任务 prompt 里
> （`automation_update(mode="view")` 查看，那是唯一真源，此处不抄第二份）。

---

## 1. 定位：日抓存料，时巡查错

两条常驻任务分工，2026-11-10 定稿：

| | 每日 00:00「抓新城市数据」 | 每小时「历史数据巡检」 |
|---|---|---|
| 干什么 | **拓取 + 入库**：把候选落成新 POI | **清洗**：把已上线的 4000+ 条逐个查错 |
| 产出 | 新点位、新候选、新图 | 修正的字段、修好的图、避雷提示、新线索 |
| 节奏 | 一晚 1 城入库 + 200 次拓取 | 一轮 1 城 6 点 |
| 判断依据 | 风评打分（`rate_poi.py`） | 权威源比对（政府/官网/官媒 > OTA > 自媒体） |

用户原话：「后期每天抓的这个抓完之后，主要就是这个每小时的在清洗数据了」。
所以**时巡的产出质量 = 站点的数据质量**，日抓只负责把料备齐。

## 2. 一圈的骨架

九段，顺序不能乱（前一段的结果是后一段的输入）：

| 段 | 做什么 | 关键约束 |
|---|---|---|
| P0 | 静态体检 `audit_history --fix-safe` + 旧账 `auto-stale` + 读 `PENDING.md` | 只修四类无歧义问题 |
| P1 | `patrol_queue next --n 6` 选城选点 | 名额已按「一半旧账、一半新点」分好，别自己调 |
| P2 | 逐点联网核实（是否还开着 / 票价 / 时间 / 地址） | **每点至少两条不同查询**，核不到就是核不到 |
| P3 | `patrol_sheet` 出九宫格图，**必须真看** | 判据只看「是不是这个点位」，不看构图 |
| P4 | 图错了重抓（每轮最多 2 点） | 多了必撞 Wikimedia 429 |
| P5 | `fix` / `retire` 落改动 | 只动白名单字段，只用 A 档证据 |
| P5.5 | **AI 点评**（每轮 20 条，2026-11-12 新增） | 没有 `review` 的点**整块不渲染**；`basis` 必须诚实 |
| P5.6 | **城市封面**（每轮 1~2 城，2026-11-12 新增） | 只用本地标当查询词、**只收 Wikimedia**、逐张看图；口径见 `docs/automation-image-review.md` 第二十节 |
| P6 | 搜「有没有新景点」→ `suggest-<city>.json` | 只写线索，**不许入库** |
| P6.5 | **热点巡检**（2026-11-10 新增） | 避雷 / 新优，热度调整 ≤20 |
| P7 | 记账 + 两条 report + 改名通知 + 有改动才 build | 人工出口只认仓库根 `TODO.md` |

## 3. 风评打分：为什么它是「入库闸门」而不是「参考意见」

### 3.1 问题

`discover` 抓候选的方式是：36 个关键词 × 2 页，每个关键词取 `page_size` 10/20 条。
图商返回的是**按相关度/距离排的前 20 条**，与「这地方值不值得去」**完全无关**。
所以一城的 200~400 条候选里必然混着：

- 已废弃的旧址、只剩地名的地方
- 同名不同址的小庙、小祠
- 连锁复刻的商业街（"XX 古镇" 全国有十几条）
- 差评一片的网红店（靠营销上榜，去了就后悔）

旧流程靠 A 段 AI 目测挑，判据不可复现 —— 换一轮、换个人结论就变，且没有留痕。
用户 2026-11-10 的原话：「抓景点，不能抓到一个景点，就开始弄数据……需要再搜一下
这个景点的风评，看风评如何，再确定是否需要入库」。

### 3.2 打分卡（四维加权）

`tools/rate_poi.py` 只接受四维分，缺一维直接拒 —— **只给总分等于又回到拍脑袋**。

| 维度 | 权重 | 看什么 | 低分特征 |
|---|---|---|---|
| 口碑 | 0.40 | 点评/携程/马蜂窝评分、差评密度 | 「避雷 / 踩雷 / 不值 / 宰客」占比高 |
| 独特 | 0.25 | 是否「只有这里有」 | 连锁、复刻街、随处可见的广场 |
| 密度 | 0.20 | 一次能看多少（看点/时长） | 单体小店、一块碑、孤塔 |
| 可信 | 0.15 | 官方/官媒背书、是否闭馆停业 | 只有自媒体吹、长期闭馆、已废弃 |

权重取舍：**口碑占 4 成**是因为它最能反映"去过的人怎么想"；独特 2.5 成用来挡
「连锁/复刻」；密度 2 成区分"专程去"和"顺路看"；可信 1.5 成只做否决项（闭馆、
停业直接拉垮），比重不宜高，因为官方背书本来就难查全。

### 3.3 判档与闸门

| 档 | 区间 | 动作 |
|---|---|---|
| `go` | ≥ 3.5 | 入库 |
| `maybe` | 2.5 ~ 3.5 | **仅当该城该子类还空着**才入 |
| `no` | < 2.5 | 不入库 |

闸门落在 `intake_candidates.py` 的校验里，**不是 prompt 里的口头约定**：

- 未评分 ⇒ 整批拒收（`--allow-unrated` 只给历史补录/紧急修数据）
- 判 `no` ⇒ 整批拒收，理由会打印出来
- 判 `maybe` ⇒ 放行但打印提醒

这样即使某轮 AI 忘了评分，也进不了库，而不是"漏一道工序"静默发生。

### 3.4 分数存在哪、为什么独立文件

`data/_generated/reviews/<city>.json`，**不与候选文件混放**。

理由：`discover` 落盘是「本次候选在前、旧候选按 title 合并」，重扫会把候选对象整个
换掉 —— 分数若挂在候选对象上，跑一次 B 段就没了。独立文件按「候选原名」索引，
跨轮存活，且 `rate` 同名覆盖（带 `at` 日期），天然支持"情况变了重新评"。

### 3.5 与 `popularity` 的关系

两个字段别混：

- `popularity`（0-100，必填）—— **热度**，前端同分排序 + 低 zoom 标注避让的依据
- 风评分数（0-5，在 reviews 里）—— **质量**，只决定入不入库

入库时 `pop` 由分数映射（4.5+→85 / 4.0+→75 / 3.5+→65），避免"好景点热度却写 50"。

## 4. 热点巡检（P6.5）

### 4.1 要解决什么

P2 查的是「这条记录写得对不对」（静态事实），P6 查的是「有没有新景点」。
两者都发现不了**最近在聊什么**：

- 某店被曝宰客 / 卫生问题 ⇒ 用户去了会踩雷，而库里还在正常推荐
- 某点突然爆火（官媒推荐、新上榜）⇒ 排序里该往上，现在沉在下面
- 某景区停业整顿 ⇒ 该降热度甚至归档

用户原话：「不能只扫某个城，还需要去找一下热点数据……哪个店需要避雷，
哪个点是新上的优质店，这些对应的数据都要去更新」。

### 4.2 三个查询（只查当前城）

| 查询 | 捞什么 |
|---|---|
| `<城市> 景点 宰客 避雷 投诉 曝光` | 负面：宰客、卫生、欺诈、事故 |
| `<城市> 2026 新开 网红 店 街区 榜单` | 正面：新开的店、新晋榜单 |
| `<城市> 景区 闭园 停业 整顿 装修` | 状态：闭园、停业、改造 |

### 4.3 证据分档（动数据的唯一门槛）

| 证据 | 动作 |
|---|---|
| A 档 + 停业/查封/永久关停 | `retire`（可逆归档） |
| A 档负面 + 仍在营业 | `fix tips` 加提示 + `popularity` 降 10~20 |
| A 档正面（官媒推荐/新上榜/新评 A 级） | `popularity` 升 5~15 |
| 只有 OTA 差评 / 自媒体吐槽 | `findings note --level B`，**一个字不改** |

A 档 = 政府/文旅部门公告、官媒、市场监管处罚。**「网友爆料」「疑似」一律只 note** ——
热点新闻标题党率高，一次错改比漏查十次贵。

### 4.4 热度调整为什么限幅 ≤20

`popularity` 同时决定：

1. 前端「同分」时的排序（`PoiList` 按它降序）
2. 低 zoom 下哪些标注先显示（`labelAvoidance` 按它排序）

所以它不能当"情绪分"用。一次调 20 已经是"从热门到冷门"半档，再多就是拿排序当惩罚。
真正严重的情况该走 `retire`，而不是把热度改成 5。

## 5. AI 点评：为什么它是「长尾清洗」而不是「一次性生成」

### 5.1 它读哪个字段、缺了会怎样

详情卡片读 `Poi.review`（`PoiReview`：`score` / `verdict` / `facets` / `body` / `basis` / `at` /
`fits` / `avoid` / `sources`）。**没有 `review` 的点整块不渲染** —— 这是有意的：
写「暂无点评」比不显示更伤，用户会以为这站没人维护。代价是 `data/` 里 4900 个点位默认都是空的。

### 5.2 两个分数不能互相校验（最容易搞混的一处）

| | 入库打分 `rate_poi.py` | AI 点评 `ai_review.py` |
|---|---|---|
| 回答什么 | 这个点位**该不该收录** | 这个点位**值不值得去** |
| 维度 | 固定四维（口碑/独特/密度/可信） | 按点位性质自取（展陈/人流/排队…） |
| 阈值 | 3.5 入库线 | 无闸门，全量都要有 |

`score` **同源**（都走四维加权口径），所以列表排序与入库判断不会打架；
但 `facets` 是**解释**，别拿它求平均去对 `score` —— 两者刻意不构成算术关系。

### 5.3 四档与分数必须对上

| 分数 | verdict |
|---|---|
| ≥ 4.5 | 专程去 |
| ≥ 4.0 | 值得一去 |
| ≥ 3.6 | 顺路看看 |
| < 3.6 | 时间富余再说 |

下界取 3.6 而不是 3.7：入库线是 3.5，落在 3.5~3.6 的点几乎不存在，把「顺路看看」压到 3.7
会让刚过线的点全掉进最差档。`_verdict_for` **不留四舍五入容差** —— 3.98 被抬成「值得一去」
会让结论和分数看起来对不上，用户第一眼就会觉得这分数是编的。（报错提示串由 `VERDICT_BANDS`
现算，曾经手写成「≥3.7」而与真阈值 3.6 分家。）

### 5.4 四道写盘闸门（整批拒收，不是逐条截断）

1. `verdict` 与 `score` 不同档
2. `facets` 少于 2 条或多于 5 条，或 label 长度不在 2~6 字
3. `body` 不在 40~400 字，**或一句负面都没有**
4. `basis=web` 却没给 `sources`

第 3 条是核心：**只夸不贬的点评是广告，不是点评**。词表刻意放宽（缺点/可惜/挤/排队/偏…
命中任一即过），宁可漏判也不逼着硬塞一个「不」字。

### 5.5 basis 决定要不要联网，也是诚实的唯一凭据

| 情况 | basis | 要求 |
|---|---|---|
| 本轮刚联网核实过这个点（巡检 P2 / 日抓 A1.5+A2） | `web` | `sources` 必须填真链接 |
| 其余同城点位 | `corpus` | 只用站内 `description`/`highlights`/`tips`/`practical` 合成 |

`corpus` 的点评**不许出现站内资料里没有的具体数字**（票价、米数、建成年份、店名、排队分钟数）——
写不出来就老实收窄成定性判断。前端两处免责（详情卡片短版 + 「关于」长版）共用
`web/app/common/ui/doc/AiReviewNotice.tsx`，**只此一份**；绝不包装成「用户评分 / 官方评定」，
那是伪造权威。

### 5.6 补全节奏（为什么不是一次性生成）

`ai_review.py next` 按 `popularity` 降序出清单，所以**热门点位先有内容**。

| 通道 | 每轮量 | 说明 |
|---|---|---|
| 每小时巡检 P5.5 | 20 条 | 本轮核实过的点用 `web`，其余同城用 `corpus`；该城写满后转全库热度序 |
| 每日 A 段 A4.5 | 本轮入库的 10~12 条 | 刚查过口碑，**必须全部 `web`**，不留空点位上线 |

按每小时 20 条 × 24 轮 ≈ **480 条/天**，4900 条存量约 **10~15 天**扫完一遍
（漏轮、被 00:00 任务顺延都会拖长）。之后进入「新增点位当场写」的常态，巡检不再需要批量补。

为什么不做一次性批量：一次写几千条必然滑向无模板废话
（「值得一去，环境不错，建议错峰」），而点评的价值全在**具体**。
宁可在十几轮里慢慢写，也不要一天生成 4900 段套话。

## 6. 三文件分工与人工出口

| 文件 | 谁写 | 谁读 | 语义 |
|---|---|---|---|
| `_tmp/patrol/findings-<city>.json` | 只有 `patrol_findings.py` | 下一轮 | 底层状态机（open/stale/closed + seen 轮次） |
| `_tmp/patrol/PENDING.md` | `patrol_report.py pending` | 下一轮 | 待办：DUE 到期 / READY 证据齐 / WAIT 未到日 / ARB 待仲裁 |
| 仓库根 `TODO.md` | `patrol_report.py todo` | **人** | 只有 `--human` 才进，正常 0 条 |

**通知通道**：WorkBuddy 的完成通知只显示任务名。所以 `todo` 末行打印 `HUMAN=n`，
`n>0` 时任务改名为 `… · ⚠️n 条待确认`。这是唯一能把待办送到手机上的通道 ——
不要指望人点开正文。

## 7. 已知坑

| 坑 | 表现 | 处理 |
|---|---|---|
| Wikimedia 429 | 一次重抓 3 个点位就大面积失败，且**静默变成"没图"** | 每轮最多 2 点；`grab` 撞 429 且空点位 ≥90% 时本身会拒绝落盘 |
| `tips` 的竖线 | `--set tips=甲\|乙` 不加引号会被 shell 当管道，参数被切断 | 必须 `--set "tips=甲\|乙"` |
| `--field` 写复合值 | `address/transport` | 只能单个字段，多个字段分开记 |
| findings 只进不出 | open 越堆越多，真正要看的那条被淹 | 每条要么 fix 自动结案、要么 close、要么第三轮 auto-stale |
| 改热度当惩罚 | 把 78 改到 20，该点从此在列表里沉底 | 幅度 ≤20，严重走 retire |
| 同名不同址 | 搜索命中的是另一个城市的同名点 | 核实时必须带城市名，坐标要算距离 |
| 图片缓存键 | `cand-{idx}.jpg` 位置名换批后会命中旧图 | 缩略图缓存键必须含 URL（已在 `review_images.fetch` 修） |
| 任务改名 | 每小时都改一次名字 = 每轮一次无意义写入 | 名字里的 `⚠️n` 与本次一致就不要调用 update |
| 点评写成广告 | `body` 全是好话，用户不信 | `ai_review.write` 硬拦（无负面词整批拒收） |
| `corpus` 编细节 | 站内没有的票价/年份被写进点评 = 造假 | 只许定性判断，具体数字必须有站内出处 |
| 档位阈值漂移 | 报错提示写「≥3.7」而代码是 3.6，写点评的一侧照错的查 | 提示串由 `VERDICT_BANDS` 现算；`check_app` AZ 组比对 `schema.ts` |

## 9. 验收方式

改完这条任务后必须验证的三件事（不是跑一遍看看有没有报错）：

1. **工具层**：`patrol_queue fix --set popularity=45 --dry` 能过、`=120` 被拒；
   `rate_poi.py` 缺维度/越界被拒、四维给全能算出分档。
2. **闸门层**：`intake_candidates._validate` 对未评分/`no`/`go`/`--allow-unrated`
   四档行为正确。
3. **护栏层**：`check_app` 里要有对应判据，且**反证过**（改坏必须报红）。
4. **点评闸门层**（2026-11-12 加）：`ai_review write --dry` 对四种毛病各试一次必须退出码 2 ——
   档位打架（3.65 写「值得一去」）、`facets` 只给 1 条、`body` 只夸不贬、`basis=web` 无 `sources`；
   改对后必须 `OK 写入` 或 `DRY OK`。

### 为什么「看图判定」仍然必须在回路里

站里有 **83 城 / 4900 个 POI**，图片全部来自采集流水线。旧管线有两个硬伤：

| 硬伤 | 表现 | 后果 |
|---|---|---|
| 固定收 3 张（`max_keep=3`） | 全库 89% 的点位"恰好 3 张"（2026-10-28 实测，修复前 4297/4808） | 能搜到 8 张也只留 3 张；不够 3 张就拿"品类氛围图"垫 |
| 零内容校验 | Wikimedia 按**文字**相关度返回，前 3 条直接入库 | 「西安地铁青龙寺站」标题里同时有"青龙寺""西安"⇒ 排在第一位 ⇒ 进了详情页 |

2026-10-29 起，采集侧已修（自动入库上限 6 张 / 入库前过相关性过滤 / 同城 URL 去重）；
2026-11-08 起，候选补图链路改为「抓全 → 逐张看图 → 判 ok 全收」（第十八节）。

实测两城的错误率（我逐格看图判的，这是"必须看图"的原始证据）：

| 城市 | 封面数 | 判为错图 | 典型错法 |
|---|---|---|---|
| 西安 | 57 | **30（53%）** | 北京回民小学挂在回民街 · 绍兴咸亨挂 5 家饭馆 · 阳朔航拍挂 3 处 · 马路照挂青龙寺 |
| 长春 | 57 | **33（58%）** | 星球大战 Chewbacca 挂长影老摄影棚 · 上海的古塔挂农安辽塔 · 新西兰溶洞挂吊水壶 |

> ★ 错图里**标题全都是对的**（"Qinglong Temple, Xi'an" 就是那张马路照的文件名）。
> 元数据过滤只能拦"说得明白的错"（地铁站 / 地图 / 坐标十万八千里），
> **"标题对、画面是别的东西"只有看图能发现** —— 这是整个流程必须有人在回路里的唯一原因。
> ⇒ 也是为什么配图库**可以进候选池、绝不能回自动入库链路**（第十七节）。

## 四、每次执行具体做什么

```
next --count 2
   ↓  拿到 2 个 slug（POI 少的先做，跳过账本里 refetched 过的）
images <city> --force          ← 强制重算，否则旧数据"恰好 3 张"永远不会变
   ↓
images <city>                  ← 不带 force：只重试带 `_noImage` 的点位（网络抖动误标）
   ↓
sheet <city> --covers --refresh ← 下缩略图 + 拼 4×5 对照表 + 写清单
   ↓
账本 refetched += slug · 日报追加
```

### 为什么是这两趟（顺序不能换）

| 趟 | 命令 | 为什么 |
|---|---|---|
| 1 | `images --force` | 旧数据 89% 是"恰好 3 张"。不带 force 会走 `have and not force → skip`，永远修不到 |
| 2 | `images`（不带） | 第一趟里 Wikimedia 偶发断连时 `search_wikimedia` **静默返回空**，点位被标 `_noImage`。西安城墙第一趟被误标"没图"、重试拿到 6 张真图 ⇒ 必须有第二趟 |

### 为什么对照组是"封面"而不是全量

一个点位最多 6 张图，全量审 4820×5 ≈ 2.4 万张，看图成本不可承受。
**封面（`coverIndex=0`）是详情页首图、也是卡片图**，错得最显眼、最该先修。
非封面图的错留到以后（账本 `image-rebuild.json` 的 `_note` 已写明这个边界：
`reviewed = 封面已过审查；非封面图尚未逐张看` —— 不要假装全审过了）。

### 5.1 三个"审查白做"的坑（都已写进工具，但你要知道为什么）

| 坑 | 现象 | 现在的做法 |
|---|---|---|
| 序号与格子**错位** | 读图的一方把 `#5` 判成 `#1` ⇒ 删错图 | 序号**烧进每格左上角**白底方框（不只在格下方写小字） |
| 删图后**新封面没审** | 删掉封面后 `coverIndex=0` 指向原来的第 2 张（没审过） | 删完**必须再出一轮 sheet 再审**。长春一审删 33 张，二审又从新封面里判出 30 张错的 |
| 判定**按位置猜** | 表格最后一列/行不满时，位置推断必错 | 一律按格内 `#序号` 作答；空白格写"空白" |

### 5.2 图下不来怎么办

`[下载失败]` 的格子**不补跑**（wsrv.nl 偶发超时）。按 Commons 文件页判定，
并在 `note` 里标「图未下成，按文件页判定，待复核」—— **不许默默放过**。
判定会按 URL 进全局缓存 `_tmp/review/verdicts-cache.jsonl`，**reject 过的图永远记住**（下轮重抓不会回来）。

## 十一、与设计文档的关系

`plans/06-data-maintenance.md` 的 6.1 / 6.2 写的是**早期设想**：GitHub Actions 每月跑
`check-images.yml`、HEAD 扫全量 URL、404 用 `query` 重搜后开 PR。那份设计解决的是**死链**（404），
解决不了**文不对题**（图活着、但是别的地方）。

实际落地的是本文这套：**本地定时任务备料 + 会话看图审查**。两者的关系：

| | 早期设想（06 文档） | 现在落地（本文） |
|---|---|---|
| 触发 | GitHub Actions 每月 1 号 | 本地定时任务每天 00:00 |
| 判据 | HTTP 状态码（404） | **看图**（内容对不对） |
| 产出 | 自动 PR | 人工判定 → `apply` → build |
| 适用 | 图挂了 | 图错了（更常见、更隐蔽） |

`query` 字段（"这张图想表达什么"）两边都依赖 —— 它是重搜的唯一依据，`images.py` 必须继续写。

前十一节讲的是「**重抓的新图**怎么审」。这一节讲另一件事：**库里躺着的历史图**。

### 12.1 为什么必须单独做一次

`USE_STOCK_SOURCES=False` 是 10-29 才关的，**存量从来没人清过**。10-31 全库扫一遍
（4820 个点位 / 13674 张图），三个硬事实：

| 类别 | 张数 | 占比 | 是什么 |
|---|---|---|---|
| `ok` | 5250 | 38% | 元数据对得上 |
| `stock` | 6602 | **48%** | Pexels / Unsplash **主题图库** |
| `reject` | 335 | 2.4% | 命中否决词（飞机、地铁站壁画、澳门招牌） |
| `dup` | 672 | 4.9% | 同一 URL 挂 ≥3 个点位 |
| `suspect` | 815 | 6.0% | 标题、坐标都对不上点位名 |

`stock` 那 48% 是最刺眼的：`pexels-photo-32686464.jpeg`（一张美食氛围图）挂在
**298 个餐饮点位**上、横跨 **48 座城**；2127 个点位（45%）的图**全部**是这种。
搜「农安辽塔」给你上海的古塔、搜「瓷泥煨鸡」给你尼泊尔的手抓饭 —— 不是相关度低，
是**根本没有对应关系**（图库按关键词返回配图，没有地点概念）。

### 12.2 分级：什么能自动删，什么只能标记

`tools/clean_images.py` 的 `AUTO_RULES` **只允许 `("stock", "reject")`**。

★★ `dup` / `suspect` **不许自动删**。原因不是保守，是它们里有大量**合理**的图：
Wikimedia 的「景区大图挂景区内几个子点位」会同时命中 dup；「合肥三国新城遗址公园.jpg」
标题明明对得上，却因为 `core_name` 取不到而落进 suspect。自动删它们 = 把有真图的点位
一起清空。这两类只能交给看图。

这条线由护栏 **AW** 守着（`check_app.py`），改 `AUTO_RULES` 会直接红。

### 12.3 操作顺序（别搞反）

```
① clean_images.py scan                     全库只读，出 _tmp/review/clean-report.json
② clean_images.py apply --rules stock,reject --dry    看数字对不对
③ clean_images.py apply --rules stock,reject          执行
④ run.py images <city> --force             重抓补图（分批，见 12.4）
⑤ review_images.py sheet <city>            出对照表
⑥ 看图判定 → verdicts-<scope>.jsonl → apply
⑦ run.py build                             全量（防 cities.index.json 被单城覆盖）
```

★ ④ 必须在 ③ 之后：先删干净，重抓才是白纸重画。反过来会把刚删的图又抓回来。

### 12.4 重抓能补回多少（实测，别抱不切实际的期待）

| 城 | 重抓前 | 重抓后 | scenic 无图率 |
|---|---|---|---|
| luoyang（知名） | 45 张 / 38 无图 | **98 张 / 32 无图** | 77% → **35%** |
| jingdezhen（冷门） | 36 张 / 44 无图 | 50 张 / 47 无图 | 仍 77% |

★ **重抓救得回景点，救不回餐饮**。洛阳 scenic 类翻倍；但两城的 food（67%）、
hotspot（70%）、culture（100%）都抓不到 ——「瓷泥煨鸡」「乐平赣剧」这类东西
Wikimedia 本来就没有照片。**占位卡是终态，不是失败**。

★ `--force` 会让原本有图、但新过滤器不认的点位**变空**（jingdezhen 无图数 44→47）。
这是"诚实的退化"：原来那张本来就不对。别因为数字变差就回滚。

★ 每城跑**两趟**：`--force` 重算 → 不带 force 再跑一次（只重试 `_noImage` 的点位）。
只跑一趟会漏掉一批偶发断连的点位（长沙 8 个、承德 6 个都是第二趟捞回来的）。

### 12.5 已知坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 重抓过了还剩一堆 Pexels 图 | `step4_images` 的 `if have and not force` 会**跳过已有图的点位** | 必须 `--force`，否则旧图原样留着 |
| `apply` 后点位字段烂掉 | 少了 `coverIndex = 0` / `_noImage` / `updatedAt` | 护栏 AW 会红，别删那三行 |
| 删完 build 报一堆 WARN | `_noImage` 点位是 WARN 不是 ERROR | 正常，前端走占位卡 |
| 单城 build 后城市索引只剩一城 | `run.py build <city>` 会覆盖 `cities.index.json` | 一律跑全量 `run.py build` |

## 十三、审查工具自身的六个坑（2026-10-31 实测）

这一节记的不是数据错，是**审查工具自己会静默失效**的六条。它们的共同点：
出错时**没有报错**，只是"少看了几张"或"删错了图"。

### 13.1 UA 不带 URL → 图取不回来（429 / 403）

`review_images.py` 原来的 UA 是 `travel-strategy-image-review/1.0 (local; low-frequency)`。
敦煌实测同一张图（玉门关信息牌）：

| UA | 结果 |
|---|---|
| `…(local; low-frequency)` | **HTTP 429** |
| 不带 UA | **HTTP 403** |
| `…(https://www.mediawiki.org/wiki/API:Etiquette; local review tool)` | **200** |

后果：敦煌 56 格里 7 格（5 张沈尹默手稿 + 2 张玉门关说明牌）全部取不到，
对照表上只印「[下载失败]」，**而这座城仍然会被记进 `reviewed`** —— 那 7 张从没被人眼看过。

★★ 判据已进护栏 **AW**：`direct_thumb()` 必须存在 + 失败必须打印「取不到图」+ 格数与清单。
反证 `_tmp/revert_probe_fetch.py` **2/2 全红**。

### 13.2 镜像失败 ≠ 没图，必须再试直连

`wsrv.nl` 对一部分历史档案照（`Bundesarchiv` 1938 年德国西藏探险队、`in Tomba` 版画）
是**稳定失败**，不是抖动，重试镜像等于永远看不到。现在的取图顺序：

```
wsrv.nl ×3  →  upload.wikimedia.org 官方缩略图  →  原图 ×2
```

★ 还有一档必须留**原图**：`Gaoligongshan IMGP5778.jpeg`（腾冲）三种宽度的官方缩略图
全部 **400**，只有原图 200。审图只要看得清，体积大点无所谓。

#### 缩略图缓存必须按 **URL** 校验，不能只用文件名

缩略图落盘名是 `cand-{idx}.jpg` —— 这是**位置名**。同一座城重抓一次，新清单的
`#48` 与上一批的 `#48` 是两张不同的照片，而 `fetch()` 只要看到同名文件存在就直接返回：

```
2026-11-09 黄山实测：对照表 #48 贴出来的是「黄山迎客松」，
而新候选清单 #48 是「西递村落.jpg」⇒ 看图判定全程在判另一张照片，零报错。
```

修法：每个缩略图旁边写一个同名 `.src` 文件存下**这条格子的真实 URL**，
命中缓存前先比对；对不上（或老缓存根本没有 `.src`）就重下一张。
代价是历史缓存一次性重下，之后照常命中。

★ 这条和 13.3 是同一类病：**缓存键选错了维度**。凡是"按键位/序号缓存"的地方，
换一批数据就会静默张冠李戴，而报错是零。

### 13.3 `apply` 跑第二次会按旧序号删到别的图

`manifest-*.json` 里的 `imageIndex` 是**出表那一刻**的序号。删完图再跑一次 `apply`，
序号已经重排 ⇒ 按旧序号删 = 删到别的图上，**零报错**。

现在 `apply` 会先比对该文件实际张数与 manifest 记的张数，不一致就跳过并提示
「表格已过期，先 `sheet --refresh` 再看」。

★★ 这条判据第一版**自己也会静默跳过**：`expect` 是按"**带判定的行**"算最大序号 +1，
只判了某点位最后一张（乐山 #6 微缩模型）时 `expect` 就偏小，5 个点位被当成「表格已过期」
整批不回写，只印了一行跳过。现在按 `full_of`（该文件**全部** manifest 行）算快照，
并加第二条判据：序号上的 **URL 必须与快照一致**（图还在但顺序被洗过也要拦）。

### 13.4 `apply` 只报"改了几个 POI" ⇒ 删错看不出来

福州实测：我手写判据 `{92..99}` 想删万福寺，**实际 #92/#93 是华林寺的真图**
（万福寺是 #94-#99）。`apply` 只回一句「改动 16 个 POI」，没提华林寺，
等回头核对才发现删错两张。

现在 `apply` 逐条印出被删图的 alt：

```
     - 又见敦煌: 沈尹默《匏瓜庵谈艺录》手稿释文2.jpg
     - 玉门关: Info Yumenguan.JPG
```

★★ **序号必须对着 manifest 核**，别凭"我记得那几张在 92-99"。判据里写的数字
是人眼在对照表上读出来的，读错一格就跨点位删图。

### 13.5 同一张图被判 ok 又被判 reject ⇒ 后写的赢，好图被删

`verdicts-cache.jsonl` 按 **URL** 去重，`load_cache()` 后写的覆盖先写的。
一张图在一个点位是正主、在另一个点位是错图时，两条判定会同时留在文件里，
**最终生效的是最后那行**。

西安实测：`翠华山 (3487673551).jpg` 先有 `ok`（10-16 封面审），后有一条 `reject`
（别的点位/别的城判的），apply 时 `reject` 赢 ⇒ 翠华山唯一一张图被删成空点位，
而这条删除**不在我这次的 verdicts 里**，是缓存带出来的。

```bash
grep -n "<URL 关键词>" _tmp/review/verdicts-cache.jsonl     # 先看有没有自相矛盾
```

救法：给该 URL **补一条 `ok`**（后写覆盖），再从 git HEAD 把 image 对象放回去（见 13.6）。
★ 更根本的做法是让缓存按 `(城市, POI, URL)` 记，但那样"这图永远是错的"就退化成本城有效 ——
现阶段宁可补 ok，也不要让缓存带出无声删除。

### 13.6 误删怎么救
```bash
# 1) 从 git HEAD 取回该点位的完整 image 对象（含 credit，不许自己编）
git show HEAD:data/cities/<省>/<市>/pois/<类>/<slug>.json
# 2) 只补回被误删的那几条（按 URL 比对），顺便 coverIndex=0、清 _noImage、写 updatedAt
# 3) 从 _tmp/review/verdicts-cache.jsonl 里**撤掉那几条 reject**
#    —— 否则以后每次重抓都会被永久跳过
```

★ HEAD 不一定有你删的那张（可能是更早的快照，福州 `picture33` 就只找回 1 张）。
找不回就接受少一张，**不要伪造 credit**（红线：图片必带 credit）。

## 十四、无图点位自动补图任务（2026-11-01 新增，**会自删**）

前十三节都有一个人工环节：定时任务备料、会话里看图判定。这一节是**把这个回路也自动化**——
定时任务自己抓、自己看、自己写回，全库做完**自己把自己删掉**。

| 项 | 值 |
|---|---|
| 名称 | 行迹 · 无图点位自动补图（做完自删） |
| id | `58792aa5-7893-4f2a-8081-dbf2d828697a` |
| 频率 | `FREQ=HOURLY;INTERVAL=1`（每小时一轮） |
| 每轮工作量 | 1 座城（本轮 <25 分钟则再做第 2 座） |
| 收尾 | `next` 返回 `ALL_DONE` → 全量 build + `check_app` → **`automation_update mode=delete` 删自己** |
| 账本 | `.workbuddy/memory/image-rebuild.json` 的 `refilled` / `attempts` / `skipped` |

### 14.1 【历史】和第三节任务的分工（当时两个任务不能同时开）

| | 第三节「每日重抓 + 备料」 | 本节「无图点位自动补图」 |
|---|---|---|
| 解决什么 | **已入库的图错了**（文不对题） | **点位根本没有图** |
| 谁判定 | 会话里（人/模型看图） | 定时任务自己（同样看图） |
| 动哪个数据 | `images --force` 重抓覆盖 | 只往空的 `images` 里加 |
| 现在状态 | **PAUSED**（2026-11-01 停） | ACTIVE |

★★ **为什么必须停掉第三节那个**：它每晚 `images --force` 两座城，而账本 `reviewed=83`（全库已审完）
⇒ 重抓 = **把已审过的图换成未审的新图**，等于自己撤销审查成果；并且和补图任务抢同一个限流接口（429 会被静默吞成"没图"）。
要恢复它，先确认补图任务已经自删（`refill_queue.py status` 显示待补 0 城）。

### 14.2 三个工具（都是这轮新写/搬出来的）

| 工具 | 干什么 | 为什么必须单独存在 |
|---|---|---|
| `tools/refill_queue.py` | `next` / `done` / `fail` / `status` | "下一座做谁、是不是全做完了"交给脚本算。写在 prompt 里让模型自己数，每天数字都不一样 ⇒ 永远不知道该收尾 |
| `tools/remap_candidates.py` | 按序号改写候选图归属（`{"8":"大同关帝庙"}`） | `grab` 按**坐标最近**分配，图对但点位错。不改归属就只能整批 reject（大同因此白扔 30 张） |
| `tools/refill_one_poi.py` | 给单点位补图（指定 Commons 文件名） | 整城流程会覆盖 `candidates.jsonl`，序号一错就把图写到别的点位且零报错 |

### 14.3 自删机制（这套东西最容易做错的地方）

```
next → ALL_DONE
  ├─ refill_queue.py status      确认待补 0 城（不是凭日志感觉）
  ├─ run.py build                全量，不许 build <city>（会覆盖 cities.index.json）
  ├─ check_app.py                期望 ALL_CLEAN
  ├─ automation_update mode=list → 按**名字**找 id（不写死 id）
  └─ automation_update mode=delete id=<list 返回的那个>
```

★ **按名字找、不按记下来的 id**：id 是人建任务那一刻的产物，写进 prompt 就等于埋一个会过期的常量。
★ **删不掉要有兜底**：`automation_update` 不可用时写 `.workbuddy/memory/REFILL_DONE.txt` 提示手动删，
**不许**当作已删（否则它每小时空转、还会在日志里反复写"已完成"）。
★ 删之前必须清 `_tmp/fetch/.running`，否则残留锁会让"下一轮"永远 BUSY。

### 14.4 防重入（为什么要那把锁）

一轮可能超过 1 小时（大城 116 张候选 / 6 页对照表）。若上一轮没跑完、下一轮又起来，
两个进程同时打 Wikimedia ⇒ **429**，而 `grab` 的 429 会被静默当成"图源没有这张图"（第一批踩过，整城判成"没料"）。

```bash
f=_tmp/fetch/.running
if [ -f "$f" ] && [ $(( $(date +%s) - $(stat -c %Y "$f") )) -lt 2700 ]; then echo BUSY; else touch "$f"; echo GO; fi
```
- `< 2700` 秒（45 分钟）= 认为上一轮还活着 ⇒ 本轮直接退出，什么都不做
- 超过 45 分钟视为**陈旧锁**（进程已崩）⇒ 抢过来继续
- 已实测三态：首次 `GO` / 立即再跑 `BUSY` / 伪造 50 分钟前 `GO`
- 每轮结束（成功或失败）都要 `rm -f _tmp/fetch/.running`

### 14.5 prompt 原文

见任务本身（`automation_update mode=view`）。改 prompt 的红线，与第七节一致，另加三条：

1. **不许降级成文字判定**。没有视觉能力就停下写日志——"看起来审过了"比不审更危险。
2. **抓 0 张要 `fail` 记账，不许静默跳过**。连 2 次才放弃，且放弃要进 `skipped` 留痕。
3. **判图前必须先打印 idx → poi 区间**。凭记忆切段必错一格（平遥把凤仪门当二郎庙，6 张院落照写进了城门点位）。

### 14.6 三个关键问题（2026-11-01 实测，不是推测）

**① 上一轮没跑完，下一轮会不会并发？——不会，调度器自己串行。**

`LocalAutomationScheduler` 的日志与代码里写着：

```
skip same-source automation <id> (<name>): sourceKey=a8163223 already active (serialized, max 1); keep due for next tick
started tickMs=30000 activeTickMs=5000 missedWindowMs=86400000 concurrency=3
```

| 参数 | 含义 |
|---|---|
| `serialized, max 1` | **同一个 sourceKey（= 同一个工作目录）同一时刻只允许 1 个 run**。上一轮还活着，本轮到期的那次会被跳过并标记 `keep due`，等上一轮结束立刻补跑 |
| `concurrency=3` | 全局最多 3 个 run 同时跑，但那是**不同工作目录**之间的事 |
| `tickMs=30000 / activeTickMs=5000` | 调度器 30 秒扫一次，有活跃任务时 5 秒扫一次 ⇒ 上一轮一结束，积压的那次马上派发 |
| `jitterMs` | 派发时加 0–25 秒随机延迟，避免同一秒齐发 |

本地化文案里还有 `alreadyRunning: "This scheduled task is already running. Please try again later."`
和 `concurrencyLimit`，说明连**手动触发**也会被拒。

⇒ 结论：**不会双开**。一轮拖到 2 小时也不会堆出两个进程，只会把后面的 occurrence 顺延。
`_tmp/fetch/.running` 那把锁因此是**第二道保险**（防的是"后台 grab 子进程残留、上一轮已被判结束"这类缝隙），
成本接近零，留着。★ 但 BUSY 分支**绝不能删锁**——锁不是你的，删了才是真双开。

**② 定时任务进程有没有读图能力？——有，是真的看图。**

探测任务（16:47 一次性）对 `_tmp/fetch/datong/sheet-cand-00.png` 的描述：

> `#0`：三重檐歇山顶楼阁，灰筒瓦（脊上带小兽），朱红廊柱与红色板壁，两层檐下各悬一块横匾；
> 坐在灰色砖石城台基座上，基座正中开大红门洞……左侧背景还有一座双尖塔的西式教堂立面。
> `#8`/`#9`：单层殿宇，灰瓦硬山顶 + 朱红廊柱 + 木格门窗，檐下一方横匾。

这层细节（檐数、屋顶形制、瓦色、基座类型、背景教堂）**不可能从文件名或 prompt 里推出来**
⇒ 「会话里看图判定」那套流程搬到定时任务里成立，不需要人在回路。

**③ 自删可不可行？——可行，但会把自己这轮踢掉，看着像失败。**

两次实测：

| 任务类型 | 触发 | 结局 | 记录是否消失 |
|---|---|---|---|
| 一次性（once） | 16:47 | 64 秒后 `[CANCELLED] unknown_interrupted`、`success=false` | **消失了** |
| 重复（DAILY 定时） | 16:52 | 13 秒后 `success=false` | **消失了** |

原因：`automation_update mode=delete` 删任务时会**顺带取消正在跑的那轮会话**（`AbortError: This operation was aborted`），
所以 run 的历史记录恒为失败。**这是正常现象**，不是删失败。

⇒ 所以收尾顺序被写死成：`status` 确认 → 全量 `build` → `check_app` → **写日志** → `delete`。
delete 之后不许再做任何事，也不许因为"看起来失败"去重试或恢复任务（否则任务回来了，白删）。

### 15.4 `--pages=2` 是这套东西的关键参数（实测）

`step12_discover` 的 `pages` 会**乘请求数**（每页各打一遍关键字），`page_size=10*(page+1)`
⇒ 第 2 页拿 20 条。2026-11-01 合肥实测：

| | 候选数 | 请求数 |
|---|---|---|
| `--pages=1`（10-22 老数据） | 212 | 36 |
| `--pages=2` | **432** | 72 |

决定（`_pages_for`：`>= 60` 条双页 72 次，否则单页 36 次摸底），**不再看余额**；
最后一城腾讯用尽时在本城某个关键词处自动切高德补完剩余关键词、当天收手。
**200 次精确用尽**（`RESERVE=0`）。

★ 2026-11-09 更正：此前结论是「一晚 1 城（72 次）留足冗余，别贪 2 城」——
  代价是**日配额 128 次白白过期**（实跑台账 75/200 连续多日）。实测 B 段一座城
  只花 2m25s，且与 A 段的 `images` 并行 ⇒ 多排 2 城几乎不增加总时长，
  83 城的重扫周期从 **83 天压到 ~31 天**。真正的硬上限是 200 次本身，不是"贪多"。

★ 2026-11-10 再更正：`next` 的**静态切分**仍不行 —— 一城 72 次、200 除不尽，
  切出 `72+72+36=180` 后固定扔掉 20 次（11-08 实跑 176/200、11-09 实跑 177/200，
  用户连续两次反馈"跑不满"）。改成**跑完一城再看 `remaining`**：`left > 0` 就开下一城，
  靠 `count_usage()` 发请求前记账保证精确。11-10 01:40 实测（当天剩 23 次）：
  深圳跑 23 次腾讯 → 第 24 个关键词起自动切高德 13 次补完 → 账本 **200/200**，
  候选 235→343（`merge` 落盘，没退化）。

★ 2026-11-10 三改：上一版仍有「`left >= 2*kw` ⇒ `pages=2`，否则 `pages=1`」——
  **拿剩余次数决定扫多深**，跟这城有多少景点毫无关系。后果是余额快见底时，

  根本没有「小城省着扫」的需求 ⇒ 页数改由 **`_pages_for(n)` 只看规模**（`>= 60` 双页）。

  用尽就切高德补完本城、当天收手。`next` 里的 `_plan()` 预算算术（`cost` / `unused`）随之删除。
  探针 `_tmp/probe_pages_by_scale.py`：`left` 取 200/100/40/20 时同一座城的 `PAGES` 必须恒定。

### 15.5 顺手修掉的 bug：跨零点「零请求」误报

`step12_discover` 里本城请求数这么算：

```python
net_requests = max(0, after_req - before_req) if same_period else 0   # ← 老代码
```

账本在**当日第一次请求时惰性归零**，所以跨零点那一次 `before` 是昨天累计值、`after` 是今天从 0 起算的值。
老代码直接判 0 ⇒ 外层 `round_net == 0` 误报「本轮零请求」并停止循环。
实测 11-01 21:26 那轮：真发 **72 次请求**、候选 212→432，日志却写「零请求」
⇒ 定时任务若按这行日志判断「有没有干活」，会得出完全相反的结论。

改为跨周期时取 `after_req`（本轮从 0 起算的真实值）。**验证**：修复后全缓存重跑同一城，
正确打印「本城全命中缓存，0 次请求 ⇒ 不重写」且**文件 md5 与 mtime 均未变**（不重写判据仍有效）。

## 十六、任务整合与「不限量 + 两轮看图」（2026-11-01 晚）

### 16.1 任务从三条并成两条

主人原话：「定时任务整理一下，一个是每天定时去抓新的城市的数据，每天一座城，不抓多了」。
「候选入库」和「点位拓取」本来就是**一个业务闭环的两步**，拆成两条要记住先后关系，合并成一条：

| 现在 | 频率 | 做什么 | 会自删 |
|---|---|---|---|
| **每日抓新城市数据** | 每天 00:00 | A 段入库一座城（消费存量候选）→ B 段拓取一座城（补新料） | 否 |
| **无图点位自动补图** | 每小时 | 1 座城的无图点位补图（两轮看图） | 是 |

★ **A 在 B 前**的理由：入库是"变现"、拓取是"囤料"。先变现，B 段就算因配额失败，成果也已落袋。
★ A、B 是**两个不同的城**，各用各的队列脚本判定（`intake_queue.py` / `discover_queue.py`）。

### 16.2 为什么"放开候选数量"不是因为命中率会变高

用 6 城已判的 565 张候选做了统计：

| 候选数 | 点位数 | 判 ok |
|---|---|---|
| 满额（11~12 张） | 25 | 42/298 = **14%** |
| 未满额 | 70 | 72/267 = **27%** |

**满额点位的命中率只有未满的一半。** 因为能拿满 12 张的恰恰是「戏曲演出、连锁小吃、同名异地」
这类关键词一搜吐一堆的；真正对的景点（云台观、太白楼）通常只有 3~7 张候选。
另外 geo 通道按距离排序，被截掉的是远的那些，本来就更不相关。

那为什么还要放开？因为**截断发生在 grab 里** —— 第 13 张之后**永远没机会被看到**，
而"这张到底对不对"只有看图的人能定。这是**流程问题**，不是命中率问题。

| 参数 | 2026-11-01 的值 | **2026-11-08 起** | 说明 |
|---|---|---|---|
| `MAX_CAND` / `mine[:60]` | 60 | **删除，不截断** | 抓到多少留多少；去留只由看图判定 |
| geo `limit` | 30 | **50** | Commons 匿名单次上限（实测传 200 也只回 50） |
| 实体 `limit` | 4 | **20** | P18 / 条目主图 / 分类页 |
| `search_wikimedia(per_page)` | 8（默认，最隐蔽的截断） | **50** | 候选链路显式传 50；自动入库链路仍用默认 8 |
| 关键词触发 / quota / `STOP_AFTER` | `<8` 才跑 / 5 个词 / 够 8 张停 | **全部查询词都跑、不提前停** | 同一个点位的其他叫法、译名、品类词不再被掐在 grab 里 |
| 配图库 `per_page` | 6 / 家 | **80（Pexels）/ 30（Unsplash）** | 两家 API 的 per_page 上限 |
| 配图库每城封顶 | 12 / 6 次 | **删除**，改按小时额度 180 / 45 次 | 第三方 200 / 50 次每小时，留余量；跨整点自动重置 |
| `apply` 入库张数 | `imgs[:6]` | **判 ok 全收，不截断** | `schema.py` / `schema.ts` 的 8 张硬上限同步删除 |
| `step4_images.MAX_PER_POI` | 6 | **6（保留）** | 自动入库链路**没有看图环节**，不能跟着放开 |

★ 保留的护栏（放开抓取 ≠ 放脏图进来）：
`rejected_urls` 历史判废缓存、`grab` 的同城 URL 去重、`verdict_for` 只作**参考分**不删图、
429 拦截（空点位 ≥90% 且撞过 429 ⇒ 拒绝落盘并返回 -1）、`_is_latin(en)` 与 `specific < 3`
这两条配图库**准确性**门槛。放开的是"数量"，不是"谁都能进库"。

### 16.2.1 实测：放开后一城候选会到什么量级

2026-11-08 用合肥做隔离目录小样本（`grab hefei --limit 2`，不写进真实 `_tmp/fetch/`）：

```
001/2 巢湖渔家文化   候选 110
002/2 合肥龙虾节     候选 80
→ 190 张 / 2 个点位，单点位 110 张 > 旧硬上限 60
```

- 这 190 张里 **110 张来自配图库**（80 Pexels + 30 Unsplash，全是"渔夫撒网"类氛围图），
  正是看图环节要判废的那一类 —— 但按新口径它们**必须先被看到**，不能由代码替 AI 删。
- Commons 侧：该点位坐标邻近能回 10 张，但全被 `rejected_urls`（历史判废）挡掉；
  4 个关键词查询全 0、`429 = 0`，实体 0。⇒ 说明「通道全空」不等于限流，缓存护栏在正常生效。
- 代价：`--dense`（48 格/页）粗筛时，单个 110 张的点位要 **3 页**。这是"全量交给 AI"的明确成本。

### 16.3 代价由「两轮看图」吸收，不是硬扛

一城候选从 100 涨到 400~900 张（**2026-11-08 全量放开后可达数千张**，见 16.2.1 实测）。
按 20 格/页要 25~45 页甚至上百页，逐页精看不现实。所以拆两轮：

| 轮次 | 命令 | 网格 | 只干什么 |
|---|---|---|---|
| 第一轮 粗筛 | `sheet <city> --dense` | 8×6 = **48 格/页**（160px） | 剔除明显不可能的类别（人像/地图/货架/室内展厅/停车场），**不确定就留** |
| 第二轮 精看 | `sheet <city> --only 1,5,9` | 4×5 = 20 格/页（300px） | 逐格下结论：是不是这个景点/这家店 |

★★ **粗筛不许下"对不对"的结论**：160px 看不清匾额和店招，「这是不是这座庙」只有大图能定。
粗筛只回答"值不值得精看"。反过来只做精看，900 张要 45 页，成本不可控。

实测（凤凰城，4 个点位 39 张）：粗筛一页看完，一眼看出「苗绣」那 10 张全是古城街拍 + 一只猫，
整批该废；而「凤凰古城街区」的 29 张全是沱江吊脚楼，全留。

### 16.4 顺手修掉的两个静默故障

**① PIL 默认字体不含中文**（`_cjk` / `_fit`）

`ImageDraw.text()` 不传 `font` 时用 `load_default()`，它**只有 ASCII 字形**。
所以旧对照表里所有中文（点位名、"已属「XX」"、通道名）一直渲染成「□□□□」——
只是判定时靠 manifest 打印的序号区间对照，没人依赖格内文字，所以从没暴露。
dense 表每格只印点位名，文字一乱等于"这格属于谁"全丢，必须修。

`_fit()` 按**像素宽度**截断（不能用 `text[:9]`）：中文全角 12px、英文半角 6px，
同样 9 个字符宽度差一倍，「慈城名牌年糕(鼓楼店)」会压到隔壁格。

**② 429 被静默吞成"没图"**（`entity_images.hits_429()`）

`_api` 重试 4 次都撞 429 后返回 `None`，对调用方来说与"这个点位确实没图"**一字不差**。
2026-11-01 凤凰城实测：同一坐标单独测返回 10 张，紧接着 4 并发 `grab` 全 0。

后果比"没抓到"严重：`refill_queue` 会记一次 `fail`，连 2 次就进 `skipped` **永久跳过这座城**。

修法：`_api` 每次撞 429 累加 `_HITS_429`，`grab` 取前后差值，在
「空点位 ≥90% 且撞过 429」时**拒绝落盘并返回 -1**（退出码 1），等图源空闲后重跑。
「连续两次仍为空」才当作真没料。

### 16.5 腾讯配额用尽改为自动切高德

主人说「腾讯每天 200 次可能不够，高德也刷新了」。查下来：`place_search` 一晚 1 城 72 次
（占 36%）其实够用，但代码里有个**让高德白白闲置**的旧判据：

```python
# 旧：_quota_dead() 只看腾讯，用尽即整城跳过（0 请求）
# 注释写的是「2026-10-08 用户确认：高德额度已满，不可用」
```

高德是**月配额**，11-01 已刷新（实测 `amap.place_search('合肥 博物馆')` 正常返回 10 条）。
所以旧判据的后果是：明明高德能用，却整城不发一个请求。

新判定顺序：

| 情形 | 行为 |
|---|---|
| 腾讯还有额度 | 用腾讯 |
| 腾讯用尽 + 高德可用 | **`GEO_PROVIDER=amap` 强制切高德**，继续跑本城（打一次提示） |
| 两家都不可用 | 整城跳过，`quotaHit=1` 留给下一轮优先补 |

★ **为什么必须显式设环境变量**，不能等 `geoprovider` 自己切：它的切换条件是
`tmap.quota_exhausted("place_search")`，而那是**进程内**内存集合 —— 新进程启动时必定是"没死"。
腾讯配额早就满了的情况下，新进程仍会先打腾讯、白烧到收到第一个 121 才切（失败请求同样计费）。
账本预判是零成本的前置判断。

★ 高德切过去后用掉的是**月配额**（用一点少一点，下个月才回来），所以仍然只做 1 城。

## 十七、配图库恢复为「候选源」（2026-11-08 用户质疑后复核）

用户原话：「现在每天取数据，不光是代码上去取图，代码取完图，会让 AI 再过一遍，
哪张图是无关的，舍弃哪张，所以这两个数据源，其实也算是有用的」。

### 复核结论：用户成立，但要分两条链路

| 链路 | 谁判最终去留 | 配图库能不能进 |
|---|---|---|
| `run.py images` → `step4_images.pick_images` | `verdict_for` **判完直接入库**，没有看图环节 | ❌ 继续关（`USE_STOCK_SOURCES=False` 不动，护栏 AV ②½ 守着） |
| `fetch_candidates.py grab` → sheet → 看图 → `apply` | **AI 看图**逐格判 ok/reject，reject 永久进缓存 | ✅ 恢复为候选源 |

关键证据：`tools/fetch_candidates.py` 里 `verdict_for` 的结果写进 `filter` 字段时
注释就写明「**只是参考分，不据此删**：ok/suspect/reject 都留着」；
`image_filter.verdict_for` 对没有 GPS / Commons 分类的图也不否决（只降级 `suspect`）。
⇒ 当初「过滤器拦不住」的停用理由，**在补图链路里不成立** —— 那正是 AI 看图要解决的。
两城实测的 58% 错图率来自**没有看图环节**的自动入库链路，不是配图库本身不可用。

### 改了什么

| 文件 | 改动 |

无图 +2 · 缺 `updatedAt` +2 · `updatedAt` 天数/30（封顶 +4）· `popularity`/25（封顶 +2）。

★ 名额分配：**未结发现的点位最多占本轮一半**（`cap = max(1, n//2)`）。
不设这个上限，一座城攒够 6 条未结发现就会永远原地打转、新点位一个都查不到。

**`tools/patrol_findings.py`**（新建，350 行）—— 发现的状态机（**这是 19.10 的核心**）

| 子命令 | 作用 |
|---|---|
| `note --city --poi --field --level --found [--old] [--source] [--note] [--due] [--alt …] [--human]` | 记一条**尚未解决的偏差**。同一 `(点位, 字段)` 重复记 ⇒ `seen+1` 合并，不是新增一行 |
| `list [--city] [--state open\|stale\|closed] [--poi]` | 查 |
| `close --city --poi --field --as resolved\|wontfix\|stale [--why]` | 结案 |
| `auto-stale [--city] [--min-seen 2] [--overdue-days 14] [--dry]` | 把「第二轮仍只有 B/C 档」的自动结案 —— **防止 findings 只增不减的关键**；`--alt` 的三轮才收，`--due` 到期后留 14 天 |
| `todo [--limit 10]` | 薄壳转发到 `patrol_report.py todo`（渲染只有一份） |
| `open-index <city>` | 给排班用（`{poi_id: {open, due, arb}}`） |

状态机：`open`（等下一轮）→ `stale`（第二轮仍无官方口径，自动结案）/ `closed`（`resolved` 已修 · `wontfix` 不修）。
`--due` 是「有明确时间点的挂起」（5A 公示期、改造工期）：到期前**既不算待人工也不打扰人**，
到期后进 `PENDING.md` 的 `DUE` 区，**由下一轮直接执行**（19.11）。
`--alt` 是「查到好几种值拿不准」：每个候选带出处，进 `PENDING.md` 的 `ARB` 区，任务是**找权威源比对**。

**`tools/patrol_report.py`**（新建，212 行）—— 两个出口文件的唯一渲染处（19.11）

| 子命令 | 作用 |
|---|---|
| `pending [--limit 40]` | 覆盖重写 `_tmp/patrol/PENDING.md` + 打机读行 `DUE/READY/WAIT/ARB`。**给下一轮巡检消费**：`due` 到期执行、`ready` 直接落地、`wait` 不动、`arb` 去查权威 |
| `todo [--limit 10]` | 覆盖重写**仓库根 `TODO.md`**，末行打印 `HUMAN=n`。只收 `--human` 与 `A 档 seen>=4`（前 2~3 轮在 PENDING 里自动做，4 轮还不行才算卡住） |

**`tools/patrol_sheet.py`**（新建，120 行）—— 已上线图片的核对表

```
python tools/patrol_sheet.py --city chengdu --n 6      # 3×2 网格，320px/格
```
它取的是**每个点位的封面（`coverIndex` 指向的那张）**，与 `fetch_candidates.py sheet`
（列**候选**）是两件事：候选表用于挑对的，核对表用于查已有的挑错了没。
取样口径与 `next` **不同** —— `next` 优先无图点位，核对表只能取**有图**点位
（混成一套会出现「整张表全是无图点位、一格格取图失败」）。

**`audit_history.py --fix-safe [--dry]`**（扩展）—— 全库安全修复，实测 `files=48 changes=103`。

**`fetch_candidates.py grab --poi <ids> [--replace]`**（扩展）—— 原 `grab` 只补**无图**点位，
永远碰不到「有图但图错」的点位。新增 `--poi` 让指定点位（含已有图）也重抓，
`--replace` 让 `apply` 用判 ok 的新图**替换**旧图（默认仍是追加）。
`--replace` 必须配 `--poi`，否则就是清全城图。

### 19.5 证据分档（只有 A 档能改数据）

| 档 | 依据 | 动作 |
|---|---|---|
| **A 强证据** | 政府 / 官方公众号 / 官媒 / 官网明确写：门票价格、开放时间、永久关闭、搬迁、改名 | 允许 `fix` / `retire`；字段不在白名单才 `note --level A` |
| **B 中等** | 多个 OTA / 旅游平台一致，但无官方口径 | **不改**，`note --level B`，**第二轮仍如此 ⇒ `auto-stale` 自动结案** |
| **C 弱 / 冲突** | 单个自媒体，或几个来源互相矛盾 | **不改**，`note --level C --alt …`，同上 |

**来源权威序（19.11，`ARB` 项按这个判，不是多数票）**：

| 序 | 来源 | 能不能当依据 |
|---|---|---|
| 1 | 政府 / 文旅部门公告（gov.cn、文旅部、省市区文旅局、街道办） | **能** |
| 2 | 景区 / 场馆官网、官方公众号、官方微博 | **能** |
| 3 | 官媒（新华社、人民日报、央视、地方党报） | **能** |
| 4 | 携程 / 美团 / 大众点评 / 去哪儿 | 只作参照 |
| 5 | 自媒体、攻略、博客、AI 摘要 | **不作依据** |

★ 1~3 给了明确值 ⇒ 就是它，跟库里不一样也照改（`--source` 填该权威页 URL）。
★ 1~3 之间也打架 ⇒ **一个字都不改**，`--alt` 记一轮，第三轮 `auto-stale` 收。

★ **核实结果与库内一致 ⇒ 什么都不写**（日志一句「已核一致」）。
  为"我查过了"写 findings 会把文件堆成假待办 —— 19.10 的病根之一就是这个。
★ 搜索里没出现该点位 ≠ 它关闭了（可能只是词不合适）⇒ 换一次词再判。
★ 「暂停营业 / 闭馆修缮 / 临时闭园」**一律不 retire** —— 改 `summary` 或加 `tips`，
半年后重开还在，否则坐标与描述全丢、得重录一遍。

### 19.8 铁律（越界比漏检严重）

- 数据只改**白名单字段**（`ticket` / `hours` / `address` / `transport` / `name` / `summary` / `point`）；
  **绝不删点位文件**（除 A 档证据下的 `retire`，且 `retire` 是可逆归档）。
- 不改 `pipeline/seeds/*.py`：巡检改的是 `data/` 侧。同一字段在采编稿里还有一份，
  跑 `run.py seed` 会回退 —— 但那条路径**本来就被禁**（会清空全城 `images`）。
- 不 `git add` / `commit`；不新建 / 删除任务；不删自己。
- 一轮只做 1 城 / 6 个核实点 / 最多 2 个重抓。
- **判不准就只记不动** —— 错改一条比漏查十条贵。

### 19.9 设计取舍（可调整）

1. **内容稽查而非只读**：这是用户明确纠正的方向。字段体检留下当 P0，因为它 2.5 秒且能兜住
   「JSON 坏了」这类硬伤。
2. **A/B/C 三档而不是「搜到什么就改」**：定时任务无人复核，把 B/C 档当 A 档用就是批量灌错数据。
3. **`retire` 可逆而不是删文件**：数据站的条目重建成本高，归档能一键搬回来。
4. **每轮 1 城 6 点**：83 城轮一遍约 3.5 天，单城点位覆盖一轮约 25 天。想更快就调 `--n`，
   但每点两次搜索 + 一张图，`--n` 太大人做不完、任务会超时。
5. **接进同一条每小时任务而不是再加一条**：用户对任务数量敏感（此前明确「一个就够了吧」）。

### 19.10 第二次改口径：这个任务不该产出「待人工复核」（2026-11-09 01:02）

用户原话：**「这个每小时的定时任务有点问题，因为是定时任务，所以不可能一直去盯着的，
好几次跑完，都有需要人工去复核的」**。

跑完 5 轮成都（`ROUND=5`，ledger 记 `checked=30 fixed=24 newFound=16`），findings 从 0 堆到 32 条。
问题不在「AI 报得多」，而在三处机制缺陷 —— 每一处都在批量制造人肉待办：

| 根因 | 实跑证据 | 为什么必然发生 |
|---|---|---|
| **① A 档证据够了，但字段不在白名单** | 望江楼 `district` 记锦江区、地址却是武侯区（文旅成都官网）；洛带 `tips` 说「博客楼需门票」而多个来源说免费；望江楼/永陵封面是文物特写（第 4 张才是园景）；自然博物馆 `_geocodeTitle` 是隔壁酒店大堂 | 判断清楚、证据硬，纯粹因为工具没这个字段，被推给人 |
| **② B/C 档永远等不到答案，但每轮当新问题报** | 门牌 23/73/136 号、41/43 号、52/62-63 号；人均 15/32/49 元；开门 08:00 vs 10:30 | 这类**信息本身没有唯一答案**（不同门店/年份/平台）。第二轮再查还是那几个 OTA 页面，`findings` 只增不减 |
| **③ findings 只写不读** | `_risk` 不看 findings ⇒ 自己标的问题永远不回头复查；没有 `resolve`/`dismiss`；同一 `(点位,字段)` 可以报两遍 | 「发现 → 存进 json → 再也不看」。**初版连排班都不读 findings，等于把发现丢进垃圾桶再加一句"待人工"** |

外加一个隐性坑：**`fix` 落完不结案**。`maojiao-huola` 的地址明明当轮改好了，
findings 里还挂着 `open`，于是下一轮又被算进「待人工 3 条」之一。

#### 改法（五件事）

1. **白名单扩容 6 → 10 项**（`district` / `tips` / `coverIndex` / `geocodeTitle`，见 19.4 表）。
   凡是「证据硬、判断唯一、且是非破坏性字符串/整数」的字段，都该自动化 —— 人只处理不可逆取舍。
   `level` 例外：站点 POI 侧**没有这个字段**，加了是空写，等级变化只能进 `summary` 或挂 `--due`。
2. **两轮收敛**：B/C 档第一次 `note`（`seen=1`）、第二次仍无 A 档 ⇒ `auto-stale` **自动结案**，
   从此不报。每轮 P0 跑一次 `patrol_findings.py auto-stale`。
3. **findings 状态机**（`open` / `stale` / `closed`）+ 统一入口 `patrol_findings.py`，
   不再让 AI 手写 json（手写会长出 `field="address/transport"` 这种复合值，`auto_close` 永远对不上）。
4. **`fix` / `retire` 落完自动结案**（`auto_close()`）。不靠 AI 记得再敲一遍 `close` —— 它十次有三次会忘。
5. **`TODO.md` 成为唯一人工出口**：每轮**覆盖重写**（不 append）、去重、上限 10 条，
   只收两类：`--human` 标过的、和 `A 档 seen>=2 却没落地`的（后者说明卡住了，不是判断问题）。
   日志里「待人工」这行只许引用它，不许列细节 —— 两个真源等于零个真源。

排班也跟着改：**未结发现的点位不受「查过就歇 30 天」约束**（`_eligible()`），
且**最多占本轮一半名额** —— 前者治「发现了却永远不复查」，后者治「旧账把新点全挤掉」。

### 19.11 第三次改口径：「等日期」和「拿不准」都不该找人（2026-11-09 01:20）

| bug | 现象 | 原因 |
|---|---|---|
| **选城顺序反了** | 成都连查 **8 轮**（`ROUND=8`），另外 82 城从未被选中 | `ranked.sort()` 升序取 `[0]`，`_days_ago` **最小**的（最近查过的）胜出。注释写的是"最久没查的先"。改成 `-_days_ago` 后立刻切到 `guangzhou (never)` |
| **`pool` 从未排序** | 到期项被「文件名 a 开头」的点位挤掉名额 | `_key()` 定义了但没人调用；`sticky[:cap]` 等于按目录扫描顺序取前 3 个 |

配 `next` 的选点也重排成三档：`urgent`（DUE/ARB）先吃名额（最多一半）→ 旧账 → 新点。
只靠打分混排不行：一条"到期"（+6）打不过"两条普通未结"（5×2=10）。

#### 存量清理：15 条「早就改好了却挂着 open」

第一版 AI 在会话里改完数据后写 `status="fixed"`，迁移脚本没看这个字段，全当 `open` 继承下来，
于是**每轮都被当成待人工报出来** —— 这正是用户抱怨"好几次跑完都要人复核"的直接来源。

逐条比对「库内现值 vs findings.found」后结掉 15 条（`yepopo-boboji` address、`chengdu-red-museum`
address/summary、`shufeng-yayun` address/transport、`wangjianglou-park` hours…），另 1 条
`chengdu-art-museum hours` 是「官方口径与库内一致」也该结。成都 open：**22 → 6**。

剩 6 条：4 条 `district`（望江楼→武侯、永陵→金牛、五凤溪→金堂、望平街→成华，现值为旧区属，
白名单新加 `district` 后可直接改），2 条 `image`（80/130 张候选里确实没有该点位实景）。

### 20.2 口径：封面是"认得出的地标"，不是"城市天际线"

| 规则 | 为什么 |
|---|---|
| 查询词只用该城 `popularity` 最高的 6 个**点位名**（故宫 / 大雁塔 / 西湖） | 点位名在 Commons 有真图与人工分类；城市名没有 —— 搜"兰州 skyline"只会返回别处的摩天楼 |
| **只收 Wikimedia** | 图库无法验证地理：看图也只看得出"是个城市"，看不出是**哪座**城。这是原理性的，不是抽样结论 |
| 地标要过**本城 bbox + 距市中心 50km** | 西安库里「华山」popularity 排第 4，但它属渭南；那条记录坐标还错的（见 20.4） |
| 排掉演出/剧场类名字 | `《长恨歌》实景演出` 拿去搜 Commons，只会返回舞台灯 |
| 判 ok 必须写**中文 alt** | Commons 文件名（`Blubb (10595970686).jpg`）不算描述，a11y 与 SEO 全落空 |
| 城市封面**允许**与本城点位同图 | 「钟楼」既是点位、也是西安门面 —— 与「同城点位之间一图不挂两处」是两件事（后者是张冠李戴） |

## 二十二、封面复核：从「一次性清洗」到「每小时看一遍」（2026-11-14）

### 22.1 为什么要多这一层

用户的原话是「省市区介绍的图片，你可以挑重点景区的图片」，紧接着问「区现在是没有详情介绍的吗」。
区这一层查下来**确实没有**（`data/` 下没有区级目录，区只有 `subcodes/name/center/poiCount`，
点区只放大不开卡），用户随后确认**不做区卡**，只统一省/市取图。

于是真正的活变成了"把省市封面**持续**看住"。而 `cover_sheet.audit_covers` 做不到这件事 ——
它回答的是「**还没审过的**长什么样」，账本 `state=ok` 的一律跳过（那是为一次性清洗设计的）。
封面上线之后会**慢慢变得不对**，四种坏法它一个都看不见：

| 坏法 | 怎么发生的 | 为什么静态审查看不出来 |
|---|---|---|
| **依据消失** | 封面 `query` 记的是「华山」，那个点位后来被 `retire` / 改名 | 图还在、还能显示，只是不再代表本辖区任何东西 |
| **重点景区换人** | 新收录一个爆火点位，封面还是三年前那三个 | 那三张本身没错，只是不再是"门面" |
| **城市名兜底通道** | 当年地标图不够，用了「<城市> skyline」补位 | 账本 `state` 是 ok（人看过），但看过 ≠ 该留 |
| **图挂掉** | Wikimedia 改名 / 删除 / 版权下架 | 只有真发一次请求才知道 |

2026-11-14 一跑体检就抓出来 **78 个单位有缺陷**，其中 14 城是**整套 Pexels 天际线**
（`query` 写成「广州 China city skyline」、`alt` 是英文）—— 而账本上它们全是 `ok`。

### 22.2 工具：`tools/cover_review.py`

```
next  [--kind city|province|both] [--n 6]          体检清单（机读行，巡检照着做）
sheet --picks city:beijing,province:610000         看**已上线**的（每单位 3 张连排）
cands --picks city:a,city:b [--per 6] [--depth 2]  看**候选**（多城合表，每地标一张轮转）
keep  --picks city:beijing,...                     看完记 reviewedAt（**不动 `at`**）
urls  [--n 12]                                      HEAD 抽查封面 URL（轮转）
```

判据与权重（分数只用来**排队**，不是结论）：

| 项 | 分 | 判据 |
|---|---|---|
| 账本 `need` | 10 | 判过要换、还没换 |
| **图源不是 Wikimedia** | 4/张 | `credit.source != wikimedia` —— 红线 |
| 张数不足 | 3 | `heroImages` < 3 |
| **依据消失** | 3/张 | `query` 经 `core_name()` 后在辖区点位里找不到 |
| 城市名兜底通道 | 2/张 | `query` == 单位名 / 含 skyline |
| alt 无中文 | 2/张 | 一个汉字都没有（Commons 文件名） |
| 前 3 重点景区零覆盖 | 2 | 只在 ≥2 张时判（1 张时必然成立，是噪音） |
| 久未复核 | 1 | `reviewedAt` 缺失或 > 90 天（缺失时拿 `at` 兜底） |

★ **省和市必须交错输出**（`next` 里按 kind 分组后交替，不按分数全局排）：34 省全是
"只有 1 张"(3 分)，全局排序会让省份长期压在城市的 2 分项前面，城市那条线几周不动。

★ **`keep` 只写 `reviewedAt`，绝不碰 `at`**：`at` 是"这份数据最后一次改动"，看完说"还行"
没改任何东西，把它推到今天会让"多久没改过"失真。

★ **`cands` 必须顺手写 `manifest.json`**：`apply` 只认 `_tmp/city-cover/<slug>/manifest.json`。
写**全部候选**而不是只写上表那 `per` 张 —— 判定时常常要从"没上表的第 3 张"里补一个。

| 哈尔滨 | 圣索菲亚教堂 / 中央大街 / 冰雪大世界 | 阳朔 | 遇龙河（2 张） |

### 22.4 四个「认错」事故（这就是必须核对 `poi` 的理由）

粗看缩略图会认错，而 `alt` 是按"我以为我看到的东西"写的 —— 写错就是**伪造描述**：

| 我以为 | 实际（看 `poi` 才知道） |
|---|---|
| 广州 #15 是五羊石像 | **陈家祠**第 2 张（与 #14 重复） |
| 南京 #36 中山陵 / #35 明孝陵 | **都是南京博物院** |
| 镇江 #18 金山寺 | **焦山**万佛塔 |
| 乌鲁木齐 #31 是城市天际线 | alt 里写着「**广东深圳福田区**」—— 那是深圳的图 |

⇒ 规则：**写 `alt` 前先查这个 `idx` 的 `poi`**；认不出就是不要。

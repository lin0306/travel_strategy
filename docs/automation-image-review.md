# 每日定时任务 · 图片重抓 + 审查备料

> **一句话**：定时任务**只备料**（重抓图片 + 拼好对照表），**审查在会话里做**（看图判定 → 回写 → build）。
> 任务名「行迹 · 每日图片重抓 + 审查备料」· 每天 00:00 · 每次滚动 2 城 · 进度以 `status` 为准（已审 2/83）。

**读这份文档的人**：下一个接手定时任务的模型 / 半年后的自己 / 想把这件事自动化得更彻底的你。
**改任务之前**：先读第 7 节（换执行者 checklist）。**出问题**：直接跳第 8 节（排错速查）。

---

## 一、为什么有这个任务

站里有 **83 城 / 4820 个 POI**，图片全部来自采集流水线。旧管线有两个硬伤：

| 硬伤 | 表现 | 后果 |
|---|---|---|
| 固定收 3 张（`max_keep=3`） | 全库 89% 的点位"恰好 3 张"（2026-10-28 实测，修复前 4297/4808） | 能搜到 8 张也只留 3 张；不够 3 张就拿"品类氛围图"垫 |
| 零内容校验 | Wikimedia 按**文字**相关度返回，前 3 条直接入库 | 「西安地铁青龙寺站」标题里同时有"青龙寺""西安"⇒ 排在第一位 ⇒ 进了详情页 |

2026-10-29 起，采集侧已修（上限 6 张 / 入库前过相关性过滤 / 同城 URL 去重 / 配图库停用），
但**其余城市仍是旧数据**，必须逐城重抓 + 逐城过审查。这就是这个任务存在的原因。

实测两城的错误率（我逐格看图判的）：

| 城市 | 封面数 | 判为错图 | 典型错法 |
|---|---|---|---|
| 西安 | 57 | **30（53%）** | 北京回民小学挂在回民街 · 绍兴咸亨挂 5 家饭馆 · 阳朔航拍挂 3 处 · 马路照挂青龙寺 |
| 长春 | 57 | **33（58%）** | 星球大战 Chewbacca 挂长影老摄影棚 · 上海的古塔挂农安辽塔 · 新西兰溶洞挂吊水壶 |

> ★ 错图里**标题全都是对的**（"Qinglong Temple, Xi'an" 就是那张马路照的文件名）。
> 元数据过滤只能拦"说得明白的错"（地铁站 / 地图 / 坐标十万八千里），
> **"标题对、画面是别的东西"只有看图能发现** —— 这是整个流程必须有人在回路里的唯一原因。

## 二、角色分工（这套流程唯一重要的一件事）

| | 定时任务（独立进程） | 会话里（能读图的执行者） |
|---|---|---|
| **做** | `next` 选城 → `images --force` 重抓 → 再跑一趟补 `_noImage` → `sheet` 出对照表 → 记账 `refetched` → 写日报 | 读对照表逐格看图 → 写 `verdicts-covers.jsonl` → `apply` 回写 → 记账 `reviewed` → `build` |
| **不做** | **不 build**（未过审的图不许进产物）· **不 apply**（没有判定依据 = 瞎删）· **不 commit**（未审数据不进版本库）· 不按标题猜对错 | 不改采集代码（那是另一件事，另开一轮） |

**为什么"不 build"是硬约束**：审查前的图是**未经审视的新图**。让它进索引/产物，
等于把未过审的数据当成品发布 —— 而 build 之后前端缓存、产物哈希、部署都会跟着变，
错图就从"待审"变成"已上线"。

**为什么也不许 commit**：2026-10-31 00:30 那次任务跑完自己 `git commit`（message「城市信息补充」），
把 changsha / chengde 的 **113 个未审文件**提交进了版本库 —— 等于绕过审查这道关（数据会被别人 pull 走、
被部署链路读到）。build 与 commit 都是"让数据出门"，两者都要等审查完。

**为什么审查不能自动化（至少现在不能）**：
- 没有视觉模型 key，也没有可靠的"图对不对"的文本替代品 —— 文字判据已被证伪（见上表）。
- 按 alt/标题过滤会漏掉一半（青龙寺那张就是反例），按"图源"过滤会误杀（Wikimedia 本身是好源）。

⇒ 所以分工是：**机器做耗时的（下载/重抓/拼图），人做判断的（看一眼）**。

## 四、每次执行具体做什么

```
next --count 2
   ↓  拿到 2 个 slug（POI 少的先做，跳过账本里 refetched 过的）
images <city> --force          ← 强制重算，否则旧数据"恰好 3 张"永远不会变
   ↓
images <city>                  ← 不带 force：只重试带 `_noImage` 的点位（网络抖动误标）
   ↓
sheet <city> --covers --refresh ← 下缩略图 + 拼 4×5 对照表 + 写清单
   ↓
账本 refetched += slug · 日报追加
```

### 为什么是这两趟（顺序不能换）

| 趟 | 命令 | 为什么 |
|---|---|---|
| 1 | `images --force` | 旧数据 89% 是"恰好 3 张"。不带 force 会走 `have and not force → skip`，永远修不到 |
| 2 | `images`（不带） | 第一趟里 Wikimedia 偶发断连时 `search_wikimedia` **静默返回空**，点位被标 `_noImage`。西安城墙第一趟被误标"没图"、重试拿到 6 张真图 ⇒ 必须有第二趟 |

### 为什么对照组是"封面"而不是全量

一个点位最多 6 张图，全量审 4820×5 ≈ 2.4 万张，看图成本不可承受。
**封面（`coverIndex=0`）是详情页首图、也是卡片图**，错得最显眼、最该先修。
非封面图的错留到以后（账本 `image-rebuild.json` 的 `_note` 已写明这个边界：
`reviewed = 封面已过审查；非封面图尚未逐张看` —— 不要假装全审过了）。

```bash

E:/BASIC/python/python.exe tools/review_images.py apply <city>

# 5. ★ 删图后**再出一轮新封面**，再审一遍（见下）
E:/BASIC/python/python.exe tools/review_images.py sheet <city> --covers --refresh

# 6. 补被删空的点位（不带 --force，不会碰已审过的封面）
E:/BASIC/python/python.exe pipeline/run.py images <city>

# 7. 全量 build（★ 单城 build 会把 cities.index.json 覆盖成只剩一城）
E:/BASIC/python/python.exe pipeline/run.py build

# 8. 记录 + 自检
E:/BASIC/python/python.exe tools/check_app.py     # 期望 RESULT: ALL_CLEAN
```

### 5.1 三个"审查白做"的坑（都已写进工具，但你要知道为什么）

| 坑 | 现象 | 现在的做法 |
|---|---|---|
| 序号与格子**错位** | 读图的一方把 `#5` 判成 `#1` ⇒ 删错图 | 序号**烧进每格左上角**白底方框（不只在格下方写小字） |
| 删图后**新封面没审** | 删掉封面后 `coverIndex=0` 指向原来的第 2 张（没审过） | 删完**必须再出一轮 sheet 再审**。长春一审删 33 张，二审又从新封面里判出 30 张错的 |
| 判定**按位置猜** | 表格最后一列/行不满时，位置推断必错 | 一律按格内 `#序号` 作答；空白格写"空白" |

### 5.2 图下不来怎么办

`[下载失败]` 的格子**不补跑**（wsrv.nl 偶发超时）。按 Commons 文件页判定，
并在 `note` 里标「图未下成，按文件页判定，待复核」—— **不许默默放过**。
判定会按 URL 进全局缓存 `_tmp/review/verdicts-cache.jsonl`，**reject 过的图永远记住**（下轮重抓不会回来）。

## 七、换执行者 / 换模型时怎么改（checklist）

### 7.1 硬约束（改了就会出事）

1. **prompt 必须自包含**。定时任务是**独立进程**，看不到任何会话上下文 ——
   背景、命令、禁止项都要写进 prompt 本身（本文档第 3.1 节就是全文）。
2. **python 写全路径** `E:/BASIC/python/python.exe`。裸 `python` 在这台机器上可能命中另一个解释器
   （依赖装在 `E:/BASIC/python`）。同理 git 用 PortableGit 的路径且**探测不写死**。
3. **保留"只备料"的分界**。任何"顺手 build 一下""顺手 apply 一下"的改动都要否掉：
   没有判定依据的 apply = 随机删图，且**零报错**。

5. **不要把审查交给没有视觉能力的执行者**。做不到就退回"只备料 + 人工审"，
   千万不要退化成"按 alt 关键词判" —— 那比不审更危险（看起来审过了）。

## 十一、与设计文档的关系

`plans/06-data-maintenance.md` 的 6.1 / 6.2 写的是**早期设想**：GitHub Actions 每月跑
`check-images.yml`、HEAD 扫全量 URL、404 用 `query` 重搜后开 PR。那份设计解决的是**死链**（404），
解决不了**文不对题**（图活着、但是别的地方）。

实际落地的是本文这套：**本地定时任务备料 + 会话看图审查**。两者的关系：

| | 早期设想（06 文档） | 现在落地（本文） |
|---|---|---|
| 触发 | GitHub Actions 每月 1 号 | 本地定时任务每天 00:00 |
| 判据 | HTTP 状态码（404） | **看图**（内容对不对） |
| 产出 | 自动 PR | 人工判定 → `apply` → build |
| 适用 | 图挂了 | 图错了（更常见、更隐蔽） |

`query` 字段（"这张图想表达什么"）两边都依赖 —— 它是重搜的唯一依据，`images.py` 必须继续写。

## 十二、存量图全量清洗（2026-10-31 新增）

前十一节讲的是「**重抓的新图**怎么审」。这一节讲另一件事：**库里躺着的历史图**。

### 12.1 为什么必须单独做一次

`USE_STOCK_SOURCES=False` 是 10-29 才关的，**存量从来没人清过**。10-31 全库扫一遍
（4820 个点位 / 13674 张图），三个硬事实：

| 类别 | 张数 | 占比 | 是什么 |
|---|---|---|---|
| `ok` | 5250 | 38% | 元数据对得上 |
| `stock` | 6602 | **48%** | Pexels / Unsplash **主题图库** |
| `reject` | 335 | 2.4% | 命中否决词（飞机、地铁站壁画、澳门招牌） |
| `dup` | 672 | 4.9% | 同一 URL 挂 ≥3 个点位 |
| `suspect` | 815 | 6.0% | 标题、坐标都对不上点位名 |

`stock` 那 48% 是最刺眼的：`pexels-photo-32686464.jpeg`（一张美食氛围图）挂在
**298 个餐饮点位**上、横跨 **48 座城**；2127 个点位（45%）的图**全部**是这种。
搜「农安辽塔」给你上海的古塔、搜「瓷泥煨鸡」给你尼泊尔的手抓饭 —— 不是相关度低，
是**根本没有对应关系**（图库按关键词返回配图，没有地点概念）。

### 12.2 分级：什么能自动删，什么只能标记

`tools/clean_images.py` 的 `AUTO_RULES` **只允许 `("stock", "reject")`**。

★★ `dup` / `suspect` **不许自动删**。原因不是保守，是它们里有大量**合理**的图：
Wikimedia 的「景区大图挂景区内几个子点位」会同时命中 dup；「合肥三国新城遗址公园.jpg」
标题明明对得上，却因为 `core_name` 取不到而落进 suspect。自动删它们 = 把有真图的点位
一起清空。这两类只能交给看图。

这条线由护栏 **AW** 守着（`check_app.py`），改 `AUTO_RULES` 会直接红。

### 12.3 操作顺序（别搞反）

```
① clean_images.py scan                     全库只读，出 _tmp/review/clean-report.json
② clean_images.py apply --rules stock,reject --dry    看数字对不对
③ clean_images.py apply --rules stock,reject          执行
④ run.py images <city> --force             重抓补图（分批，见 12.4）
⑤ review_images.py sheet <city>            出对照表
⑥ 看图判定 → verdicts-<scope>.jsonl → apply
⑦ run.py build                             全量（防 cities.index.json 被单城覆盖）
```

★ ④ 必须在 ③ 之后：先删干净，重抓才是白纸重画。反过来会把刚删的图又抓回来。

### 12.4 重抓能补回多少（实测，别抱不切实际的期待）

| 城 | 重抓前 | 重抓后 | scenic 无图率 |
|---|---|---|---|
| luoyang（知名） | 45 张 / 38 无图 | **98 张 / 32 无图** | 77% → **35%** |
| jingdezhen（冷门） | 36 张 / 44 无图 | 50 张 / 47 无图 | 仍 77% |

★ **重抓救得回景点，救不回餐饮**。洛阳 scenic 类翻倍；但两城的 food（67%）、
hotspot（70%）、culture（100%）都抓不到 ——「瓷泥煨鸡」「乐平赣剧」这类东西
Wikimedia 本来就没有照片。**占位卡是终态，不是失败**。

★ `--force` 会让原本有图、但新过滤器不认的点位**变空**（jingdezhen 无图数 44→47）。
这是"诚实的退化"：原来那张本来就不对。别因为数字变差就回滚。

★ 每城跑**两趟**：`--force` 重算 → 不带 force 再跑一次（只重试 `_noImage` 的点位）。
只跑一趟会漏掉一批偶发断连的点位（长沙 8 个、承德 6 个都是第二趟捞回来的）。

### 12.5 已知坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 重抓过了还剩一堆 Pexels 图 | `step4_images` 的 `if have and not force` 会**跳过已有图的点位** | 必须 `--force`，否则旧图原样留着 |
| `apply` 后点位字段烂掉 | 少了 `coverIndex = 0` / `_noImage` / `updatedAt` | 护栏 AW 会红，别删那三行 |
| 删完 build 报一堆 WARN | `_noImage` 点位是 WARN 不是 ERROR | 正常，前端走占位卡 |
| 单城 build 后城市索引只剩一城 | `run.py build <city>` 会覆盖 `cities.index.json` | 一律跑全量 `run.py build` |

## 十三、审查工具自身的六个坑（2026-10-31 实测）

这一节记的不是数据错，是**审查工具自己会静默失效**的六条。它们的共同点：
出错时**没有报错**，只是"少看了几张"或"删错了图"。

### 13.1 UA 不带 URL → 图取不回来（429 / 403）

`review_images.py` 原来的 UA 是 `travel-strategy-image-review/1.0 (local; low-frequency)`。
敦煌实测同一张图（玉门关信息牌）：

| UA | 结果 |
|---|---|
| `…(local; low-frequency)` | **HTTP 429** |
| 不带 UA | **HTTP 403** |
| `…(https://www.mediawiki.org/wiki/API:Etiquette; local review tool)` | **200** |

后果：敦煌 56 格里 7 格（5 张沈尹默手稿 + 2 张玉门关说明牌）全部取不到，
对照表上只印「[下载失败]」，**而这座城仍然会被记进 `reviewed`** —— 那 7 张从没被人眼看过。

★★ 判据已进护栏 **AW**：`direct_thumb()` 必须存在 + 失败必须打印「取不到图」+ 格数与清单。
反证 `_tmp/revert_probe_fetch.py` **2/2 全红**。

### 13.2 镜像失败 ≠ 没图，必须再试直连

`wsrv.nl` 对一部分历史档案照（`Bundesarchiv` 1938 年德国西藏探险队、`in Tomba` 版画）
是**稳定失败**，不是抖动，重试镜像等于永远看不到。现在的取图顺序：

```
wsrv.nl ×3  →  upload.wikimedia.org 官方缩略图  →  原图 ×2
```

★ 还有一档必须留**原图**：`Gaoligongshan IMGP5778.jpeg`（腾冲）三种宽度的官方缩略图
全部 **400**，只有原图 200。审图只要看得清，体积大点无所谓。

### 13.3 `apply` 跑第二次会按旧序号删到别的图

`manifest-*.json` 里的 `imageIndex` 是**出表那一刻**的序号。删完图再跑一次 `apply`，
序号已经重排 ⇒ 按旧序号删 = 删到别的图上，**零报错**。

现在 `apply` 会先比对该文件实际张数与 manifest 记的张数，不一致就跳过并提示
「表格已过期，先 `sheet --refresh` 再看」。

★★ 这条判据第一版**自己也会静默跳过**：`expect` 是按"**带判定的行**"算最大序号 +1，
只判了某点位最后一张（乐山 #6 微缩模型）时 `expect` 就偏小，5 个点位被当成「表格已过期」
整批不回写，只印了一行跳过。现在按 `full_of`（该文件**全部** manifest 行）算快照，
并加第二条判据：序号上的 **URL 必须与快照一致**（图还在但顺序被洗过也要拦）。

### 13.4 `apply` 只报"改了几个 POI" ⇒ 删错看不出来

福州实测：我手写判据 `{92..99}` 想删万福寺，**实际 #92/#93 是华林寺的真图**
（万福寺是 #94-#99）。`apply` 只回一句「改动 16 个 POI」，没提华林寺，
等回头核对才发现删错两张。

现在 `apply` 逐条印出被删图的 alt：

```
     - 又见敦煌: 沈尹默《匏瓜庵谈艺录》手稿释文2.jpg
     - 玉门关: Info Yumenguan.JPG
```

★★ **序号必须对着 manifest 核**，别凭"我记得那几张在 92-99"。判据里写的数字
是人眼在对照表上读出来的，读错一格就跨点位删图。

### 13.5 同一张图被判 ok 又被判 reject ⇒ 后写的赢，好图被删

`verdicts-cache.jsonl` 按 **URL** 去重，`load_cache()` 后写的覆盖先写的。
一张图在一个点位是正主、在另一个点位是错图时，两条判定会同时留在文件里，
**最终生效的是最后那行**。

西安实测：`翠华山 (3487673551).jpg` 先有 `ok`（10-16 封面审），后有一条 `reject`
（别的点位/别的城判的），apply 时 `reject` 赢 ⇒ 翠华山唯一一张图被删成空点位，
而这条删除**不在我这次的 verdicts 里**，是缓存带出来的。

```bash
grep -n "<URL 关键词>" _tmp/review/verdicts-cache.jsonl     # 先看有没有自相矛盾
```

救法：给该 URL **补一条 `ok`**（后写覆盖），再从 git HEAD 把 image 对象放回去（见 13.6）。
★ 更根本的做法是让缓存按 `(城市, POI, URL)` 记，但那样"这图永远是错的"就退化成本城有效 ——
现阶段宁可补 ok，也不要让缓存带出无声删除。

### 13.6 误删怎么救
```bash
# 1) 从 git HEAD 取回该点位的完整 image 对象（含 credit，不许自己编）
git show HEAD:data/cities/<省>/<市>/pois/<类>/<slug>.json
# 2) 只补回被误删的那几条（按 URL 比对），顺便 coverIndex=0、清 _noImage、写 updatedAt
# 3) 从 _tmp/review/verdicts-cache.jsonl 里**撤掉那几条 reject**
#    —— 否则以后每次重抓都会被永久跳过
```

★ HEAD 不一定有你删的那张（可能是更早的快照，福州 `picture33` 就只找回 1 张）。
找不回就接受少一张，**不要伪造 credit**（红线：图片必带 credit）。

## 十四、无图点位自动补图任务（2026-11-01 新增，**会自删**）

前十三节都有一个人工环节：定时任务备料、会话里看图判定。这一节是**把这个回路也自动化**——
定时任务自己抓、自己看、自己写回，全库做完**自己把自己删掉**。

| 项 | 值 |
|---|---|
| 名称 | 行迹 · 无图点位自动补图（做完自删） |
| id | `58792aa5-7893-4f2a-8081-dbf2d828697a` |
| 频率 | `FREQ=HOURLY;INTERVAL=1`（每小时一轮） |
| 每轮工作量 | 1 座城（本轮 <25 分钟则再做第 2 座） |
| 收尾 | `next` 返回 `ALL_DONE` → 全量 build + `check_app` → **`automation_update mode=delete` 删自己** |
| 账本 | `.workbuddy/memory/image-rebuild.json` 的 `refilled` / `attempts` / `skipped` |

### 14.1 和第三节任务的分工（**两个任务不能同时开**）

| | 第三节「每日重抓 + 备料」 | 本节「无图点位自动补图」 |
|---|---|---|
| 解决什么 | **已入库的图错了**（文不对题） | **点位根本没有图** |
| 谁判定 | 会话里（人/模型看图） | 定时任务自己（同样看图） |
| 动哪个数据 | `images --force` 重抓覆盖 | 只往空的 `images` 里加 |
| 现在状态 | **PAUSED**（2026-11-01 停） | ACTIVE |

★★ **为什么必须停掉第三节那个**：它每晚 `images --force` 两座城，而账本 `reviewed=83`（全库已审完）
⇒ 重抓 = **把已审过的图换成未审的新图**，等于自己撤销审查成果；并且和补图任务抢同一个限流接口（429 会被静默吞成"没图"）。
要恢复它，先确认补图任务已经自删（`refill_queue.py status` 显示待补 0 城）。

### 14.2 三个工具（都是这轮新写/搬出来的）

| 工具 | 干什么 | 为什么必须单独存在 |
|---|---|---|
| `tools/refill_queue.py` | `next` / `done` / `fail` / `status` | "下一座做谁、是不是全做完了"交给脚本算。写在 prompt 里让模型自己数，每天数字都不一样 ⇒ 永远不知道该收尾 |
| `tools/remap_candidates.py` | 按序号改写候选图归属（`{"8":"大同关帝庙"}`） | `grab` 按**坐标最近**分配，图对但点位错。不改归属就只能整批 reject（大同因此白扔 30 张） |
| `tools/refill_one_poi.py` | 给单点位补图（指定 Commons 文件名） | 整城流程会覆盖 `candidates.jsonl`，序号一错就把图写到别的点位且零报错 |

### 14.3 自删机制（这套东西最容易做错的地方）

```
next → ALL_DONE
  ├─ refill_queue.py status      确认待补 0 城（不是凭日志感觉）
  ├─ run.py build                全量，不许 build <city>（会覆盖 cities.index.json）
  ├─ check_app.py                期望 ALL_CLEAN
  ├─ automation_update mode=list → 按**名字**找 id（不写死 id）
  └─ automation_update mode=delete id=<list 返回的那个>
```

★ **按名字找、不按记下来的 id**：id 是人建任务那一刻的产物，写进 prompt 就等于埋一个会过期的常量。
★ **删不掉要有兜底**：`automation_update` 不可用时写 `.workbuddy/memory/REFILL_DONE.txt` 提示手动删，
**不许**当作已删（否则它每小时空转、还会在日志里反复写"已完成"）。
★ 删之前必须清 `_tmp/fetch/.running`，否则残留锁会让"下一轮"永远 BUSY。

### 14.4 防重入（为什么要那把锁）

一轮可能超过 1 小时（大城 116 张候选 / 6 页对照表）。若上一轮没跑完、下一轮又起来，
两个进程同时打 Wikimedia ⇒ **429**，而 `grab` 的 429 会被静默当成"图源没有这张图"（第一批踩过，整城判成"没料"）。

```bash
f=_tmp/fetch/.running
if [ -f "$f" ] && [ $(( $(date +%s) - $(stat -c %Y "$f") )) -lt 2700 ]; then echo BUSY; else touch "$f"; echo GO; fi
```
- `< 2700` 秒（45 分钟）= 认为上一轮还活着 ⇒ 本轮直接退出，什么都不做
- 超过 45 分钟视为**陈旧锁**（进程已崩）⇒ 抢过来继续
- 已实测三态：首次 `GO` / 立即再跑 `BUSY` / 伪造 50 分钟前 `GO`
- 每轮结束（成功或失败）都要 `rm -f _tmp/fetch/.running`

### 14.5 prompt 原文

见任务本身（`automation_update mode=view`）。改 prompt 的红线，与第七节一致，另加三条：

1. **不许降级成文字判定**。没有视觉能力就停下写日志——"看起来审过了"比不审更危险。
2. **抓 0 张要 `fail` 记账，不许静默跳过**。连 2 次才放弃，且放弃要进 `skipped` 留痕。
3. **判图前必须先打印 idx → poi 区间**。凭记忆切段必错一格（平遥把凤仪门当二郎庙，6 张院落照写进了城门点位）。

### 14.6 三个关键问题（2026-11-01 实测，不是推测）

**① 上一轮没跑完，下一轮会不会并发？——不会，调度器自己串行。**

`LocalAutomationScheduler` 的日志与代码里写着：

```
skip same-source automation <id> (<name>): sourceKey=a8163223 already active (serialized, max 1); keep due for next tick
started tickMs=30000 activeTickMs=5000 missedWindowMs=86400000 concurrency=3
```

| 参数 | 含义 |
|---|---|
| `serialized, max 1` | **同一个 sourceKey（= 同一个工作目录）同一时刻只允许 1 个 run**。上一轮还活着，本轮到期的那次会被跳过并标记 `keep due`，等上一轮结束立刻补跑 |
| `concurrency=3` | 全局最多 3 个 run 同时跑，但那是**不同工作目录**之间的事 |
| `tickMs=30000 / activeTickMs=5000` | 调度器 30 秒扫一次，有活跃任务时 5 秒扫一次 ⇒ 上一轮一结束，积压的那次马上派发 |
| `jitterMs` | 派发时加 0–25 秒随机延迟，避免同一秒齐发 |

本地化文案里还有 `alreadyRunning: "This scheduled task is already running. Please try again later."`
和 `concurrencyLimit`，说明连**手动触发**也会被拒。

⇒ 结论：**不会双开**。一轮拖到 2 小时也不会堆出两个进程，只会把后面的 occurrence 顺延。
`_tmp/fetch/.running` 那把锁因此是**第二道保险**（防的是"后台 grab 子进程残留、上一轮已被判结束"这类缝隙），
成本接近零，留着。★ 但 BUSY 分支**绝不能删锁**——锁不是你的，删了才是真双开。

**② 定时任务进程有没有读图能力？——有，是真的看图。**

探测任务（16:47 一次性）对 `_tmp/fetch/datong/sheet-cand-00.png` 的描述：

> `#0`：三重檐歇山顶楼阁，灰筒瓦（脊上带小兽），朱红廊柱与红色板壁，两层檐下各悬一块横匾；
> 坐在灰色砖石城台基座上，基座正中开大红门洞……左侧背景还有一座双尖塔的西式教堂立面。
> `#8`/`#9`：单层殿宇，灰瓦硬山顶 + 朱红廊柱 + 木格门窗，檐下一方横匾。

这层细节（檐数、屋顶形制、瓦色、基座类型、背景教堂）**不可能从文件名或 prompt 里推出来**
⇒ 「会话里看图判定」那套流程搬到定时任务里成立，不需要人在回路。

**③ 自删可不可行？——可行，但会把自己这轮踢掉，看着像失败。**

两次实测：

| 任务类型 | 触发 | 结局 | 记录是否消失 |
|---|---|---|---|
| 一次性（once） | 16:47 | 64 秒后 `[CANCELLED] unknown_interrupted`、`success=false` | **消失了** |
| 重复（DAILY 定时） | 16:52 | 13 秒后 `success=false` | **消失了** |

原因：`automation_update mode=delete` 删任务时会**顺带取消正在跑的那轮会话**（`AbortError: This operation was aborted`），
所以 run 的历史记录恒为失败。**这是正常现象**，不是删失败。

⇒ 所以收尾顺序被写死成：`status` 确认 → 全量 `build` → `check_app` → **写日志** → `delete`。
delete 之后不许再做任何事，也不许因为"看起来失败"去重试或恢复任务（否则任务回来了，白删）。

### 15.5 顺手修掉的 bug：跨零点「零请求」误报

`step12_discover` 里本城请求数这么算：

```python
net_requests = max(0, after_req - before_req) if same_period else 0   # ← 老代码
```

账本在**当日第一次请求时惰性归零**，所以跨零点那一次 `before` 是昨天累计值、`after` 是今天从 0 起算的值。
老代码直接判 0 ⇒ 外层 `round_net == 0` 误报「本轮零请求」并停止循环。
实测 11-01 21:26 那轮：真发 **72 次请求**、候选 212→432，日志却写「零请求」
⇒ 定时任务若按这行日志判断「有没有干活」，会得出完全相反的结论。

改为跨周期时取 `after_req`（本轮从 0 起算的真实值）。**验证**：修复后全缓存重跑同一城，
正确打印「本城全命中缓存，0 次请求 ⇒ 不重写」且**文件 md5 与 mtime 均未变**（不重写判据仍有效）。

## 十六、任务整合与「不限量 + 两轮看图」（2026-11-01 晚）

### 16.1 任务从三条并成两条

主人原话：「定时任务整理一下，一个是每天定时去抓新的城市的数据，每天一座城，不抓多了」。
「候选入库」和「点位拓取」本来就是**一个业务闭环的两步**，拆成两条要记住先后关系，合并成一条：

| 现在 | 频率 | 做什么 | 会自删 |
|---|---|---|---|
| **每日抓新城市数据** | 每天 00:00 | A 段入库一座城（消费存量候选）→ B 段拓取一座城（补新料） | 否 |
| **无图点位自动补图** | 每小时 | 1 座城的无图点位补图（两轮看图） | 是 |

★ **A 在 B 前**的理由：入库是"变现"、拓取是"囤料"。先变现，B 段就算因配额失败，成果也已落袋。
★ A、B 是**两个不同的城**，各用各的队列脚本判定（`intake_queue.py` / `discover_queue.py`）。

### 16.2 为什么"放开候选数量"不是因为命中率会变高

用 6 城已判的 565 张候选做了统计：

| 候选数 | 点位数 | 判 ok |
|---|---|---|
| 满额（11~12 张） | 25 | 42/298 = **14%** |
| 未满额 | 70 | 72/267 = **27%** |

**满额点位的命中率只有未满的一半。** 因为能拿满 12 张的恰恰是「戏曲演出、连锁小吃、同名异地」
这类关键词一搜吐一堆的；真正对的景点（云台观、太白楼）通常只有 3~7 张候选。
另外 geo 通道按距离排序，被截掉的是远的那些，本来就更不相关。

那为什么还要放开？因为**截断发生在 grab 里** —— 第 13 张之后**永远没机会被看到**，
而"这张到底对不对"只有看图的人能定。这是**流程问题**，不是命中率问题。

| 参数 | 旧 | 新 | 说明 |
|---|---|---|---|
| `MAX_CAND` | 12 | **60** | 单点位候选上限 |
| geo `limit` | 16 | **30** | geosearch 是**一个请求**，多要不是多花钱 |
| `specific < N` 才跑关键词 | 3 | **8** | 实体通道最多给 4 张，`<3` 等于"有维基条目就别搜关键词"，而条目主图常是徽标/老照片 |
| 关键词 quota | 3 | **5** | — |
| `STOP_AFTER` | 5 | **8** | — |

### 16.3 代价由「两轮看图」吸收，不是硬扛

一城候选从 100 涨到 400~900 张。按 20 格/页要 25~45 页，逐页精看不现实。所以拆两轮：

| 轮次 | 命令 | 网格 | 只干什么 |
|---|---|---|---|
| 第一轮 粗筛 | `sheet <city> --dense` | 8×6 = **48 格/页**（160px） | 剔除明显不可能的类别（人像/地图/货架/室内展厅/停车场），**不确定就留** |
| 第二轮 精看 | `sheet <city> --only 1,5,9` | 4×5 = 20 格/页（300px） | 逐格下结论：是不是这个景点/这家店 |

★★ **粗筛不许下"对不对"的结论**：160px 看不清匾额和店招，「这是不是这座庙」只有大图能定。
粗筛只回答"值不值得精看"。反过来只做精看，900 张要 45 页，成本不可控。

实测（凤凰城，4 个点位 39 张）：粗筛一页看完，一眼看出「苗绣」那 10 张全是古城街拍 + 一只猫，
整批该废；而「凤凰古城街区」的 29 张全是沱江吊脚楼，全留。

### 16.4 顺手修掉的两个静默故障

**① PIL 默认字体不含中文**（`_cjk` / `_fit`）

`ImageDraw.text()` 不传 `font` 时用 `load_default()`，它**只有 ASCII 字形**。
所以旧对照表里所有中文（点位名、"已属「XX」"、通道名）一直渲染成「□□□□」——
只是判定时靠 manifest 打印的序号区间对照，没人依赖格内文字，所以从没暴露。
dense 表每格只印点位名，文字一乱等于"这格属于谁"全丢，必须修。

`_fit()` 按**像素宽度**截断（不能用 `text[:9]`）：中文全角 12px、英文半角 6px，
同样 9 个字符宽度差一倍，「慈城名牌年糕(鼓楼店)」会压到隔壁格。

**② 429 被静默吞成"没图"**（`entity_images.hits_429()`）

`_api` 重试 4 次都撞 429 后返回 `None`，对调用方来说与"这个点位确实没图"**一字不差**。
2026-11-01 凤凰城实测：同一坐标单独测返回 10 张，紧接着 4 并发 `grab` 全 0。

后果比"没抓到"严重：`refill_queue` 会记一次 `fail`，连 2 次就进 `skipped` **永久跳过这座城**。

修法：`_api` 每次撞 429 累加 `_HITS_429`，`grab` 取前后差值，在
「空点位 ≥90% 且撞过 429」时**拒绝落盘并返回 -1**（退出码 1），等图源空闲后重跑。
「连续两次仍为空」才当作真没料。

### 16.5 腾讯配额用尽改为自动切高德

主人说「腾讯每天 200 次可能不够，高德也刷新了」。查下来：`place_search` 一晚 1 城 72 次
（占 36%）其实够用，但代码里有个**让高德白白闲置**的旧判据：

```python
# 旧：_quota_dead() 只看腾讯，用尽即整城跳过（0 请求）
# 注释写的是「2026-10-08 用户确认：高德额度已满，不可用」
```

高德是**月配额**，11-01 已刷新（实测 `amap.place_search('合肥 博物馆')` 正常返回 10 条）。
所以旧判据的后果是：明明高德能用，却整城不发一个请求。

新判定顺序：

| 情形 | 行为 |
|---|---|
| 腾讯还有额度 | 用腾讯 |
| 腾讯用尽 + 高德可用 | **`GEO_PROVIDER=amap` 强制切高德**，继续跑本城（打一次提示） |
| 两家都不可用 | 整城跳过，`quotaHit=1` 留给下一轮优先补 |

★ **为什么必须显式设环境变量**，不能等 `geoprovider` 自己切：它的切换条件是
`tmap.quota_exhausted("place_search")`，而那是**进程内**内存集合 —— 新进程启动时必定是"没死"。
腾讯配额早就满了的情况下，新进程仍会先打腾讯、白烧到收到第一个 121 才切（失败请求同样计费）。
账本预判是零成本的前置判断。

★ 高德切过去后用掉的是**月配额**（用一点少一点，下个月才回来），所以仍然只做 1 城。

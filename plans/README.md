# 旅游攻略 · 架构设计文档集

> 目标：一个**纯前端**的「城市旅游攻略 + 行程规划」站点 —— 地图是主界面，默认打开是**中国全图**，逐级下钻到省、市，把景点按**细类**着色撒在图上，并标注**适游群体**与**无障碍友好**；在此基础上支持**用户自定住宿点、自选点位、自排顺序，系统算出通勤时间**，六种通行方式各给多条备选路线。
> 所有文案、图片、坐标均由**联网搜索抓取 + 结构化清洗**产出，**全国区划的景点计数在构建期算好**，最终固化成静态 JSON，前端零后端依赖。
> ★ **通勤时长例外：运行时才算，不预存**（2026-10-06 决策，见下方「决策变更记录」）。

## ⚠️ 决策变更记录（**先看这里，否则下面几份文档会骗你**）

### ① 通勤矩阵：**构建期预存 → 运行时按需计算**

**现在的做法**：通勤时长（POI ↔ POI）**不落盘、不预计算**，在用户实际规划行程时才请求图商接口，带本地缓存 + 配额账本。

**为什么推翻原方案**（原方案是"构建期把 N×N 种组合算完固化进 JSON、运行时 O(1) 查表、零 API 调用"）：

| 维度 | 原方案（构建期预存） | 现方案（运行时算） |
|---|---|---|
| 仓库体积 | 62 城 × 约 1600 对 × 3 方式 ⇒ **几百 MB 级**，远超"单城 ≤300KB gzip"的预算 | 0（不进仓库） |
| 时效性 | 时长是**生成时刻的快照**，一两个月后驾车时长已明显失真 | 每次都是当下的真实路况 |
| 与架构的一致性 | 需要一个"构建期产物"例外，而区划计数已经是构建期产物了 —— 两种口径并存难解释 | 与「运行时零 API 调用」的原表述冲突，必须**改表述而不是加例外** |

**连带变更**：
- `pipeline/steps/step6_transit.py`（原构建期矩阵生成脚本）是**遗留死链路，不许跑**。`run.py` 已把 `transit` 子命令摘掉。
- `transit.json` / `transit` 字段**不再生成**。★ **2026-10-25 已彻底拆干净**：`cityRegistry` 的 glob 与赋值、
  `usePlanView` 的 `city?.transit`、`usePosterExport` 的同款读取、`schema`（`.ts` / `.py`）的
  `CityTransitMatrix`、`itinerary/matrix.ts`、`pipeline/steps/step6_transit.py`、`build.py` 里那条
  「缺 transit」假 WARN —— 全部删除。行程页段时长并轨到 `routeSetCache`（与海报同源）。
- 行程页的通勤时长走 `common/logic/itinerary/routeOptions.ts` 的**实时链路**（与住宿点、公交/地铁同一条路）。
- ★ **判"有没有跑通"别看 `run.py usage` 的 matrix 用量** —— 失败请求也记账，会虚增。
- ⚠️ ~~`build.py` 里那条「缺 transit」WARN 是假告警~~ —— 2026-10-25 连告警本身一起删了。

## 一句话架构

```
开发期：联网搜索抓取 + 结构化 + 地理编码 + 取图外链 + ★区划树计数 + 质量校验
        ↓
   data/ 目录（纯文本 JSON：文案 + 坐标 + 图片 URL + ★各级景点计数）→ 进仓库
        ↓  Vite + React Router 预渲染（SSG）
   每路由一份静态 HTML（含正文与 SEO meta）+ 客户端 bundle
        ↓  Netlify 部署
   CDN 直出 HTML → 搜索引擎能收录，用户秒开
        ↕ 可选
   GitHub Actions：月度图片巡检自愈 / 季度内容刷新 → 自动 PR → Build Hook 触发重建

默认打开：★ 中国全图（各省景点数）→ 点击省 → 省地图（各市景点数）→ 点击市 → 城市撒点（细类着色）
运行时的通勤时长：★ **实时调图商算**（2026-10-06 决策，不预存矩阵），带缓存 + 配额账本
   —— 「各级景点计数」才是构建期固化、运行时零调用的那部分
```

**开源可复现**：数据层与代码层完全解耦，clone 后 `cd web && npm i && npm run dev` 即可开发（应用工程在 `web/`，`data/` 在仓库根 —— 见 [01 文档](./01-overview.md) 第五节）。
**唯一前置依赖**：一个免费的**腾讯位置服务 key**（个人开发者即可；也可以在页面里填自己的 key，见下方「开源使用者如何自备 key」）。

## 核心决策速览

| 项 | 决策 | 理由 |
|----|------|------|
| 运行时形态 | **纯静态 + 预渲染**，无后端 API、无数据库 | 满足"纯前端"要求；Netlify 直接托管，零服务端运行时 |
| 渲染策略 | **SSG**（React Router 7 `prerender`）+ 客户端 hydrate | 搜索引擎能收录城市页与每个 POI 详情页；交互体验与 SPA 一致 |
| 数据采集时机 | **开发期就生成好**，数据随仓库走；运行时零抓取 | 浏览器无法跨域抓取，也不该把第三方 API key 放进前端 |
| 地图服务商 | **腾讯位置服务 · JavaScript API GL** | **判据变了**：新增行程规划后，「批量距离矩阵」升为首要判据，因此结论由高德**改回腾讯** —— `/ws/distance/v1/matrix` 一次 25×25 = 625 对，**驾车 / 步行 / 骑行三种方式都有批量**（高德骑行只能一对一，1,035 次/城）。且腾讯 JS API **只需一把 key**（无 `securityJsCode` 负担），配额**按接口独立、每日重置**（无"1 年免费期"问题）。完整论证与三次决策变迁见 [07](./07-map-provider.md) |
| **行程规划** | **用户定住宿点 + 自选点位 + 自排顺序，系统只算时间** | 用户明确要"自己确定住的地方、自己确定去哪些景点"，所以**不做自动排序优化（TSP）**。且缺营业时间窗与预约时段数据，"最优顺序"不可信 —— 只算时间反而是更硬的承诺。见 [09](./09-itinerary-planner.md) |
| **通勤时长来源** | ★ **运行时按需算，不预存**（2026-06-06 决策，见上方变更记录） | 原方案是构建期把 N×N 种组合算完固化进 JSON、运行时 O(1) 查表，但 62 城 × 约 1600 对 × 3 方式要**几百 MB**，且时长是生成时刻的快照、一两个月就失真。现在统一走运行时链路（与住宿点、公交/地铁同一条），带缓存 + 配额账本。**六种方式**里驾车/打车/骑行/步行走批量矩阵接口，公交/地铁走 transit 接口 |
| **地图 key 策略** | **双 key：内置受限 key + 使用者可自备** | 内置 key 保证 clone 后开箱可用；同时提供「使用我自己的 Key」入口，把用量转移到使用者自己的账号。腾讯按接口独立计配额（各 10,000/日、每日重置），无到期断供问题。见 [07](./07-map-provider.md) 第八节 |
| 底图策略 | **类型 + 详细度开关**：底图类型（矢量图 / 影像图）单选，"简略 / 详细"一键，再往下是逐项开关（地点名称 / 道路名称 / 建筑 / 路网与地名）；两端默认一致 | 用哪张图**由用户决定**，不再按缩放自动切换 —— 界面不听指令（选了影像却自己变回矢量）本身就是 bug。可开关的项来自 `features` 白名单，是[真机探针实测](03-map-interaction.md)出来的（**文档里有、实测完全无效的 `arrow` 一律不收**）；偏好写入 `localStorage` 下次沿用。⚠️ 按 POI 类别（地铁站 / 超市 / 区划）单独控制**做不到** —— 腾讯只给图层级开关，见 03 文档 2.2.1 |
| 坐标来源 | 腾讯「地理编码」WebService | 与底图同源同坐标系，落点不偏、无需纠偏。⚠️ 一对一接口（无批量），但请求数 = POI 数，量很小。**与高德同为 GCJ-02，改回腾讯不需动坐标字段** |
| **三级下钻** | **全国 → 省 → 市，逐级展示景点数** | 默认打开中国全图（各省景点数），点省看各市，点市撒点。计数在构建期预计算进 `district-tree.json`（运行时零调用）；边界只用腾讯 District 服务；未收录城市显示"待收录"（**不是 0**）。见 [10](./10-map-drilldown.md) |
| **POI 类型体系** | **两级：大类（筛选维度）+ 细类（颜色维度）** | 4 大类（景点 / 美食 / 网红 / 特色）承担筛选；12 细类（自然景观 / 博物馆 / 古迹 / 公园 / 本地菜 / 小吃 / 咖啡馆 / 拍照机位 …）决定地图点位颜色。细类上限 12 是因为 34px marker 下超过约 12 色人眼就分不清 |
| **适游群体** | **6 类枚举 + 无障碍布尔** | 独游 / 情侣 / 亲子 / 朋友 / 家庭 / 长辈；`accessible` 默认 `false`（未核实不声称）。判定依据必须来自来源页面的客观描述，**禁止凭印象打标**。见 [02](./02-data-model.md) |
| **六种通行方式** | 驾车 / 打车 / 公交 / 地铁 / 骑行 / 步行，**各给多条备选路线** | 打车复用驾车通道（同路同速、费用不同）；公交+地铁走 `transit` 接口；其余三条走矩阵接口 —— **六种方式落到两条接口链路**，且**全部在运行时请求**。多路线靠 `get_mp=1`（最多 3 条）+ `get_speed=1`（路况）实现，应对堵车。见 [09](./09-itinerary-planner.md) 3.2 / 3.6 |
| 图片策略 | **全外链直链**：Unsplash 主 + 百科兜底 + Pexels 补，仓库零图片文件 | Unsplash 官方强制热链（禁止下载重托管），正好契合零维护；**Wikimedia 因国内被封锁降为备用** |
| 图片更新 | 每张图带 `query` → Actions 月度巡检 → 失效自动重搜补图 → 开 PR | 热链 URL 本身不过期，真正要防的是文件被删/改名，靠自愈闭环解决 |
| 数据格式 | **JSON 分片**（不是 SQLite） | 内容是靠 PR 协作的，JSON 的 diff 人能读、二进制不能；46 条数据内存查询微秒级，SQL 是杀鸡用牛刀 |
| 数据目录 | 顶层 `data/`（cities + credits + _generated），与 `app/` 解耦 | 新增城市只加一份 JSON，路由与索引自动生成，**不改一行前端代码**；区划树/边界在 `_generated/` 下统一生成 |
| 溯源 | **字段级** `xxxRef` → `sources[]` 下标，UI 角标可跳转 | 每个事实都能点回原始出处；图片必带 credit 与来源链接 |
| 部署 | **Netlify** | Deploy Preview（数据 PR 能直接看效果）+ Build Hook（数据更新自动重建） |
| 布局模型 | **地图即画布（Map as Canvas）**：底层是铺满 100% 视口的地图，所有 UI（顶栏 / 列表 / 详情 / 图例 / 控件）都是浮在地图之上的浮层 | 地图和内容不再争同一块面积。地图拿到 100%，UI 随时可收起且收起后地图不变形。两端共用同一模型，只是浮层形态不同（移动端胶囊 + Sheet / 桌面端悬浮卡片） |
| 端适配 | **移动优先**：默认样式即手机竖屏，媒体查询向上增强（`min-width`）；三档断点之间**只改浮层尺寸，不改布局模型** | 主力流量在移动端浏览器；地图铺满同时消除了"地图拖动 vs 页面滚动"的手势冲突。详见 [05 第 1.0 节](./05-ui-ux-design.md)与 [08](./08-mobile-adaptation.md) |
| 技术栈 | Vite 7 + React 19 + TS + Tailwind 4 + Zustand + React Router 7 | 生态成熟、构建快、类型安全 |

## ✅ 已确认的决策

**内容与托管：**

**1. 内容规模：每城 ≈ 46 个点位** —— 景点 15 / 美食 15 / 网红打卡 10 / 特色 6。
这个量在地图上不挤、列表够滚，且单城 JSON 实测约 30KB gzip，远低于 300KB 上限。（★ 原先算进来的**通勤矩阵已不再入库** —— 改运行时算，见变更记录。）

**2. 托管平台：Netlify 单站。**
项目定位是个人自用的简单开源项目，**优先"零运维"，不为国内可达性引入域名备案与国内云资源**。

> ⚠️ 已知取舍（记录在案，不回避）：Netlify 免费版最近的 CDN 节点在新加坡，**国内实测"能连通但加载完成不了"**（2026-08-30 探测：首字节 335ms、首屏 1.4s，但 3 次请求全部未能在 60s 内完成）。这会拖慢国内移动端 LCP，也会削弱百度收录。
> **接受的理由**：构建产物是纯静态文件 —— 路径全相对、无服务端依赖、无数据库。将来若要迁国内，**只换托管、不改一行代码**。国内加速是可选升级项，不必现在做。详见 [08](./08-mobile-adaptation.md) 第十节。

**行程规划与地图（本轮新增的 6 项）：**

| # | 决策 | 选项 | 影响 |
|---|------|------|------|
| 3 | **行程粒度** | **多日、可中途换住宿** | 数据模型要支持多个住宿段，每天归属一个 `Stay`（`fromDay`/`toDay`）。比"固定一个酒店"复杂，但贴合真实行程 |
| 4 | **排序方式** | **只算时间，顺序用户自己定** | ✅ **砍掉了浏览器端的 TSP / 2-opt 优化器** —— 算法从"路径优化"退化为"查表 + 时间链推导"。更简单、更可控，且避免了用缺失的数据（营业时间窗）去算不可信的"最优" |
| 5 | **通勤方式** | **六种全做**（驾车 / 打车 / 公交 / 地铁 / 骑行 / 步行），**各给多条备选路线** | 腾讯矩阵**驾车 / 步行 / 骑行三种都有批量**，每城约 12 次请求 ≈ 7,500 计算次数。打车复用驾车通道（同路同速、费用不同），公交 / 地铁走 `transit` 接口（运行时按需）。多路线靠 `get_mp=1`（最多 3 条）+ `get_speed=1`（路况）实现，应对堵车 |
| 6 | **地图 key 策略** | **内置受限 key + 使用者可自备** | 双 key 模式。既保证 clone 后开箱可用，又把运行期用量转移给使用者。腾讯按接口独立计配额（各 10,000/日、每日重置），**无"1 年免费期"到期问题** |
| 7 | **地图层级** | **全国 → 省 → 市 三级下钻** | 用户明确要求：默认中国全图看各省景点数，点省看各市，点市撒点。计数预计算进 `district-tree.json`，运行时零调用；**先只填成都 / 四川**，其余显示"待收录"（非 0）。见 [10](./10-map-drilldown.md) |
| 8 | **POI 展示维度** | **细类着色 + 适游群体 + 无障碍标识** | 细类（12 个）决定点位颜色以区分类型；`audience`（6 类）标注适合谁去；`accessible` 标注无障碍友好。见 [02](./02-data-model.md) |

> 📌 决策 4 是本轮**最重要的取舍**：它让"行程规划"从一个大工程变成了一个可控的小工程。如果后来想加自动排序，`buildTimeline` 是纯函数、矩阵是完备的 —— 加一层排序是在现有基础上叠加，不需要重构。见 [09](./09-itinerary-planner.md) 1.1。

## 合规红线（不可绕过）

- **地图**：只能用高德地图 / 腾讯地图 / 百度地图 / 天地图；Google Maps、Leaflet+OSM、Mapbox 一律不用。
- **地图 key**：不得硬编码进代码，统一从环境变量读 + 占位符兜底；**必须在控制台配 Referer 域名白名单 + 配额告警**。
  > 前端 key 在**任何**托管平台都可见（Netlify 也不例外，这是浏览器的机制而非平台缺陷）。腾讯 JS API key 本就是公开设计，护城河是域名白名单，不是隐藏。相比高德，腾讯**不需要额外的 `securityJsCode`**，暴露面更小。详见 [07](./07-map-provider.md) 第七节。
- **行政边界（合规红线）**：三级下钻的省 / 市边界**只能来自腾讯 District 服务**，**绝对禁止**使用第三方 GeoJSON —— 这涉及台湾、藏南、南海诸岛的表达，属于《地图管理条例》范畴。必须覆盖**全部 34 个省级单位**（含中国台湾 / 中国香港 / 中国澳门）。详见 [10](./10-map-drilldown.md) 第九节。
- **影像图**：是四档预设之一（用户可自行选择），只调用服务商的合规影像服务；不得截图后加工、二次分发或作为自有地图数据；**服务商版权署名不得遮挡或移除** —— 切换底图时署名文案要跟着变，别残留上一个底图的署名。
- **图片**：只用开放许可素材（Unsplash / Pexels / 百度百科署名引用）；携程、马蜂窝、小红书等站点图片**仅供参考、不得外链入库**；Pixabay 因禁止热链已排除。
- **图片署名**：Unsplash / Pexels 建议署名，百度百科与 CC BY 系列**必须**在界面显示可见署名与来源链接。
- **内容**：每个点位必须记录来源链接与抓取日期（`sources[]` + `fetchedAt`），不做无出处的编造。
- **通勤时长**：⚠️ **原来的表述已随决策反转**。旧方案里时长是构建期生成的**快照**，要求"不得说成实时"；现在时长是**运行时按当下路况算出来的**，但仍**必须如实标注**它是"查询时刻的估算"（受缓存与配额降级影响，见变更记录与降级表）—— **不允许把它说成"实时路况"**，因为缓存命中时可能是几分钟前的结果。
- **敏感地物**：不标注军事管理区、涉密单位、私人住宅坐标；不采集、不上传用户位置。
  > ⚠️ **行程规划引入了新的个人信息面**：住宿点是用户隐私（等于"他在哪过夜"）。因此行程数据**只存 `localStorage`**，不上传、不进 URL（分享链接只在用户主动点"分享"时才生成，且**住宿点默认脱敏**为「住宿点」不带名称，可选项才带）。见 [09](./09-itinerary-planner.md) 第八节。

## 开源使用者如何自备 key

为了让 clone 者「5 分钟能跑起来」，同时**不让维护者的配额被他人消耗**，本项目采用**双 key 模式**：

| 层 | 来源 | 用途 |
|---|------|------|
| ① 最高优先 | 使用者在页面里填的自己的 key（存 `localStorage`） | 重度使用者 / fork 者 / 自部署者。**配额与用量都算他自己的** |
| ② 兜底 | 构建期注入的环境变量 key（维护者的「受限 key」） | 只配 Referer 域名白名单，保证 clone 后打开就能看到效果 |
| ③ 都没有 | — | **不初始化地图，走降级卡片**（列表、筛选、详情、**下钻计数**、**以及行程的时间计算**全部照常可用） |

**申请步骤**（约 5 分钟）：
1. <https://lbs.qq.com/> → 注册（QQ / 微信 / 手机号均可）→ 完善**个人开发者**信息
2. 应用管理 → 我的应用 → 创建应用 → 添加 Key → 选「**JavaScript API GL**」→ 配 **Referer 域名白名单**
3. 记下 **key**
4. 本地开发：复制 `.env.example` 为 `.env`，填入这个值
   - 或更省事：直接打开站点，在设置里填进去（存本地，不落仓库）

> 💡 **再建一个「WebService API」类型的 Key**给采集脚本用（地理编码 + 距离矩阵 + 区划服务），建议配 IP 白名单或开启 SN 签名校验。分开的好处是**用量能分别统计**，且脚本 key 泄露不影响线上。

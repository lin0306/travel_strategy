# 10 · 三级地图下钻（全国 → 省 → 市）

> **一句话**：默认打开就是中国地图，每个省标着「有多少个可玩的地方」；点进去看这个省里哪些市有内容；再点进去就是那座城市的点位图。
> **本质**：把「我该去哪玩」这个决策，拆成三次由粗到细的空间选择 —— 而不是让用户在一堆城市卡片里盲选。

---

## 一、Why：为什么要有下钻

### 1.1 它解决的是什么问题

原方案的首屏是「一张地图 + 10 个城市 marker + 左侧列表」。这在只有 10 个城市时可用，但有两个结构性缺陷：

| 问题 | 说明 |
|------|------|
| **不可扩展** | 城市涨到 100 个时，地图上 100 个点会糊成一片，列表变成无意义的滚动 |
| **缺少决策依据** | 用户看着"成都""西安"两个名字，不知道哪个更值得去、哪个内容更多。**他需要的是"这个省有没有内容、有多少"**，而不是一串地名 |

下钻把首屏从「城市清单」升级为「**内容分布图**」：哪个省内容多、哪个市值得点，一眼可见。

### 1.2 用户的实际决策路径

```
"我想出去玩，但不知道去哪" 
  → 看中国地图，哪个省内容多（四川 46 个，看着多）
  → 点进四川，成都 46 个、其余待收录
  → 点进成都，撒点图：46 个点按类型铺开
  → 挑几个点，进入行程规划
```

**每一步都比上一步更具体，且每一步都能退出重选** —— 这是它比"城市卡片网格"好的根本原因。

### 1.3 为什么不做成「城市列表页」

| 方案 | 问题 |
|------|------|
| 城市卡片网格 | 与「地图即画布」模型冲突（回到了"地图占一块"的分栏） |
| 全国城市列表 | 100 个城市的名词列表，用户读完还是不知道去哪 |
| **地图下钻** | ✅ 空间选择 + 数量信息 + 与现有布局模型一致 |

> 📌 **判定标准**：如果某个导航方案需要新增一个「非地图」的页面结构，它就不该做 —— 见 [05 文档](./05-ui-ux-design.md) 1.0 节的「地图即画布」硬规则。

## 二、层级模型与路由

### 2.1 三级模型

```
Level 1  中国全图        每个省级区划显示「N 个可玩的地方」
   │     /                34 个省级单位（含港澳台）
   │     点击某个省
   ▼
Level 2  省级地图        每个市级区划显示「N 个可玩的地方」
   │     /province/510000 该省的各地级市
   │     点击某个市
   ▼
Level 3  市级地图        撒点：该市的全部 POI，按细分类型配色
         /city/chengdu
```

### 2.2 路由设计

| 层级 | 路由 | 说明 |
|------|------|------|
| 全国 | `/` | 首页即全国图 |
| 省级 | `/province/:adcode` | 如 `/province/510000`（四川省）。**用 adcode 而非拼音** —— 省是纯区划概念，没有对应的城市数据文件 |
| 市级 | `/city/:cityId` | 如 `/city/chengdu`。**沿用现有 slug** —— 与 `data/cities/{id}.json` 一一对应，且 SEO 友好 |
| 详情 | `/city/:cityId/poi/:poiId` | 不变 |
| 行程 | `/city/:cityId/plan` | 不变 |

**为什么两级用不同的键**：

- 省级用 `adcode`：省没有独立的数据文件，它只是区划树上的一个节点
- 市级用 `slug`：城市有独立数据文件（`chengdu.json`），slug 是可读的、SEO 友好的

**关联键**：城市数据文件里的 `adcode` 字段（如 `"510100"`）把两者接起来：

```jsonc
// data/cities/chengdu.json
{
  "id": "chengdu",
  "adcode": "510100",      // ★ 与区划树的关联键
  "provinceAdcode": "510000",
  "name": "成都",
  ...
}
```

### 2.3 路由与 SEO

**每一级都要预渲染独立 HTML**（这与现有 SSG 策略一致）：

```
dist/
├─ index.html                              中国全图（含各省计数，可被搜到）
├─ province/510000/index.html              四川省页
├─ city/chengdu/index.html                 成都页
└─ city/chengdu/poi/xxx/index.html         点位详情
```

省级页的 `<title>` 形如「四川旅游攻略 · 21 个市 · 46 个可玩的地方」—— 这类"数量 + 地名"的长尾词是真实搜索需求。

### 2.4 前进 / 返回的状态管理

| 动作 | 行为 |
|------|------|
| 点省边界 | `push` 到 `/province/:adcode`，地图 `fitBounds` 到该省范围 |
| 点市边界 | `push` 到 `/city/:cityId`，地图 `fitBounds` 到该市点位 |
| 浏览器后退 | 回到上一级，**恢复上一级的视野与浮层状态**（不是重新初始化） |
| 面包屑点击 | 同上，等同于后退到该级 |
| `ESC` 键 | 返回上一级（桌面端） |
| 移动端右滑 | 返回上一级（见第八节） |

> ⚠️ **「恢复上一级视野」不是自动的**。浏览器后退只恢复 URL，地图实例是同一个、视野停在下钻前的状态。需要把每级的视野存进 `history.state`，`popstate` 时读回来重新 `fitBounds`。**这是最容易做漏的一处** —— 漏了的话用户后退会看到"URL 变了但地图没动"。

## 三、数据源：腾讯 District 服务

### 3.1 三个接口

```
GET https://apis.map.qq.com/ws/district/v1/list
    → 全国省 / 市 / 区县三级完整列表（不含边界，体积小）

GET https://apis.map.qq.com/ws/district/v1/getchildren?id=510000&get_polygon=1
    → 指定区划的子级 + 边界点串

GET https://apis.map.qq.com/ws/district/v1/search?keyword=成都&get_polygon=1
    → 关键词匹配单个区划 + 边界
```

**JS API 侧封装**：`TMap.service.District`，配 `POLICY_CONTAIN_CHILDREN` 可一次拿到子级。

### 3.2 返回结构

| 字段 | 说明 | 我们的用法 |
|------|------|-----------|
| `id` | adcode（6 位） | 路由键、关联键 |
| `name` / `fullname` | 简称 / 全称 | 简称用于地图标注（"内蒙古"），全称用于 SEO |
| **`location`** | **中心点经纬度** | ★ **"各省/市有多少个"的标注锚点** —— API 直接给了，**不需要自己算多边形质心** |
| `level` | 几级区划 | 校验层级对不对 |
| `polygon` | 轮廓面点串 | 绘制边界（需 `get_polygon=1`） |
| `cidx` | 子级在下级数组中的下标 | 构建树结构用 |

> 💡 **`location` 中心点是这个接口最省事的地方**。自己算多边形质心会遇到"环状区域质心落在空洞里""狭长地形质心跑到边界外"的问题（比如甘肃），官方给的中心点是经过处理的可用点。

### 3.3 adcode 规则与特例（必须处理，否则下钻会崩）

```
格式：6 位数字    前 2 位 = 省    中 2 位 = 市 / 地区    后 2 位 = 区县

130000  河北省
130600  河北省保定市
130681  河北省保定市涿州市
```

**四个必须写进代码的特例**：

| # | 特例 | 处理 |
|---|------|------|
| 1 | **直辖市**（北京 110000 / 上海 310000 / 天津 120000 / 重庆 500000）**与港澳**（810000 / 820000） | 省级下**直接是区级**，没有二级结构。下钻时若发现 `children` 的第一项是区级，**不报错**，直接展示（用户点"北京"看到各区的计数） |
| 2 | **省直辖县**：第 3、4 位为 `90`（如 419001 济源市） | 视同地级市处理（作为直辖县单独列出） |
| 3 | **中国范围内非行政区划区域**：`999999`（如东海） | **过滤掉**，不入树，不显示 |
| 4 | **台湾省 / 香港 / 澳门** | **必须作为省级单位正常出现在全国图上**（710000 / 810000 / 820000）。见第九节合规红线 |

### 3.4 边界数据的参数（含待核实项）

从腾讯官方示例里看到的参数组合：

```
/ws/district/v1/getchildren?key=...&get_polygon=2&max_offset=3000
```

| 参数 | 观察到的取值 | 状态 |
|------|------------|------|
| `get_polygon` | 文档写 `1` = 返回轮廓；官方 demo 用了 `2` | ⚠️ **待核实**：`2` 是否表示"简化轮廓"。见第十一节 T3 |
| `max_offset` | demo 用 `3000` | ⚠️ **待核实**：推测是轮廓简化的容差（米）。越大越简化、体积越小。见 T4 |

> **这两个参数直接决定边界数据的体积**，而体积决定首屏能不能秒开（全国 34 个省级边界）。**必须在 M1 阶段实测确定**，不能照抄 demo。

## 四、区划树与聚合索引

### 4.1 为什么要在构建期做

区划树 + 计数是**纯静态数据**，与用户无关 —— 完全可以在构建期算好固化进仓库，运行时零 API 调用（除非用户下钻到没缓存的省）。

这保住了本项目的核心架构前提：**运行时纯前端**。

### 4.2 聚合索引的结构

```jsonc
// data/_generated/district-tree.json
// ★ 全部脚本生成，禁止手改
{
  "version": "20260101",            // District 数据的 data_version
  "generatedAt": "2026-09-17",
  "provinces": [
    {
      "adcode": "510000",
      "name": "四川",
      "fullname": "四川省",
      "center": { "lng": 104.075931, "lat": 30.651652 },   // ★ 直接用 API 的 location
      "poiCount": 46,                // 该省已收录 POI 总数
      "cityCount": 1,                // 已收录城市数
      "childCount": 21,              // 下辖地级市数（来自区划树）
      "children": [
        {
          "adcode": "510100",
          "name": "成都",
          "center": { "lng": 104.0665, "lat": 30.5723 },
          "cityId": "chengdu",       // ★ 有数据 → 指向城市文件
          "poiCount": 46
        },
        {
          "adcode": "510300",
          "name": "自贡",
          "center": { "lng": 104.7784, "lat": 29.3392 },
          "cityId": null,            // ★ 无数据 → null，UI 显示"待收录"
          "poiCount": 0
        }
      ]
    }
  ]
}
```

**关键字段语义**：

| 字段 | 语义 | 空态判定 |
|------|------|---------|
| `cityId` | 是否已收录这座城市 | `null` = 待收录 |
| `poiCount` | **仅统计已收录的 POI** | — |
| `childCount` | 区划树上的下辖数量（与内容无关） | — |

> ⚠️ **`childCount` 与 `cityCount` 必须分开**。四川下辖 21 个地级市（`childCount`），但只有 1 个已收录（`cityCount`）。UI 上要表达的是「**已收录 1 / 共 21 个市**」—— 让用户知道这是进度问题，不是内容问题。

### 4.3 计数口径

用户说的是「有多少个**景点**」，但我们的数据有四类内容（景点/美食/网红/特色）。定义：

- **默认口径**：全部 POI 总数
- **可切换口径**：按四大类筛选后重新计数（如只看"景点"）

UI 文案统一用「**可玩的地方**」而不是"景点"，因为它涵盖了美食与打卡点：

```
四川
46 个可玩的地方 · 已收录 1/21 个市
```

## 五、地图侧实现

### 5.1 边界图层

```ts
// app/map/tencent/districtLayer.ts
const layer = new TMap.MultiPolygon({ map, styles: DISTRICT_STYLES, geometries: [] })
```

**填色按 `poiCount` 分四档** —— 让全国图一眼能看出内容密度：

| 档位 | `poiCount` | 填充 | 描边 |
|------|-----------|------|------|
| **待收录** | 0 | 极浅灰 `rgba(136,135,128,0.06)` | 灰**虚线** |
| 稀疏 | 1–20 | 浅蓝 | 蓝实线 |
| 中等 | 21–60 | 中蓝 | 蓝实线 |
| 密集 | 61+ | 较深蓝 | 深蓝实线 |

### 5.2 计数徽标

在每个区划的 `center` 上挂一个徽标（`MultiLabel` 或自定义 marker）：

```
        ┌──────────┐
        │  四川     │
        │ 46 个     │
        └──────────┘
```

- 待收录的区划：徽标显示「待收录」，且用**弱化样式**（浅灰底、灰字）
- 徽标可点击（等同于点边界）
- ⚠️ **徽标与边界多边形都要能点** —— 小省份（如上海）的多边形可能很小，只靠多边形命中率低。徽标提供了一个"最小点击面积"的兜底

### 5.3 层级切换的过渡

```ts
// 下钻：把视野框到目标区划的边界范围
map.fitBounds(provinceBounds, { padding: freeRectToPadding(), duration: 600 })
```

**过渡要给出方向感**：

| 动作 | 动画 |
|------|------|
| 下钻（全国 → 省） | 目标省放大充满视野；其他省淡出到 0.3 不透明度 |
| 返回（省 → 全国） | 反向：本省缩回原位，其他省恢复 |

> ⚠️ **不要做"渐变替换"（旧层淡出 + 新层淡入同时进行）** —— 中间会有一段两层都半透明的混沌期，看起来像渲染错误。正确做法：**旧层保持可见，新层直接铺上，然后旧层淡出**。

## 六、空态设计（本轮最重要的体验决策）

### 6.1 问题

用户选了「**先跑通链路**」—— 架构按全国 34 省设计，但首批只有四川（成都）有数据。这意味着：

```
全国图上 34 个省级区划 → 1 个有数据，33 个是 0
```

**首屏怎么设计，决定了这个项目看起来是"刚起步"还是"很空"。**

### 6.2 四种处理方式的取舍

| 做法 | 判定 |
|------|------|
| ❌ 显示「0 个景点」 | **信息是错的** —— 用户会以为"这地方没景点"，而事实是"我们还没收录" |
| ❌ 完全不画这些省 | 中国地图出现空洞 → **触发版图完整性问题**（见第九节） |
| ❌ 和其他省一样的实色 | 用户点进去发现没数据 → 挫败 |
| ✅ **灰色 + 虚线描边 + 「待收录」** | 边界完整可见（合规），视觉上明确表达"未完成"，点击有导流 |

### 6.3 空态的视觉语言

```
待收录省份：
  填充  rgba(136,135,128,0.06)    ← 极低透明度，几乎只剩轮廓
  描边  #B4B2A9  虚线 [4,3]        ← ★ 虚线是关键：表达"未完成/规划中"
  徽标  「待收录」  浅灰底 + 灰字

有数据省份：
  填充  蓝色梯度（按 poiCount 分档）
  描边  蓝色实线
  徽标  「N 个」  白底 + 深字
```

**为什么虚线是对的**：虚线在中国地图语境里天然表达"未完成/规划中"，且**不破坏版图完整性** —— 边界依然清晰可见，只是用线型区分了状态。

### 6.4 点击待收录省份不能给死路

```
┌─────────────────────────────────┐
│  甘肃 · 待收录                   │
│                                 │
│  我们正在陆续补充全国城市。       │
│  先看看已上线的成都？             │
│                                 │
│  [ 去看成都 ]      [ 知道了 ]    │
└─────────────────────────────────┘
```

**三个设计点**：

1. **不跳转，只弹卡片** —— 不把用户扔到一个空页面
2. **把空态变成导流** —— "先看看已上线的成都" 直接把流量导向有内容的地方
3. **文案要诚实** —— "我们正在陆续补充"，而不是假装"暂无数据"

> 💡 **这个空态设计是「先跑通链路」这个决策能成立的前提。** 没有它，首屏 33 个灰省份会显得项目很空；有了它，"待收录"反而变成了**进度感**的表达 —— 用户能看到这个项目在长大，而不是"做了一半"。

### 6.5 省级页的空态

四川页有 21 个地级市，20 个待收录。处理同上，但要额外给一行汇总：

```
四川 · 已收录 1 / 21 个市
[成都 46] [自贡 待收录] [攀枝花 待收录] ...
```

> 📌 **面包屑放在底部图例条里，不新增浮层** —— 这是原型阶段确立的原则：**能并入已有浮层的信息，绝不新开浮层**。新浮层无论放哪儿都会压住地图上的内容（原型里 `.fbtag` 的教训）。

## 九、合规红线（本章最重要）

### 9.1 🚨 边界数据只能来自腾讯官方服务

> **三级下钻的行政区划边界，只能使用腾讯 District 服务返回的数据。**
> **绝对禁止**：
> - 引入任何第三方 GeoJSON（哪怕看起来很权威）
> - 自行绘制、简化、拼接中国地图轮廓
> - 使用 Wikipedia / Natural Earth / 各类开源数据集的中国边界

**为什么这条是红线**：中国地图的行政区划边界涉及**国家版图完整性**，具体包括：

| 敏感区域 | 常见错误 |
|---------|---------|
| **台湾省** | 第三方数据常把它单独成"国家"或缺失 |
| **藏南地区** | 第三方数据常按错误的实控线绘制 |
| **南海诸岛** | 第三方数据常完全缺失，或未按九段线表达 |
| **阿克赛钦** | 第三方数据常有偏差 |

这类错误**违反《地图管理条例》**，且在开源项目中极其常见（因为大量开源 GeoJSON 来自境外数据源）。

**用腾讯官方服务就自动合规** —— 持牌图商的数据已经过审图。

### 9.2 全国图必须包含的区划

```
✅ 23 个省 + 5 个自治区 + 4 个直辖市 + 2 个特别行政区 + 台湾省
   台湾省   710000   必须出现，不得缺失
   香港     810000   必须出现
   澳门     820000   必须出现
```

**验收方式**：全国图上数一遍省级区划数量，确认 34 个（含港澳台）齐全。

### 9.3 其他合规要求

| 项 | 要求 |
|----|------|
| 底图 | 使用腾讯底图自带的国家版图表达（含南海诸岛的标准画法），**不自行裁剪或遮盖** |
| 署名 | 「© 腾讯地图 + 审图号」**不得遮挡、不得移除**；切换底图时署名文案要跟着变 |
| 边界形状 | **不得修改** API 返回的边界形状（不简化到失真、不"修补"凹陷） |
| 敏感地物 | 不标注军事管理区、涉密单位；描述中不出现敏感地名 |
| 正式发布 | 若对外商用，应使用自然资源部**标准地图服务**（带审图号）或走商业授权 |

## 十、性能

### 10.1 边界数据的体积控制

**这是本方案最大的性能风险**。全国 34 个省级边界，如果每个用全精度轮廓，总量可能达到数 MB。

| 数据 | 体积估算 | 策略 |
|------|---------|------|
| 全国省级边界（34 个） | 未知，**待实测**（见 T3/T4） | 若 > 300KB，用 `max_offset` 提高简化容差；或按需加载（先画简化版，放大后补精度） |
| 单省市级边界（约 21 个） | 约为省级的 1/5 | 按需拉取 + 缓存 |
| 区划树（无边界） | **< 50KB** | 直接内联进首屏 bundle |

### 10.2 缓存策略

```
① 区划树（无边界）      → 进仓库 data/_generated/district-tree.json，随构建打包
② 全国省级边界          → 进仓库 data/_generated/districts/provinces.geo.json（构建期生成一次）
③ 各省市级边界          → 构建期生成到 data/_generated/districts/{adcode}.geo.json
                          ★ 只生成「已收录城市所在省」的，其余按需拉 + localStorage 缓存
```

> 💡 **关键洞察**：既然只收录了四川，**就只需要预生成四川的市级边界**。其余 33 个省的边界等真正有内容时再生成 —— 避免为"待收录"的省浪费体积。

### 10.3 性能预算

| 指标 | 目标 |
|------|------|
| 全国图首屏（含省级边界） | ≤ 2.5s（4G） |
| 边界数据总量 | ≤ 500KB gzip |
| 层级切换动画 | 稳定 60fps |
| 区划树解析 | ≤ 10ms |

# 10 · 三级地图下钻（全国 → 省 → 市）

> **一句话**：默认打开就是中国地图，每个省标着「有多少个可玩的地方」；点进去看这个省里哪些市有内容；再点进去就是那座城市的点位图。
> **本质**：把「我该去哪玩」这个决策，拆成三次由粗到细的空间选择 —— 而不是让用户在一堆城市卡片里盲选。

---

## 一、Why：为什么要有下钻

### 1.1 它解决的是什么问题

原方案的首屏是「一张地图 + 10 个城市 marker + 左侧列表」。这在只有 10 个城市时可用，但有两个结构性缺陷：

| 问题 | 说明 |
|------|------|
| **不可扩展** | 城市涨到 100 个时，地图上 100 个点会糊成一片，列表变成无意义的滚动 |
| **缺少决策依据** | 用户看着"成都""西安"两个名字，不知道哪个更值得去、哪个内容更多。**他需要的是"这个省有没有内容、有多少"**，而不是一串地名 |

下钻把首屏从「城市清单」升级为「**内容分布图**」：哪个省内容多、哪个市值得点，一眼可见。

### 1.2 用户的实际决策路径

```
"我想出去玩，但不知道去哪" 
  → 看中国地图，哪个省内容多（四川 46 个，看着多）
  → 点进四川，成都 46 个、其余待收录
  → 点进成都，撒点图：46 个点按类型铺开
  → 挑几个点，进入行程规划
```

**每一步都比上一步更具体，且每一步都能退出重选** —— 这是它比"城市卡片网格"好的根本原因。

### 1.3 为什么不做成「城市列表页」

| 方案 | 问题 |
|------|------|
| 城市卡片网格 | 与「地图即画布」模型冲突（回到了"地图占一块"的分栏） |
| 全国城市列表 | 100 个城市的名词列表，用户读完还是不知道去哪 |
| **地图下钻** | ✅ 空间选择 + 数量信息 + 与现有布局模型一致 |

> 📌 **判定标准**：如果某个导航方案需要新增一个「非地图」的页面结构，它就不该做 —— 见 [05 文档](./05-ui-ux-design.md) 1.0 节的「地图即画布」硬规则。

## 二、层级模型与路由

### 2.1 三级模型

```
Level 1  中国全图        每个省级区划显示「N 个可玩的地方」
   │     /                34 个省级单位（含港澳台）
   │     点击某个省
   ▼
Level 2  省级地图        每个市级区划显示「N 个可玩的地方」
   │     /province/510000 该省的各地级市
   │     点击某个市
   ▼
Level 3  市级地图        撒点：该市的全部 POI，按细分类型配色
         /city/chengdu
```

### 2.1.1 分层与缩放的分工（2026-09-19 修订）

**修订前的写法**是「层级由路由决定，缩放只在层内决定给多少」。它的后果很具体：
**首页与省级页的缩放完全不起作用** —— 34 个省徽标、21 个市徽标在任何一个
缩放级别下一模一样，用户的原话是"地图缩放级别不同，显示不同的内容，这个你没做"。

**现在的分工**：

- **路由决定基准层级**（`base`）：`/` = 省、`/province/:adcode` = 市、`/city/:cityId` = 点
- **缩放决定往下揭示到哪一级**：同页放大 → 下一级的内容直接铺出来，**不换路由**
- **点地图上的东西也不换路由**（2026-09-23 定稿）：
  | 点的是 | 做什么 |
  |--------|--------|
  | 省 / 市**徽标** | **放大到对应的比例**（框住它的下级；见 `common/logic/districtFocus.ts`） |
  | 景点**图标 / 名字** | **就地打开完整详情** —— 桌面 620px 面板（**只有这一块**），移动端底部 Sheet |
  | 地图**空白** | 收起详情 |
  只有**清单里换页的行**（如省级页的 `pickCity`）才换页；**详情页只留给外链 / SEO / 分享**。

> ⚠️ 这一行原来写的是「点击徽标 / 圆点才换路由（进左侧清单与详情）」。它有两个毛病，
> 用户的原话：「点击地图的任何内容，url 都不需要出现变化……点对应的标签，
> 放大对应的比例就行了」：
> 1. **URL 一变，刷新就停在新页面上** —— 而省级页/城市页**没有回全国的出口**
>    （顶栏品牌名不是链接），于是"我点了四川，四川就固定死在地图上，怎么都关不掉"；
> 2. 换页把"我在哪一级"交给**路由**，屏幕上铺的内容却由**缩放**决定 —— 两套口径。
>    既然早就定了"揭示不换路由"，点击却换页是自相矛盾的。
> 3. 顺带：点徽标只是"想去那儿看看"，直接把人扔到另一个页面（还带一个左侧清单）
>    是过度反应；**放大**才是同一件事在地图上的自然表达。
>
> ⚠️⚠️ 然后这里又写偏了一次：把上面那句推广成「**点地图上的任何东西都只放大**」，
> 于是**景点**点击也去推镜头了。用户当场纠正：「点景点的标签和图标，不应该是打开景点详情吗，
> 怎么缩放地图了」。**徽标与景点的语义本来就不同**：
> · 徽标是"这一级有什么" → 点它就该看得更清（放大）；
> · 景点是"它是什么" → 点它就该看详情（**镜头不该动**，否则你想看的那一枚会被甩出屏幕）。
> 判据也因此在 `check_app.py` 的 Y⑤ 里**分成两段**分别守（写死键顺序，改结构会先报"需要同步"）。
>
> ⚠️⚠️⚠️ 第三次修正（2026-09-23 晚）：**"看详情"本身也不能跳转**。当时的做法是
> 点景点先浮一张 326px **预览卡**，卡上「看详情」再 `navigate('/city/:id/poi/:pid')` ——
> 用户：「现在点景点，右侧是会显示一个景点的简要信息，这个不需要，点击直接看详情就行，
> 点那个看详情，会触发跳转，这个跳转不需要，url 不需要有任何变化」。
> 于是：预览卡（`PoiCard` / `PoiPreviewCard`）**整体删除**，点景点直接浮出**同一份完整详情**
> （桌面 620px 一块面板 / 移动底部 Sheet）；清单里的「详情」也改成就地开（Y⑦ 守）。
> ★ 后来又收了一次（同一天深夜）：桌面那块独立的 300px 位置卡也删了 ——「位置与交通」
>   砌进 `PoiDetail` 正文末尾，**整页只剩一块浮层**（用户：「右侧那个简要信息不需要」）。
>   判据 **Y⑧**：`PoiDetailOverlay` 的 `<Overlay` 必须恰好 1 个 + 全仓不得引用已删 token。
> 详情**页**继续存在，但它只服务外链 / SEO / 分享 —— **点击不再进入它**。



| 视图 | `base` | 放大后依次揭示 |
|------|--------|----------------|
| 全国 `/` | `province` | ≥6.5 视野内各省的**市徽标**；≥9.5 视野内已收录市的**点位圆点** |
| 省级 `/province/:adcode` | `city` | ≥9.5 该省已收录市的**点位圆点** |
| 城市 `/city/:cityId` | `poi` | 无（已在最深层）—— 缩放只改圆点与名字的密度 |

#### 为什么不与路由打架了

当初拒绝语义缩放的理由是"两套导航同时存在，'我在哪一级'就没有唯一答案"。
但那个问题的答案是**路由与顶栏的地区选择器**，而揭示是**单向的**：只会比 `base` 更深，
**永远不退浅**。首页再怎么放大也仍是"全国视图"，地区按钮写「全国」是**准确的**
—— 这一页就是全国图，放大只是看得更细，并没有走进去。

真正会打架的是"缩小自动回到上一级"。**那个不做**：往回走靠顶栏地区选择器或浏览器后退。
把"我只是想把地图拉远看一眼"变成一次不可预期的导航，比层级标签重复糟得多。

#### 阈值（唯一出处 `web/app/map/tencent/zoomTiers.ts`）

| 常量 | 值 | 依据（实测 `fit()` 后的缩放，容器 1418×802） |
|------|----|------------------------------|
| `CITY_REVEAL_ZOOM` | **6.5** | 首页 4.39 < 6.5 < 省级 7.26 |
| `POI_REVEAL_ZOOM` | **9.5** | 省级 7.26 < 9.5 < 城市 11.02 |

★ 阈值必须**严格大于上一级的 `fit` 缩放**，否则页面一打开就自动触发揭示，
等于阈值失效。

★ **别去追这三个 `fit` 数的绝对值** —— `fitBounds` 按容器尺寸反算缩放，
窗口矮一截数就跟着变（1440×900 的窗口里量到的是 4.57 / 7.44 / 11.21）。
要守的是**相邻两级的大小关系**：阈值落在相邻两级之间、且相邻两级之间隔着 2 以上，
容器尺寸怎么变都不至于越界。改标定前跑 `_tmp/cdp_loop.mjs` 重量一遍。

★ **退回规则（2026-09-20 变成"每一级都试"；2026-09-29 收窄成"只有徽标级才回流"）**：
揭示到某一级、但该视野内**没有内容**时，**退回上一级**继续铺徽标。
"这里没内容"和"这里没做"是两回事，不能摆一张空地图。

修复前这条规则只实现了一半 —— 只有 点位 → 市徽标 那一段有回流，
而且判据是"缩放到 6.5 就该铺市徽标"（只看缩放、不看内容）。判定与回流收在
`web/app/map/tencent/reveal.ts` 的 `decideReveal()`：**从最深的候选级往回走，
第一个"视野里够看"的层级才是答案**，并且带一份 `trace`（每一级的视野内候选数、
有没有被采用）供探针直接读出来。

★★ **但 `poi` 这一级不回流**（2026-09-29。用户："我点那个区，放大到区级了，
**我再怎么放大这个标签都不会消失，一直显示**"）：点位是**最细的一级，它没有退路**
—— 退回去拿到的是**尺度完全不对的徽标**。实测站在 z=16（街道尺度）、视野落在一片
没有收录景点的山坡上时，旧规则一路退回**市级**，屏幕上冒出一枚「成都 57」。
它钉在成都市中心、**离用户正在看的地方几十公里**，却一直挂在屏幕上不走；
而且放大越深视野越窄、越容易"没有点位" ⇒ **越是一直不走**。

代价还是双份的：回流要走 `districtLayer.setNodes()` —— 重建多边形几何（含边界解码）
+ 重算徽标避让。**放大过程中反复回流 = 反复重建**，那正是同一轮用户报的
「地图渲染怎么变得好慢」。
⇒ 深处没有点位是**正常事实**（这一片就是没收录景点），如实铺空即可；
返回的 `districts: []` 顺手把上（几）级的徽标清干净。

★ **「未就绪」不是「没有」**：`pois(level)` 返回 `null` = 数据还没加载（乐观通过 +
**只按住点位层**），返回 `[]` = 确定没有（**不退**，如实铺空）。
两者写成一样，懒加载与回流就会互相锁死（不铺就不加载、不加载就永远判空）。

★★ **`pending` 只许挡住点位层**（2026-09-29 修）：它原先"**整天跳过**"（连上层徽标
一起按住），理由是"数据马上到、先清会闪一帧白"。那理由只在**数据马上到**时成立 ——
首页放大到景点级要读**全部收录城市**的点位（17 座，实测 4s+），这段时间里屏幕上
一直是那 20 个区徽标（在街道尺度上看到区徽标，正是上面那条抱怨）。

⇒ 两处一起改：`pending` 时**上层照常按决策同步**（`districts: []` ⇒ 清掉），
只把点位同步挡住；点位的懒加载改成**分批** —— `common/logic/preloadCities.ts`
按"离地图中心多远"排序，先读最近的两座城（页面立刻铺一次）、其余随后补齐，
最终状态与"一次全读"完全一致。首页那段空窗实测 **4s+ → 0.8s**，缩放期间的
主线程长任务（97~113ms）也随之消失。

护栏 = **AK**（3 条判据），反证 `_tmp/falsify_ak.py`（3 个变异）；行为面
`_tmp/cdp_mapdiag.mjs`（首页 / 省级页 / 城市页三页都跑，量的是"从放大到点位真的到场"）。

★★ **判据必须看「内容自己」**（这条踩过坑，别改回去）：
- 点位级成立 = **视野里有「点位本身」**，判据取**严格视野**（`pad = 0`）
- ⛔ 曾经写成「**所属城市的中心点**在不在视野里」。缩放越大，同一段地理偏移
  换算成的像素越多 —— 于是放大到都江堰（在成都市域内、离市中心约 50km）时
  市中心移出屏幕 → 判据判空 → **连点位带徽标一起消失**。用户的原话是
  "地图放大到一定级别，连热门景点也不显示了"。中心点是**一个点**，而放大是
  **按像素**算距离的，这个判据随缩放单方向崩塌。

**撒点范围**（回答"是只撒屏幕上的，还是一起全撒"）：

| 层 | 范围 | 为什么 |
|----|------|--------|
| 区划徽标 | 视野 **外扩 1 倍** → 再交由图层做像素避让与视口剔除 | 放大后市徽标的中心常常在屏幕外而市域还在屏上；外扩一圈不至于"贴着边就消失" |
| 点位圆点 | 视野 **外扩 0.6 倍** | 屏幕外的几何只有开销没有收益（三城 138 个，将来几百城就是上万）；外扩一点则要平移两屏才重算一次集合，不会忽现忽隐 |
| **判据** | **严格视野（pad = 0）** | 判据必须比上屏集合**更严**：若判据也用 0.6，会出现"判据说有点、屏幕上却一个都没有"—— 点在屏外 60% 以内、而文字避让只认屏内，于是整屏空白 |

**圆点的空间闸门**（回答"撒点会不会堆在一块"）：

| 闸门 | 判据 | 只管住什么 |
|------|------|-----------|
| ① 总量 | `zoomTiers.poiTierForZoom(z).dots`，超出按热度取前 N | "数量不多" |
| ② **空间** | **屏幕像素**距离 < `MIN_DOT_GAP_PX` 的两枚，只留更热的那枚（`poiLayer.pickDots`） | "互不重合" |

★ **两道都要**。只有 ① 的话：`zoom ≥ 11` 的档位语义是"不再按数量截断"，
而**热门点位在地理上是聚簇的**（成都热度前 20 里有十几个落在市区 3km 内）——
46 枚 8px 圆点会在屏幕上叠成一坨。用户的原话：
「撒点不是这样撒的，这样会出现全堆在一块」。

★ 判据取**屏幕像素**而不是地理距离：同一个 2km 间距，z9 时两点叠着、z15 时隔几百像素。
按地理距离定阈值就得随缩放改阈值，而按像素定义是**一次性**的 ——
顺带把"放大自动露出更多点"也做掉了，不必再为它调档位。

★ 贪心顺序 = **屏内优先 → 热度降序 → id 兜底**：屏外的点不该挤掉用户正看着的点；
热度相同时结果必须可复现（否则缩放时点位忽闪）。**选中的点先占位**，让邻点给它让路。

★ **实现**：`web/app/hooks/useMapReveal.ts` —— 两个图层归它独占，
页面只提供 `districts(level)` / `pois(level)` 两个**纯数据源**函数
（只吃层级、**不吃视野** —— 页面上再筛一次就会与钩子的判据分叉）。
各页各写一遍会让"只在内容真的变了才重铺"这条判断分叉：一边写了签名比对、
另一边没写，就会在缩放过程中反复重建几何，表现为徽标闪烁。

#### 城市页的圆点分档（同一张表）

文档只记纪律：① 圆点上限恒 ≥ 名字上限（名字是点位的注解，注解比本体多没意义）；
② 任何档位都必须保证 `fit()` 之后有东西可看 —— 早期阈值写成"低缩放给 0"，
恰好把移动端 `fit` 之后的缩放（≈9.7）判成 0，于是"一个名字都不显示"，
而页面看起来一切正常。③ 揭示出来的点位**共用同一张分档表** ——
同一个缩放下"该给多少个圆点"只有一个答案，不该因为从哪一页进来而不同。
④ `dots: Infinity` 的语义是"**这一档不再按数量截断**"，不是"46 个全都会画出来" ——
实际上屏数还要过空间闸门，实测成都 `z11.02` 是 **21 枚**（不是 46）。
⑤ **移动端与桌面端先过同一份预算**（`dotBudget.pickDots`），只是画法不同
（桌面 `MultiMarker` + `MultiLabel`，移动 `MarkerCluster`）。修复前移动端
`repaint()` 首行就因 `cluster` 返回，整条分档链路一次都没跑。

★ 撒点的三道闸门**顺序不能换**：投影 → **网格抽稀** → 总量闸门 → 像素去重。
修复前是"先按热度取前 N、再像素去重"，而**热门点位在地理上是聚簇的**
（成都热度前 20 有十几个落在市区 3km 内）—— 前 N 名全落在同一片，
去重后 8 枚只剩 1~2 枚，低缩放的圆点等于没撒。先抽稀再截断，
取到的 N 枚天然落在不同格子里。实测城市页 `z8.6 → 5 枚`、`z9.6 → 11 枚`、
`z10.5 → 16 枚`、`z12.5 → 32 枚`（单调增，而不是一两枚）。

### 2.2 路由设计

| 层级 | 路由 | 说明 |
|------|------|------|
| 全国 | `/` | 首页即全国图 |
| 省级 | `/province/:adcode` | 如 `/province/510000`（四川省）。**用 adcode 而非拼音** —— 省是纯区划概念，没有对应的城市数据文件 |
| 市级 | `/city/:cityId` | 如 `/city/chengdu`。**沿用现有 slug** —— 与 `data/cities/{id}.json` 一一对应，且 SEO 友好 |
| 详情 | `/city/:cityId/poi/:poiId` | 不变 |
| 行程 | `/city/:cityId/plan` | 不变 |

**为什么两级用不同的键**：

- 省级用 `adcode`：省没有独立的数据文件，它只是区划树上的一个节点
- 市级用 `slug`：城市有独立数据文件（`chengdu.json`），slug 是可读的、SEO 友好的

**关联键**：城市数据文件里的 `adcode` 字段（如 `"510100"`）把两者接起来：

```jsonc
// data/cities/chengdu.json
{
  "id": "chengdu",
  "adcode": "510100",      // ★ 与区划树的关联键
  "provinceAdcode": "510000",
  "name": "成都",
  ...
}
```

### 2.3 路由与 SEO

**每一级都要预渲染独立 HTML**（这与现有 SSG 策略一致）：

```
dist/
├─ index.html                              中国全图（含各省计数，可被搜到）
├─ province/510000/index.html              四川省页
├─ city/chengdu/index.html                 成都页
└─ city/chengdu/poi/xxx/index.html         点位详情
```

省级页的 `<title>` 形如「四川旅游攻略 · 21 个市 · 46 个可玩的地方」—— 这类"数量 + 地名"的长尾词是真实搜索需求。

### 2.4 前进 / 返回的状态管理

| 动作 | 行为 |
|------|------|
| 点省边界 | `push` 到 `/province/:adcode`，地图 `fitBounds` 到该省范围 |
| 点市边界 | `push` 到 `/city/:cityId`，地图 `fitBounds` 到该市点位 |
| 浏览器后退 | 回到上一级，**恢复上一级的视野与浮层状态**（不是重新初始化） |
| 地区选择器选任意一级 | 同上 —— 但**可以跨级**（在城市页直接选「全国」就是两级一起退），不等同于"后退一步" |
| `ESC` 键 | 返回上一级（桌面端） |
| 移动端右滑 | 返回上一级（见第八节） |

> ⚠️ **「恢复上一级视野」不是自动的**。浏览器后退只恢复 URL，地图实例是同一个、视野停在下钻前的状态。需要把每级的视野存进 `history.state`，`popstate` 时读回来重新 `fitBounds`。**这是最容易做漏的一处** —— 漏了的话用户后退会看到"URL 变了但地图没动"。

## 三、数据源：腾讯 District 服务

### 3.1 三个接口

```
GET https://apis.map.qq.com/ws/district/v1/list
    → 全国省 / 市 / 区县三级完整列表（不含边界，体积小）

GET https://apis.map.qq.com/ws/district/v1/getchildren?id=510000&get_polygon=1
    → 指定区划的子级 + 边界点串

GET https://apis.map.qq.com/ws/district/v1/search?keyword=成都&get_polygon=1
    → 关键词匹配单个区划 + 边界
```

**JS API 侧封装**：`TMap.service.District`，配 `POLICY_CONTAIN_CHILDREN` 可一次拿到子级。

### 3.2 返回结构

| 字段 | 说明 | 我们的用法 |
|------|------|-----------|
| `id` | adcode（6 位） | 路由键、关联键 |
| `name` / `fullname` | 简称 / 全称 | 简称用于地图标注（"内蒙古"），全称用于 SEO |
| **`location`** | **中心点经纬度** | ★ **"各省/市有多少个"的标注锚点** —— API 直接给了，**不需要自己算多边形质心** |
| `level` | 几级区划 | 校验层级对不对 |
| `polygon` | 轮廓面点串 | 绘制边界（需 `get_polygon=1`） |
| `cidx` | 子级在下级数组中的下标 | 构建树结构用 |

> 💡 **`location` 中心点是这个接口最省事的地方**。自己算多边形质心会遇到"环状区域质心落在空洞里""狭长地形质心跑到边界外"的问题（比如甘肃），官方给的中心点是经过处理的可用点。

### 3.3 adcode 规则与特例（必须处理，否则下钻会崩）

```
格式：6 位数字    前 2 位 = 省    中 2 位 = 市 / 地区    后 2 位 = 区县

130000  河北省
130600  河北省保定市
130681  河北省保定市涿州市
```

**四个必须写进代码的特例**：

| # | 特例 | 处理 |
|---|------|------|
| 1 | **直辖市**（北京 110000 / 上海 310000 / 天津 120000 / 重庆 500000）**与港澳**（810000 / 820000） | 省级下**直接是区级**，没有二级结构。下钻时若发现 `children` 的第一项是区级，**不报错**，直接展示（用户点"北京"看到各区的计数） |
| 2 | **省直辖县**：第 3、4 位为 `90`（如 419001 济源市） | 视同地级市处理（作为直辖县单独列出） |
| 3 | **中国范围内非行政区划区域**：`999999`（如东海） | **过滤掉**，不入树，不显示 |
| 4 | **台湾省 / 香港 / 澳门** | **必须作为省级单位正常出现在全国图上**（710000 / 810000 / 820000）。见第九节合规红线 |

### 3.4 边界数据的参数（含待核实项）

从腾讯官方示例里看到的参数组合：

```
/ws/district/v1/getchildren?key=...&get_polygon=2&max_offset=3000
```

| 参数 | 观察到的取值 | 状态 |
|------|------------|------|
| `get_polygon` | 文档写 `1` = 返回轮廓；官方 demo 用了 `2` | ⚠️ **待核实**：`2` 是否表示"简化轮廓"。见第十一节 T3 |
| `max_offset` | demo 用 `3000` | ⚠️ **待核实**：推测是轮廓简化的容差（米）。越大越简化、体积越小。见 T4 |

> **这两个参数直接决定边界数据的体积**，而体积决定首屏能不能秒开（全国 34 个省级边界）。**必须在 M1 阶段实测确定**，不能照抄 demo。

## 四、区划树与聚合索引

### 4.1 为什么要在构建期做

区划树 + 计数是**纯静态数据**，与用户无关 —— 完全可以在构建期算好固化进仓库，运行时零 API 调用（除非用户下钻到没缓存的省）。

这保住了本项目的核心架构前提：**运行时纯前端**。

### 4.2 聚合索引的结构

```jsonc
// data/_generated/district-tree.json
// ★ 全部脚本生成，禁止手改
{
  "version": "20260101",            // District 数据的 data_version
  "generatedAt": "2026-09-17",
  "provinces": [
    {
      "adcode": "510000",
      "name": "四川",
      "fullname": "四川省",
      "center": { "lng": 104.075931, "lat": 30.651652 },   // ★ 直接用 API 的 location
      "poiCount": 46,                // 该省已收录 POI 总数
      "cityCount": 1,                // 已收录城市数
      "childCount": 21,              // 下辖地级市数（来自区划树）
      "children": [
        {
          "adcode": "510100",
          "name": "成都",
          "center": { "lng": 104.0665, "lat": 30.5723 },
          "cityId": "chengdu",       // ★ 有数据 → 指向城市文件
          "poiCount": 46
        },
        {
          "adcode": "510300",
          "name": "自贡",
          "center": { "lng": 104.7784, "lat": 29.3392 },
          "cityId": null,            // ★ 无数据 → null，UI 显示"待收录"
          "poiCount": 0
        }
      ]
    }
  ]
}
```

**关键字段语义**：

| 字段 | 语义 | 空态判定 |
|------|------|---------|
| `cityId` | 是否已收录这座城市 | `null` = 待收录 |
| `poiCount` | **仅统计已收录的 POI** | — |
| `childCount` | 区划树上的下辖数量（与内容无关） | — |

> ⚠️ **`childCount` 与 `cityCount` 必须分开**。四川下辖 21 个地级市（`childCount`），但只有 1 个已收录（`cityCount`）。UI 上要表达的是「**已收录 1 / 共 21 个市**」—— 让用户知道这是进度问题，不是内容问题。

### 4.3 计数口径

用户说的是「有多少个**景点**」，但我们的数据有四类内容（景点/美食/网红/特色）。定义：

- **默认口径**：全部 POI 总数
- **可切换口径**：按四大类筛选后重新计数（如只看"景点"）

UI 文案统一用「**可玩的地方**」而不是"景点"，因为它涵盖了美食与打卡点：

```
四川
46 个可玩的地方 · 已收录 1/21 个市
```

## 五、地图侧实现

### 5.1 边界图层

```ts
// app/map/tencent/districtLayer.ts
const layer = new TMap.MultiPolygon({ map, styles: DISTRICT_STYLES, geometries: [] })
```

**填色按 `poiCount` 分四档** —— 让全国图一眼能看出内容密度：

| 档位 | `poiCount` | 填充 | 描边 |
|------|-----------|------|------|
| **待收录** | 0 | 极浅灰 `rgba(136,135,128,0.06)` | 灰**虚线** |
| 稀疏 | 1–20 | 浅蓝 | 蓝实线 |
| 中等 | 21–60 | 中蓝 | 蓝实线 |
| 密集 | 61+ | 较深蓝 | 深蓝实线 |

### 5.2 计数徽标

在每个区划的 `center` 上挂一个徽标（`MultiLabel` 或自定义 marker）：

```
        ┌──────────┐
        │  四川     │
        │ 46 个     │
        └──────────┘
```

- 待收录的区划：徽标显示「待收录」，且用**弱化样式**（浅灰底、灰字）
- 徽标可点击（等同于点边界）
- ⚠️ **徽标与边界多边形都要能点** —— 小省份（如上海）的多边形可能很小，只靠多边形命中率低。徽标提供了一个"最小点击面积"的兜底

### 5.3 层级切换的过渡

```ts
// 下钻：把视野框到目标区划的边界范围
map.fitBounds(provinceBounds, { padding: freeRectToPadding(), duration: 600 })
```

**过渡要给出方向感**：

| 动作 | 动画 |
|------|------|
| 下钻（全国 → 省） | 目标省放大充满视野；其他省淡出到 0.3 不透明度 |
| 返回（省 → 全国） | 反向：本省缩回原位，其他省恢复 |

> ⚠️ **不要做"渐变替换"（旧层淡出 + 新层淡入同时进行）** —— 中间会有一段两层都半透明的混沌期，看起来像渲染错误。正确做法：**旧层保持可见，新层直接铺上，然后旧层淡出**。

## 六、空态设计（本轮最重要的体验决策）

### 6.1 问题

用户选了「**先跑通链路**」—— 架构按全国 34 省设计，但首批只有四川（成都）有数据。这意味着：

```
全国图上 34 个省级区划 → 1 个有数据，33 个是 0
```

**首屏怎么设计，决定了这个项目看起来是"刚起步"还是"很空"。**

### 6.2 四种处理方式的取舍

| 做法 | 判定 |
|------|------|
| ❌ 显示「0 个景点」 | **信息是错的** —— 用户会以为"这地方没景点"，而事实是"我们还没收录" |
| ❌ 完全不画这些省 | 中国地图出现空洞 → **触发版图完整性问题**（见第九节） |
| ❌ 和其他省一样的实色 | 用户点进去发现没数据 → 挫败 |
| ✅ **灰色 + 虚线描边 + 「待收录」** | 边界完整可见（合规），视觉上明确表达"未完成"，点击有导流 |

### 6.3 空态的视觉语言

```
待收录省份：
  填充  rgba(136,135,128,0.06)    ← 极低透明度，几乎只剩轮廓
  描边  #B4B2A9  虚线 [4,3]        ← ★ 虚线是关键：表达"未完成/规划中"
  徽标  「待收录」  浅灰底 + 灰字

有数据省份：
  填充  蓝色梯度（按 poiCount 分档）
  描边  蓝色实线
  徽标  「N 个」  白底 + 深字
```

**为什么虚线是对的**：虚线在中国地图语境里天然表达"未完成/规划中"，且**不破坏版图完整性** —— 边界依然清晰可见，只是用线型区分了状态。

### 6.4 点击待收录省份不能给死路

```
┌─────────────────────────────────┐
│  甘肃 · 待收录                   │
│                                 │
│  我们正在陆续补充全国城市。       │
│  先看看已上线的成都？             │
│                                 │
│  [ 去看成都 ]      [ 知道了 ]    │
└─────────────────────────────────┘
```

**三个设计点**：

1. **不跳转，只弹卡片** —— 不把用户扔到一个空页面
2. **把空态变成导流** —— "先看看已上线的成都" 直接把流量导向有内容的地方
3. **文案要诚实** —— "我们正在陆续补充"，而不是假装"暂无数据"

> 💡 **这个空态设计是「先跑通链路」这个决策能成立的前提。** 没有它，首屏 33 个灰省份会显得项目很空；有了它，"待收录"反而变成了**进度感**的表达 —— 用户能看到这个项目在长大，而不是"做了一半"。

### 6.5 省级页的空态

四川页有 21 个地级市，20 个待收录。处理同上，但要额外给一行汇总：

```
四川 · 已收录 1 / 21 个市
[成都 46] [自贡 待收录] [攀枝花 待收录] ...
```

## 九、合规红线（本章最重要）

### 9.1 🚨 边界数据只能来自**持牌图商 / 官方平台**

> **行政区划边界（省 / 市 / 区三级）只能使用持牌图商或官方平台返回的数据：**
> **腾讯 / 高德 / 百度 / 天地图**（自然资源部标准地图服务亦可）。
> **绝对禁止**：
> - 引入任何第三方 GeoJSON（哪怕看起来很权威）
> - 使用 Wikipedia / Natural Earth / GADM / geoBoundaries / 各类开源数据集的中国边界

**为什么这条是红线**：中国地图的行政区划边界涉及**国家版图完整性**，具体包括：

| 敏感区域 | 常见错误 |
|---------|---------|
| **台湾省** | 第三方数据常把它单独成"国家"或缺失 |
| **藏南地区** | 第三方数据常按错误的实控线绘制 |
| **南海诸岛** | 第三方数据常完全缺失，或未按九段线表达 |
| **阿克赛钦** | 第三方数据常有偏差 |

这类错误**违反《地图管理条例》**，且在开源项目中极其常见（因为大量开源 GeoJSON 来自境外数据源）。

**红线的实质是"数据必须过审图"，不是"必须是腾讯"** —— 上表四家都是持牌图商 / 官方平台，
数据都过了审图，所以换源不破这条线。

#### ★ 现阶段的实际取数分工（2026-10-02 已全部落地）

| 层级 | 来源 | 为什么 |
|------|------|--------|
| **区（自身轮廓）** | **高德** `config/district?subdistrict=0&extensions=all`（按市打包） | 腾讯给下辖区的轮廓**极度抽稀**：北京 16 个区里 4 个只有 **4 个点**（一个矩形）、西安莲湖区 **5 点**、雁塔区 15 点 —— 而区面从 `z=9.5` 一直画到点位档（`z≥12`）⇒ 满屏方块（用户 2026-10-02：「这个区的轮廓，怎么方方正正的，这轮廓数据不对吧」）。高德给的是该区**自身**的全精度轮廓（莲湖 556 点 / 雁塔 1042 点） |
| **市** | **高德** `config/district?subdistrict=0&extensions=all`（按省打包） | 腾讯那份只对"已收录城市所在的省"生成过（实测 **20/34** 份）⇒ 市这一级半个国家没有面；且它是各自独立抽稀的粗轮廓（点距几公里 ⇒ `z≈9.5` 时几十像素的硬折角） |
| **省（自身轮廓）** | **高德** `config/district?subdistrict=0&extensions=all` | 腾讯**没有**"某个行政区自身轮廓"的接口（`getchildren` 只给下辖子级、`search` 不带 polygon、`/boundary` 不存在、`id=100000` 返 0 个节点），只能"用各市拼"，而拼出来会把省内市界一起描出来 |

（腾讯那份 `districts/<键>.geo.json` **保留**：它是**逐级兜底** —— 区这一级逐区退回、
市这一级整份退回。抓取是分批做的（高德月配额），所以"抓到一半"必须仍然能用。）

生成方式：
· **省**：`python pipeline/run.py outline` → `data/_generated/provinces/<省adcode>.geo.json`
· **市**：`python pipeline/run.py cities`  → `data/_generated/cities/<省adcode>.geo.json`（按省打包）
· **区**：`python pipeline/run.py district-outline` → `data/_generated/districts-own/<市adcode>.geo.json`
  （键 = 市 adcode；**直辖市/特区 = 省码**，它们没有中间市层）
（**构建期抓一次，运行时零 key 零请求**；三份都可断点续跑，`--only=` / `--limit=` 分批抓。）
★★ **都要抓全**：省级抓**全部 34 个省级单位**（含中国台湾 / 中国香港 / 中国澳门），
市级抓**全部 493 个市级节点**，不是"只抓有收录城市的省"—— 第一版那么干过，
结果图上一半的省/市没有面（用户 2026-09-30：「轮廓数据好像没抓全，只有部分省的部分区是全的」）。
未收录的省/市自然走**「待收录」灰虚线**（`districtStyles` 的 `pending` 档），
这本来就是 §6.3 的视觉语言；顺带把 §9.2「全国图必须包含 34 个省级单位」
从"靠底图"变成"我们自己也有轮廓"。
前端 `bounds.ts` 的 `loadProvinceFaces()` / `loadCityOwnBounds()` **先试自身轮廓、
缺谁退回上一版来源**（省退回"各市拼"、市退回腾讯的 `districts/`）；
区这一级走**唯一入口 `loadDistrictFaces()`**，它是**逐区**合并
（`{...腾讯那份, ...高德那份}`）—— 所以"只抓到一半"时，已抓到的区用精确轮廓、
其余的仍用腾讯的粗轮廓，**不会整片没有面**。
★ 读那三份"自身轮廓"的代码在 `data/ownBounds.ts`（2026-10-02 从 `bounds.ts` 拆出，撞了 420 行）。

##### 五条实施细节（都是踩出来的）

1. **必须抽稀 + 降精度**，而且**容差要按"这一级最深的显示档"算**：
   · 省的面只在 `z<6.5` 渲染（`1px≈1416m`）⇒ `SIMPLIFY_TOL_M=600` 是 **0.42px**；
   · 市的面在 `z<9.5` 渲染（`1px≈177m`）⇒ `SIMPLIFY_TOL_M=100` 是 **0.56px**；
   · 区的面一直画到**点位档**（`z≥12`，`1px≈31.7m`）⇒ `SIMPLIFY_TOL_M=30` 是 **0.95px**
     （实测体积：莲湖 2.4KB / 雁塔 5.7KB / 北京朝阳 9.9KB）。
   ⇒ **三级的容差不能共用**（省 600m 放到区那一级就是 19px，一眼假）。
   降精度同理：省 4 位小数（≈11m）、市/区 5 位（≈1.1m）。
   不做任何处理时：省 34 个单位 ~14MB、市 493 个节点更大 —— 而首页一进来就要拉它们。
   （§9.3 的"不得简化到失真"守的就是"看得出来"这条线。）
2. **位置自检要用 bbox 重合系数，不能用中心距离、也不能用 IoU**：
   · 中心距离被**离岛**骗过 —— 高德的海南含南海诸岛（纬度下探到 3.84°），
     两边中心差 0.49°，但显然是同一个省；
   · IoU 被**参考值自己的坏环**骗过 —— 腾讯 `districts/120000.geo.json`（天津）里有个
     438km 外（邢台）的成员（腾讯偶发，见 TRAPS"坏环"），把参考框撑大 ⇒ IoU 只有 **0.14**
     （而高德的框**完整落在里面**，重合系数 = 1.00）；
   · `inter / min(面积) ≥ 0.7` 对两者都免疫，而"拿错行政区"时 ≈ 0，照样拦得住。
3. **面积对照只能当参考**：腾讯那份的"各市/各区之和"本身是**各自独立抽稀**的粗多边形，
   直辖市与特区尤其粗（`districts/110000.geo.json` 里每个区只有 4~28 个点）。
   实测：香港"18 个区之和"约 **2200km²**（真值 ~1114km²）、澳门那份差 **-44%**
   —— **参考值自己就是错的**。所以面积只打 ✓/⚠/✗ 三级提示，**位置**才是硬判据（超限**不写盘**）。
4. **7 个「自身就是市这一级」的省级单位**（北京 / 天津 / 上海 / 重庆 / 中国台湾 /
   中国香港 / 中国澳门）**不发请求** —— 它们的轮廓 == 省自身轮廓，
   `step10` 直接从 `provinces/` 抄。原来在市这一级对它取 `districts/<直辖市adcode>.geo.json`
   （key 是**区**），与节点 adcode 对不上 ⇒ 这几格在市这一级压根没有面。
5. **腾讯对"街道级"不给边界**：全国有 **38 个城市**的下一级是街道（东莞 / 中山 / 儋州 /
   济源 / 仙桃…这些**不设区**的市），它们的 `subdistricts/<市adcode>.json` 里挂着 9 位码
   的街道节点，而 `districts/<市adcode>.geo.json` 里没有对应几何。
   **已收录城市里 0 个**受影响，所以界面上看不到 —— 但将来若收录这类城市，得先想清楚
   这一级的徽标怎么表达。

#### ★★ 坐标系：这一格比"合规"更容易出事

| 来源 | 坐标系 | 与腾讯底图的关系 |
|------|--------|-----------------|
| 腾讯（底图 / District / 我们的 POI） | **GCJ-02** | 基准 |
| 高德 | **GCJ-02** | **同系 ⇒ 零转换，可直接叠** |
| 百度 | BD-09 | 要转 |
| 天地图 | **CGCS2000（≈WGS-84）** | 要 WGS84→GCJ-02 |

偏移量级 **50~500m**。按缩放算：`z≈4.4`（省档，分辨率 ≈6.4km/px）是 **0.008~0.08px**，看不见；
而 `z=12`（区 / 点位档，≈38m/px）是 **1.3~13px**，一眼假。

⇒ **换源只用得在"省"这一级**；市 / 区 / 点位必须继续用腾讯（同级、同源、同坐标系，
而且 POI 圆点也是 GCJ-02，换源会让点位与边界整体错开）。
这也是选**高德**而不是天地图的原因：省掉一整套坐标转换，以及转换本身引入的误差。

**验收**：`check_app.py` 的 **AC⑥** —— ① 高德请求必须带 `subdistrict=0` + `extensions=all`
（这就是"要自身轮廓"的契约）；② `amap.py` 里出现的**所有 URL 主机名**必须在
`ALLOWED_BOUNDARY_HOSTS` 白名单内；③ 省这一级必须"先试自身轮廓、缺了才退回拼接"。
反证见 `_tmp/falsify_ac.py`（12 个变异全被拦住）。

## 十、性能

### 10.1 边界数据的体积控制

**这是本方案最大的性能风险**。全国 34 个省级边界，如果每个用全精度轮廓，总量可能达到数 MB。

| 数据 | 体积估算 | 策略 |
|------|---------|------|
| 全国省级边界（34 个） | 未知，**待实测**（见 T3/T4） | 若 > 300KB，用 `max_offset` 提高简化容差；或按需加载（先画简化版，放大后补精度） |
| 单省市级边界（约 21 个） | 约为省级的 1/5 | 按需拉取 + 缓存 |
| 区划树（无边界） | **< 50KB** | 直接内联进首屏 bundle |

### 10.2 缓存策略

```
① 区划树（无边界）      → 进仓库 data/_generated/district-tree.json，随构建打包
② 全国省级边界          → 进仓库 data/_generated/districts/provinces.geo.json（构建期生成一次）
③ 各省市级边界          → 构建期生成到 data/_generated/districts/{adcode}.geo.json
                          ★ 只生成「已收录城市所在省」的，其余按需拉 + localStorage 缓存
```

> 💡 **关键洞察**：既然只收录了四川，**就只需要预生成四川的市级边界**。其余 33 个省的边界等真正有内容时再生成 —— 避免为"待收录"的省浪费体积。

### 10.3 性能预算

| 指标 | 目标 |
|------|------|
| 全国图首屏（含省级边界） | ≤ 2.5s（4G） |
| 边界数据总量 | ≤ 500KB gzip |
| 层级切换动画 | 稳定 60fps |
| 区划树解析 | ≤ 10ms |

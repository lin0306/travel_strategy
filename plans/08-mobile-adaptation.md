# 08 · 双端适配设计（移动优先）

> **定位声明**：本项目**以移动端为主场景**，桌面端为增强。这不是"再补个响应式"，而是**布局骨架、交互模型、性能预算三件事都要按移动端重新定**。
> 结论先行：全站采用 **地图即画布（Map as Canvas）** —— 地图铺满 100% 视口，所有 UI 都是浮在地图之上的浮层。移动端浮层形态为「顶部胶囊 + 底部 Sheet 三档吸附」，桌面端为「悬浮卡片」。早期"吸顶 40vh 地图 + 下方列表"与"地图左 60% / 列表右 40%"两种方案均已否决。下面第 2、3 节说清为什么。

## 一、前提与目标

| 前提 | 依据 | 对设计的约束 |
|------|------|-------------|
| 主力是移动端浏览器 | 主人明确"大部分可能是用移动端去访问"；国内移动端搜索流量占比已超七成（百度搜索资源平台口径） | 默认样式写移动端，媒体查询**向上增强**（`min-width`），不是向下兼容 |
| 主要在国内访问 | 用户在深圳，内容为国内城市 | 图源必须国内可达（见 04）；**托管平台要单独评估，见第七节** |
| 传播路径含微信 | 旅游攻略天然在微信聊天/朋友圈里流转 | 微信内置浏览器是必测端，且分享卡片要单独优化（见第六节） |
| 内容是"边看边去" | 用户在手机上大概率是**现场决策**：附近有什么、怎么走 | 就近排序、定位按钮是一等公民（但**不上传位置**，见第九节） |

### 设计目标（可验收）

1. **同一条 URL、同一份代码**适配两端，不做 `m.` 独立站（百度官方推荐响应式，单 URL 抓取效率最高）
2. 手机竖屏（≤ 640px）下**地图是主视图**，不缩成页内小挂件
3. 全站触控目标 ≥ 44×44 CSS px，正文 ≥ 16px
4. 移动端 4G 下 LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1
5. 微信内置浏览器（iOS + Android）打开无功能缺失

## 二、断点与布局骨架

### 2.1 断点表（Tailwind 4 默认档位，够用不改）

| 档 | 宽度 | 典型设备 | 浮层布局（底层永远是全屏地图） |
|----|------|---------|------|
| **S**（默认，无前缀） | < 640px | **手机竖屏 —— 主力场景** | 地图铺满 `100svh`；顶部一行悬浮胶囊；内容 = 底部 Sheet 三档吸附 |
| M | 640–1023px | 大屏手机横屏 / 平板竖屏 | 地图铺满；左面板 `320px` 悬浮；Sheet 退化为定高悬浮面板（**同一套组件，换容器模式**） |
| L | 1024–1439px | 笔记本 | 地图铺满；左面板 `348px` + 右预览卡 `300px` |
| XL | ≥ 1440px | 桌面大屏 | 地图铺满；左面板 `348px` + 右预览卡 `326px` + 左下竖向控件组 |

> **Tailwind 写法约定**：默认类 = 移动端，只在需要增强时加 `md:` / `lg:` / `xl:`。禁止先写桌面样式再用 `max-md:` 覆盖——那是反向适配，会持续产生漏网样式。
> **注意**：三档之间只变浮层尺寸，**不变布局模型** —— 地图在任何档位都是 100% × 100%。全站布局模型的完整说明见 [05-ui-ux-design.md](./05-ui-ux-design.md) 第 1.0 节。

### 2.2 移动端骨架（S 档）— 地图即画布 + 底部 Sheet

> **底层整块是地图**（含刘海区与 Home 区，不做任何留白或分割）。顶栏不是一条背景带，而是**直接压在地图上的几个悬浮胶囊**；内容不是"地图下面的区域"，而是**从底部浮上来的 Sheet**。

```
┌──────────────────────────────────────┐  ← 100svh，body overflow:hidden
│                                      │
│        ┌─ 悬浮胶囊行（top:44px）─┐    │
│        │ [≡] [搜索城市/景点] [⦿] │    │  ← 直接压在地图上，无背景带
│        └────────────────────────┘    │
│                                      │
│    (3)新疆      (46)四川   (44)陕西   │  ← 全国视图：省级计数徽标
│                                      │
│  全屏地图画布（100% × 100%）          │
│  可拖动 / 缩放 / 点选 / 逐级下钻       │
│                                      │
│                             ●厦门    │
│  © 腾讯地图（小字，任何档位不可遮挡） │
│ ┌──────────────────────────────────┐ │
│ │ ═══ 拖拽把手 ═══                  │ │  ← Sheet 三档吸附
│ │ 全国概览              10 省       │ │     peek 28svh / half 56svh / full 88svh
│ │ ────────────────────              │ │     默认 half
│ │ ▸ 四川  46 个景点                  │ │
│ │ ▸ 陕西  44 个景点     ← 内部滚动   │ │
│ │ ▸ …                               │ │
│ └──────────────────────────────────┘ │
└──────────────────────────────────────┘
```

城市探索页（M2）骨架一致，只是 Sheet 里换成 `CategoryTabs`（chips）+ `SubtypeLegend` + `PoiList`，且顶栏保留底图下拉、Sheet 上沿多一个定位圆钮。

#### 移动端的三级下钻（M1 → M1.5 → M2）

| 层级 | 路由 | Sheet 内容 | 手势 |
|------|------|-----------|------|
| 全国 | `/` | 省列表（含计数，未收录灰显） | 点省面 / Sheet 行 → 下钻 |
| 省级 | `/province/:adcode` | 市列表（含计数） | 点市 → 下钻；顶栏**地区按钮**可换到全国 / 任意省 / 任意市（一次展开、任意跳转） |
| 城市 | `/city/:cityId` | `CategoryTabs` + `SubtypeLegend` + `PoiList` | 同 M2 |

- **下钻不改 Sheet 档位**（保持当前 half / full），只换 Sheet 内容与地图图层 —— 避免"每级都弹一下"的抖动。
- 返回：`Breadcrumb` 与系统返回键（`popstate`）都要能回上级，**不能把用户困在城市页**。
- ⚠️ 省级 / 市级面在移动端是**大面积填充**，透明度太低会盖住道路：未选中面 **0.18**，选中 / hover 升到 **0.35**（与 03 文档的区划图层一致）。

**这套模型替换掉了早期的两个方案**，理由：

| 被否决的方案 | 问题 |
|-------------|------|
| 地图吸顶 40vh + 下方长列表 | 375×667 屏上 40vh 只有 **267px**，46 个点铺不开，看不出空间关系 —— 而"空间关系"正是地图存在的唯一理由 |
| 地图占左 60% + 列表占右 40%（桌面分栏） | 地图永远只是一条窄带，UI 和地图在争同一块面积的解释权，两边都做不好 |

改成「地图即画布 + 悬浮层」后有 3 个连带收益：

1. **视觉上地图是主角**，任何一块 UI 都能收起，收起后地图不变形
2. **手势冲突源消失**：页面本身不滚动，地图单指拖动不再和页面滚动抢事件（见 3.2）
3. **两端共用一套模型**：移动端是「胶囊 + Sheet」，桌面端是「浮层卡片」，底层与交互逻辑完全一致

### 2.3 桌面端骨架（L / XL 档）

同一模型换浮层形态：地图铺满视口，**顶部一条通栏悬浮顶栏（52px，左右贴 `--flt-inset`；左＝站标 + 地区按钮 + 搜索框，右＝底图下拉 + 站点导航 + 全屏）** + 左侧 348px 悬浮面板 + 右侧 326px 悬浮预览卡 + 左下竖向控件组。全部是 `position:absolute` 盖在地图上，面板之间保持 `--flt-gap`（12px），面板起点是 `--rail-top`（= 顶栏 52px + 上边距 + 一条间隙）。（底图署名不占浮层 —— 由 SDK 自渲染在左下角。）

> ★ 顶栏是**通栏**不是两块贴角胶囊 —— 以前这里写的是"两块贴角胶囊"，
> 与两个原型（`prototype/index.html`、`prototype/hifi/index.html` 的 `.topbar`）
> 以及 05 文档 P1 骨架都不一致，是实现自己发明的形态，已改回通栏。

> ⚠️ 本文下方示意图里的「底部图例条」**已废弃**：地区选择器进顶栏、
> 细类色板并入 `FilterBar`、底图署名**由腾讯 SDK 自带**（左下角，含审图号）。
> 详见 [10 文档第七节](./10-map-drilldown.md)。

> 详情页同理：左 620px 内容面板 + 右下 300px 位置卡，右侧地图区域仍完全可拖可缩。完整骨架见 [05-ui-ux-design.md](./05-ui-ux-design.md) 第 1.0 节与 P4。

## 三、移动端交互模型

### 3.1 底部 Sheet：三档吸附

| 档位 | 高度 | 内容可见 | 用途 |
|------|------|---------|------|
| `peek` | 28svh | 拖拽把手 + CategoryTabs + 首张卡片 | 看地图为主，知道"有这些分类" |
| `half` | 56svh | Tabs + 筛选 + 约 3–4 张卡片 | **默认档**，地图与列表同时可用 |
| `full` | 88svh | 完整列表 | 专心挑点，此时地图仅露一条边 |

**默认停 `half`**：既不遮挡地图主体，又能一眼看到内容（避免用户以为页面只有一张地图）。

**拖拽判定**：松手时用「位置 30% + 速度 70%」的加权判定，速度阈值 500px/s 触发 fling 换档。只认三档，不做自由高度 —— 自由拖拽的手感上限低、边界情况多。

**实现要点**：换档只改 `transform: translateY()` + `transition`，**不改 `height`**（避免每帧 reflow）。拖拽期间关掉 transition，松手恢复。

### 3.2 手势冲突矩阵（移动端最容易返工的部分）

| 手势发生位置 | 单指 | 双指 | 处理 |
|-------------|------|------|------|
| 地图区域 | **拖动地图**（`touch-action: none`） | 缩放地图 | app-shell 下页面不滚，**无冲突**，无需激活遮罩 |
| 地图区域 | 单指点击 marker | — | 选中 → Sheet 升到 `half` + 地图 `easeTo` 该点 |
| Sheet 内列表 | 滚动列表 | — | 列表 `scrollTop > 0` 时手势归列表 |
| Sheet 内列表（已在顶部） | **下拉 = Sheet 降档** | — | 标准行为：到达滚动边界后接手手势 |
| Sheet 把手 | **拖拽换档** | — | 始终归 Sheet |
| 悬浮控件 | 点击 | — | 控件尺寸 ≥ 44px，且相互间距 ≥ 8px |

> ⚠️ **早期文档里的「点击激活地图」遮罩可以直接删掉**。那个方案是为"页内嵌地图 + 页面可滚动"设计的妥协；改成 app-shell 后页面不滚动，冲突源不存在。
> **唯一例外**：独立详情页（可滚动页面）里若放地图预览小图，那里仍需要激活遮罩。

**必加的两条**：`overscroll-behavior: contain`（阻止滚动链穿透到页面）、`touch-action: manipulation`（去掉 300ms 点击延迟）。

### 3.3 拇指区规则

- 高频操作（分类切换、筛选、定位）**全部落在屏幕下 1/3** —— Sheet 顶栏与右下悬浮控件天然满足
- **底图选择留在顶栏下拉**：它是"偏好设置"而非高频动作（选一次通常整程不变），
  下移到拇指区反而占掉一个圆钮位；且下拉本身即选择器，代价只是首屏多点一下
- 顶部 Header 只放低频操作（Logo、地区选择入口、底图下拉）
- 卡片的主操作（"看详情"）不要做成右侧小箭头，**整卡可点**即可

### 3.4 点选后的反馈链

```
点 marker → Sheet 从 peek/full 回到 half + 地图 easeTo
          → 卡片滚动到可视区并高亮（左侧 3px 主色条）
          → 不再默认弹 InfoWindow（小屏 InfoWindow 挤占地图且难关）
          → 卡片上「查看详情」→ 打开详情
```

**移动端默认不弹 InfoWindow**，这是对 03 文档的覆盖说明：桌面端可保留 InfoWindow，移动端用 Sheet + 卡片高亮替代。

## 三·B、行程规划页的移动端形态（本轮新增）

行程页是移动端**第二大场景**（第一大是"现场找附近去处"）—— 因为它恰恰是"用户坐在酒店里排今天的计划"这个动作，大概率发生在手机上。

**骨架不变**：仍是「地图铺满 + 底部 Sheet 三档」，只是 Sheet 里装的是**时间轴**而不是 POI 列表。

### 3·B.1 Sheet 三档的内容分配

| 档位 | 高度 | 行程页的内容 | 用途 |
|------|------|------------|------|
| `peek` | 28svh | 把手 + `DayTabs` + **当天首段**（「09:00 出发 → 09:18 宽窄巷子」） | 看地图与连线为主，知道"几点出门、先去哪" |
| `half` | 56svh | `DayTabs` + 时间轴前 3–4 项 + **`DaySummary` 汇总条** | **默认档**，地图与时间轴同时可用 |
| `full` | 88svh | 完整时间轴 + 底部操作（`＋ 添加点位` / 导出 / 分享） | 专心编排 |

> `DaySummary`（在途 / 停留 / 合计）**必须固定在 Sheet 上沿可见位置**，不能随着时间轴滚走 —— 它是这一页最重要的一个数字，用户每次改顺序都想知道"一共几小时"。

### 3·B.2 手势冲突：这是本页最容易返工的地方

城市页只有「列表滚动 vs Sheet 换档」一对冲突（见 3.1）。行程页多了一对：**时间轴的拖拽排序 vs Sheet 下拉换档**。

```
时间轴行的手势判定（priority 从高到低）：
  ├ 长按 ≥ 300ms 未移动        → 进入「拖拽排序」态：行浮起 + 触觉反馈，此后纵向手势归拖拽
  ├ 已有滚动位移（非长按启动）  → 归列表滚动
  ├ 列表 scrollTop = 0 且向下拖 → 归 Sheet（降档）
  └ 把手区域                    → 始终归 Sheet
```

**为什么用长按激活而不是直接拖**：直接拖会和"滚动列表"的意图完全无法区分 —— 用户想往下滚一屏，结果动了一行顺序，是最招人烦的交互事故之一。长按 300ms 是一个**明确的意图声明**。

```css
/* 时间轴行：默认允许纵向滚动；拖拽态由 JS 加类切换 */
.timeline-row { touch-action: pan-y; }
.timeline-row--dragging { touch-action: none; }
```

**降级方案**：微信内长按可能被「长按识别/保存图片」抢占（列为待实测 V6）。所以**必须有替代路径**：

- 每行右侧提供一个**拖拽把手**（≡ 图标），按住把手即可拖动（此时不依赖长按判定）
- 以及一个**「移到第 N 位」的菜单**（完全无手势的路径）

> ⚠️ 这三条路径（长按拖 / 把手拖 / 菜单移动）**至少实现两条**。移动端的拖拽排序是这个页面唯一"必须有 Plan B"的交互。

### 3·B.3 连线在小屏的简化

| 桌面 | 移动 |
|------|------|
| 段上有文字标签「23 分 · 5.2 km」 | ❌ 小屏上文字会糊成一团 → 改为**段中点一个小圆点**，数字由时间轴承载 |
| 点位显示序号图标 + 名称 | 名称在移动端**默认隐藏**，只留序号（避免 46 个名字压满屏）；选中时该点才显示名称 |
| 住宿点图标 + 名称 | 住宿点**始终显示名称**（它是行程的锚，用户需要随时确认"我从哪出发"） |

### 3·B.4 两个移动端特有的细节

1. **住宿点是隐私**：手机上更容易随手分享。所以「分享」按钮在移动端**默认关闭"显示住宿点名称"**，且分享前弹一次确认（「将生成一个包含你行程的链接」）。见 [09](./09-itinerary-planner.md) 第八节
2. **加点位复用城市页选择器**：`PoiPickerSheet` 直接复用城市页的 `CategoryTabs` + `FilterBar` + `PoiList`（**不另写一套**），只是选中行为从"打开预览卡"变成"追加到当天"。这也让用户能顺手用上「就近排序」

## 四、视口、安全区与排版

### 4.1 视口声明

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover" />
```

- **`viewport-fit=cover` 必加** —— 否则 `env(safe-area-inset-*)` 恒为 0，iPhone 刘海/底部横条区域会压住内容
- **禁止 `user-scalable=no` / `maximum-scale=1`** —— 百度移动搜索规范明确禁止强制用户缩放，且会造成无障碍问题

### 4.2 高度单位：用 `svh`，不用 `vh`

`100vh` 在移动端等于**大视口**（地址栏收起时的尺寸），比实际可见区域高 **56–80px**，直接后果是底部内容被地址栏吃掉。

| 单位 | 含义 | 用在哪 |
|------|------|--------|
| `svh` | 小视口（地址栏可见） | **默认选择**：app-shell 高度、Sheet 档位。不随滚动跳动 |
| `dvh` | 动态视口 | **慎用**。会随地址栏伸缩实时变化 → 滚动时布局抖动 |
| `vh` | 等同上限（大视口） | 只在需要 `svh` 的降级 fallback 里写一行 |

```css
/* 正确写法：先 vh 兜底，再 svh 覆盖 */
.app-shell {
  height: 100vh;
  height: 100svh;
}
```

浏览器支持：`svh/dvh` 需 Chrome 108+ / Safari 15.4+ / Firefox 101+。**与 `@supports (height: 100svh)` 配合**给旧内核留降级。

### 4.3 安全区

```css
.sheet {
  padding-bottom: max(16px, env(safe-area-inset-bottom));
}
.floating-toolbar {
  bottom: calc(16px + env(safe-area-inset-bottom));
}
```

只要涉及 `position: fixed` 的底部元素，都要过一遍安全区，否则 iPhone 上会被 Home Indicator 压住。

### 4.4 排版与触控（百度移动搜索规范 + W3C）

| 项 | 要求 | 说明 |
|----|------|------|
| 正文 | **≥ 16px** | 兼作 iOS 表单聚焦不自动放大的门槛（< 16px 会触发自动放大） |
| 辅助文字 | ≥ 14px | 版权署名、来源日期也在内 |
| 行高 | 1.6–1.75 | 中文长文可读性 |
| 触控目标 | **≥ 44×44 CSS px** | 含地图 marker 的**点击热区**（视觉 28px，热区 44px） |
| 相邻目标间距 | ≥ 8px | 防误触 |
| 对比度 | ≥ WCAG AA | 主色 `#1677FF` 上写白字达标；`#E8389B` 需检查 |

## 五、地图的移动端专项设计

### 5.1 底图默认值：两端统一，用户自选

底图**不再分端**，也**不做自动降级** —— 桌面与移动默认都是 **「矢量图 · 详细」**（`DEFAULT_BASEMAP`），之后一切由用户决定。

| 端 | 默认底图 | 理由 |
|----|---------|------|
| 桌面（L / XL） | **矢量图 · 详细** | 文字（地点名 + 路名）与建筑齐全，首屏即能读懂"哪里有地方" |
| **移动（S / M）** | **矢量图 · 详细** | 影像瓦片体积是矢量的 **5–10 倍**，4G 首帧明显更慢；手机上看攻略的诉求是"这个点在哪、周围有什么"，不是城市肌理 |

用户在底图菜单里做两件事：**选类型** + **调详细度**（2026-09-25 从"四档预设"改）：

| 段 | 取值 | 进 `features` 的要素 |
|----|------|--------------------|
| 底图类型 | 矢量图 / 影像图 | `base` 恒在 |
| 详细度（快捷档） | 详细 / 简略 | 详细 = 下表四项全开；简略 = 全关 |
| 逐项开关（矢量） | 地点名称 / 道路名称 / 建筑 | `point` / `label` / `building2d` |
| 逐项开关（影像） | 路网与地名 | `road` |

> 道路、地铁线与区划边界属于底面 `base`，腾讯**不提供**单独开关 —— 详见 [03](./03-map-interaction.md) 2.2.1。

> 各端选择结果写入 `localStorage`（`STORAGE_KEYS.basemapPreference`），下次进来沿用。
> 曾设计过的"`zoom ≥ 15.5` 自动切矢量 + 迟滞 0.5 + 一次性说明 + 锁定"四件套**整体废弃** ——
> 用户选了影像、地图却自己变回矢量，属于"界面不听指令"；需要解释规则 = 规则本身错了。
> 各档对应的合法 `features` 名字是**真机探针实测**出来的白名单（白名单外的名字被静默忽略，`getBaseMap()` 还会原样回读，见 [03 文档第二节](./03-map-interaction.md)）。

### 5.2 点聚合（移动端必做）

46 个标注点在 375px 宽的屏幕上是**大面积重叠**的。腾讯 JS API GL 自带 `TMap.MarkerCluster`（在 core 里，**不需要 `libraries` 参数**）：

```ts
// 腾讯 MarkerCluster
const cluster = new TMap.MarkerCluster({
  map,
  geometries: pois.map((p) => ({
    id: p.id,
    // ★ 按细类着色：每个 subtype 一个 PointGeometry 样式（见 SUBTYPE_META）
    styleId: `sub-${p.subtype}`,
    position: new TMap.LatLng(p.lat, p.lng),   // ⚠️ 纬度在前，写反了落点全错
  })),
  gridSize: isMobile ? 60 : 40,   // 聚合网格像素大小
  minimumClusterSize: 2,          // 少于该数量不聚合
  zoomOnClick: true,              // ★ 点击聚合簇原生放大展开（腾讯内置，无需手写）
  enableDefaultStyle: false,      // 关掉默认样式，用自己的（按分类着色 / 中性色 + 数字）
})

// 数据变化时用 setGeometries，不要重新 new
cluster.setGeometries(next)
```

- **移动端聚合、桌面端不聚合**（复用：同一个 `cluster.ts`，聚合开关按端配置）
- **聚合簇的样式按分类着色**（簇内多细类时用中性色 + 数字）
- 腾讯的 `zoomOnClick` **原生支持**点击散开（高德需自己算簇中心并放大）—— 这是腾讯相较省事的一处

> ⚠️ **两个腾讯特有的坑**（与 03 文档踩坑清单对应）：
> 1. `position` 必须是 `new TMap.LatLng(lat, lng)`（**纬度在前**）。直接传 `{lng, lat}` 对象会静默落到错误位置
> 2. **坐标完全相同的点会互相顶掉** —— 若两个 POI 锚点重合，先做去重或微调（~1e-5 度），否则会静默少一个点

### 5.3 控件精简

腾讯 JS API GL 的默认控件在小屏上是负担，移动端处理：

| 控件 | 桌面 | 移动 |
|------|------|------|
| 缩放按钮 +/- | 保留 | **移除**（双指缩放） |
| 比例尺 | 保留 | 保留（小尺寸，攻略场景有用） |
| 底图选择 | 顶部工具条（**下拉气泡**） | **右下角工具条 → 底部浮层**（2026-10-27 改；原来在顶栏） |
| 回到全览 / 定位 | 顶部工具条 | **已撤**：顶栏只剩搜索，回家出口收在搜索空态的「回到全国视图」 |
| 3D 俯仰 | 可保留 | 建议关闭（单指拖拽时易误触发倾斜） |

> **右下角工具条（2026-10-28 第五轮定稿）**：路线规划 / 图层 / 关于 / GitHub 四枚圆角图标
> **竖排一列**，`bottom: var(--flt-inset)` **钉在屏幕右下角**，`z-[27]`（**低于**底部浮层 `z-28`）。
> 用户原话：「右下角那四个悬浮按钮，是固定在底部的，不会被其他东西往上挤」——
> 上一版让它跟着浮层高度上移，在半屏处飘着像被顶上去，已撤。
>
> **层级方向（同日第三轮）**：用户看到三块浮层两种规矩 ——「图层的浮层在按钮之下、详情也是、
> 路线规划的在按钮之上，没统一」，选定了**「浮层永远在最上」**。于是
> ① 工具条回到 `z-[27]`；② 删掉 `planOpen` 时 `return null` 那条特例
> （它让工具条整条消失，才显得"规划压住了按钮"）；③ 城市列表 `pr-[40px]` /
> 页脚 `mr-[44px]` 的让位一起删（按钮已在浮层底下，不再是覆盖物）。
> **已知代价**：城市页/省级页的清单浮层常驻且没有出口，所以四枚在那两页被整块盖住；
> 首页、点位详情页没有常驻浮层，照常可点。要恢复"城市页也能点"，把层级抬回 `z-[29]`
> 并把两处让位加回来 —— 但那会重新变成"按钮压着浮层"。
>
> **同时只显示一块浮层（同日第三轮）**：用户：「不要隐藏一个下方还有一个」。
> 仲裁在 `mobile/ui/sheetHub`：有出口的浮层（详情 / 点位详情页 / 规划 / 图层）走
> `useSheetClaim(key, close)`，谁新开谁把别的关掉；页面主体（城市 / 省级清单）走
> `usePageSheet()`，挂载时清场、自己不会被关。注册按**挂载/卸载**走 ——
> 项目里所有浮层都是"关掉就 `return null`"。
>
> 图层点开的是**与详情/规划同一个浮层基座**（`mobile/ui/Sheet`），但尺寸模式是
> **自由拉伸**（`size={{min:34,max:88,initial:56}}`），不做三档。
>
> **收起判据（两种浮层共用）**：拖到比最小高度还低 ⇒ 收；或快速下甩（≥24px 且 ≥0.5px/ms）⇒ 收。
> 旧的「只有在 peek 档再拉一次才收」被否掉了 —— 用户：「我明明一次性拉到底了，
> 没有触发隐藏，而是显示的最小态，再往下拉一次，才会关闭」。
> 自由模式没有"档"可降，所以速度判据更宽（≥40px 的甩动作就收）。

### 5.4 定位与就近排序

- 用 `navigator.geolocation` 或腾讯 `TMap.service.Geolocation`（**需要 HTTPS**；Netlify/CF 默认为 HTTPS，满足）
- 拿到位置后**只在本地内存里算距离并排序**，不写 localStorage、不上传（合规红线，见第九节）
- 权限被拒 → 排序项灰掉并给 Tooltip 说明，不弹错误

## 六、微信内置浏览器（必测端）

旅游内容的实际到达路径大概率是：**微信里点开别人分享的链接**。这条路径有两个独立问题。

### 6.1 内核差异：不要依赖 `backdrop-filter`

| 环境 | 内核 | `backdrop-filter` |
|------|------|------------------|
| iOS 微信 | WKWebView（跟随系统 Safari） | 支持 |
| Android 微信 | X5 / XWeb（基于 Chromium，版本落后） | **支持情况不一致，多份资料互相矛盾** |

**处置：不作为关键视觉分层的依赖。** 毛玻璃只做锦上添花：

```css
/* 兜底：不透明半透明白，任何内核都能看 */
.sheet {
  background: rgba(255, 255, 255, 0.96);
}
/* 增强：支持才启用，且只做小面积（Sheet 顶栏、悬浮控件） */
@supports (backdrop-filter: blur(8px)) or (-webkit-backdrop-filter: blur(8px)) {
  .sheet { background: rgba(255, 255, 255, 0.72); backdrop-filter: blur(8px); }
}
```

- `blur()` 取值 **6–8px**：更高在部分 Android WebView 上会掉帧
- **不要**用 `filter: blur()` 伪元素去模拟（会把子元素一起糊掉）

### 6.2 分享卡片

微信**不读 `og:` 标签**（那是 Facebook/Twitter 的协议），自定义卡片需要 JS-SDK + 已认证公众号 + 域名校验 —— 开源项目不做这件事。所以只能优化微信**自动抓取**的字段：

| 抓取项 | 优化做法 |
|--------|---------|
| 标题 | `<title>` 控制在约 30 字内，**城市名 + 核心价值前置**（微信会截断） |
| 摘要 | `<meta name="description">`，写成一句完整的推荐语，不堆关键词 |
| 缩略图 | 取页面中**靠前的、尺寸 ≥ 300×300 的位图**；建议城市封面单独提供一张 **JPG/PNG 方图**（避免 WebP），并保持在 DOM 靠前位置 |
| 落地页 | 分享的多为 POI 详情页 → 该页的 `meta` 与首图尤其要认真做（与 SEO 清单 S1/S3 复用同一套 meta） |

> ⚠️ 微信首图对 WebP 的抓取行为**未实测**，列入第 9 节待验证项。若确认不支持，则城市封面额外导出一张 JPG 供抓取。

### 6.3 微信特有坑

- **滚动穿透**：`position: fixed` 遮罩下背景页面仍可滚。用 `overscroll-behavior: contain` + 打开遮罩时给 `body` 加 `overflow: hidden`（记下 `scrollTop`，关闭时还原）
- **`localStorage` 配额更严**：只存轻量偏好（`map.basemap`、`sheet.snap`），不要缓存 JSON
- **顶部栏遮挡**：微信有自带顶部导航，`svh` 已扣除；但 `100vh` 会算进微信工具栏高度，进一步印证 4.2 的结论

## 七、性能预算（分端）

### 7.1 指标

| 指标 | 桌面 | **移动 4G** | 说明 |
|------|------|------------|------|
| LCP | ≤ 2.0s | **≤ 2.5s** | 移动端取 2.5s —— 这是百度/Google 的硬标准，定 2.0s 会变成长期超标项 |
| INP | ≤ 200ms | ≤ 200ms | 地图交互、Sheet 拖拽是主要风险 |
| CLS | ≤ 0.1 | **≤ 0.05** | 移动端更严：Sheet 高度跳变、图片无尺寸都会贡献偏移 |
| 首屏 JS | ≤ 200KB gzip | ≤ 200KB gzip | 地图 SDK 独立异步 chunk，不阻塞首屏 |
| 预渲染 HTML | ≤ 60KB/页 | 同 | |
| 城市 JSON | 见 7.2 | | |
| 图片 | 封面 1080w | **列表 400w / 详情 800w** | 见 7.3 |

> 📏 **验收必须用真机 + 网络节流**（DevTools 的移动模拟不还原微信内核，也不还原跨境链路）。移动端验收清单见 7.5。

### 7.2 数据体积：先算清楚，别做无用的分片

按每城 46 个 POI、每个 POI 约 2KB 原始 JSON 估算：

```
46 × 2KB ≈ 92KB 原始 → gzip 后约 25–30KB
```

**结论：城市 JSON 不需要按分类分片**。文档里 300KB gzip 的上限留得很宽松，实际用不到十分之一。

分片的触发条件写死（避免以后拍脑袋）：**单城 POI > 150 或首屏 JSON > 150KB gzip 时**，再改为「列表轻量字段 + 详情字段」两文件拆分。

### 7.3 图片（移动优先）

- 移动端窄屏**不需要 1080w 的大图**：列表用 **400w**，详情页首图 800w，lightbox 才取大图
- 用 `srcset` + `sizes` 交给浏览器选，**不要用 JS 判 UA 拼 URL**（与 04 文档「用 API 返回的 URL」约束一致，避免手工拼参数违规）
- Hero / 城市封面图加 `fetchpriority="high"`，其余全部 `loading="lazy"` + 显式 `width`/`height`（防 CLS）
- 竖屏构图问题：横构图封面在手机上会被裁掉两侧。**城市封面建议准备竖版裁切**（Unsplash 返回的 `portrait` 尺寸即可，无需手工裁）

### 7.4 首屏策略

- 预渲染 HTML 已含文案 → **无骨架屏**，文案立即可见（这是 SSG 的最大红利，移动端网络慢时尤其明显）
- 地图 SDK 在 `requestIdleCallback` 或首个交互后加载；加载完成前地图区显示**城市封面图 + "地图加载中"**，不是空白
- 地图 key 缺失 / SDK 失败 → 地图区降级为**静态封面 + 完整列表**，功能不中断

### 7.5 测试矩阵（真机，不可省）

| 维度 | 覆盖 |
|------|------|
| 设备 | iPhone（Safari）、iPhone（**微信**）、Android（Chrome）、Android（**微信**）、Android 小屏 360×640 |
| 视口 | 360×640 / 375×667 / 390×844 / 414×896 / 768×1024 / 1440×900 |

## 十、托管平台的国内可达性（已决策：采用 Netlify）

> 这一节是查移动端性能时顺带查出来的。**结论已定：维持 Netlify（路径 A）** —— 理由与取舍见 10.3。

### 10.1 实测事实

| 来源 | 测量 | 结果 |
|------|------|------|
| 21YunBox（2026-08-30，阿里云张家口探测点） | 从大陆发起访问 netlify.com | 首字节 335ms、首屏 1.4s，**但 3 次请求全部未能在 60s 内完成** |
| 21YunBox（2026-08-30，北京家庭宽带） | 88 次真实页面加载 | 102 个未响应的 host 中，**101 个是页面引入的第三方**，而非平台本身 |
| 国外静态托管国内速度横评（2026） | 按国内响应排序 | EdgeOne Pages（备案）50–90ms > EdgeOne（未备案）670–1400ms > Netlify（部分地区偏慢）> Cloudflare Pages（联通晚高峰 800ms+，波动大）> GitHub Pages（极慢）|
| 阿里云官方文档 | OSS 静态托管的备案要求 | **Bucket 在中国内地时，绑定的自定义域名必须完成 ICP 备案**；用 Bucket 默认域名访问 HTML 会强制下载 |

### 10.2 结论

- **Netlify 没有被墙，但"完成不了"**：免费版最近的 CDN 节点在新加坡（付费高阶也只到仁川/东京），跨境链路 + 第三方资源是主要失败点
- **"第三方资源"这条对我们格外致命**：我们的图片全部依赖 Unsplash / 百度百科 / Pexels 外链。**虽然深圳实测 Unsplash 0.43–0.84s 可用，但一旦某张图失败，`ImageLazy` 降级链会被频繁触发，观感会比单纯的"加载慢"更差**
- 更麻烦的是**百度收录**：百度官方明确"优先本地速度与可达性"，跨境的托管平台在 SEO 上是先天劣势 —— 这与"做 SEO"的目标直接冲突

### 10.3 三个可选路径

| 路径 | 国内移动端体验 | 成本 / 门槛 | 对开源的影响 |
|------|--------------|-----------|-------------|
| **A. 维持 Netlify** | 能开但不稳；LCP 目标可能长期不达标 | 零 | 最佳（Deploy Preview 好用） |
| **B. Cloudflare Pages（免备案）** | 联通晚高峰 800ms+，波动大；但海外极快、带宽无限 | 零、免备案 | 好 |
| **C. 域名备案 + EdgeOne Pages / 腾讯云 COS+CDN** | **50–90ms，最优** | 需域名 + 备案（个人可办，约 1–3 周） | 备案绑定维护者个人域名，fork 者需自备 |

**决策：路径 A —— 单站 Netlify。**

理由：项目定位是个人自用的简单开源项目，**"零运维"的权重高于"国内极致速度"**。C 路径要引入域名 + 备案（1–3 周，备案绑定维护者个人身份，fork 者还得自备），B 的国内表现也不理想，等于用一个次优换另一个次优 —— 都不值得为这个项目增加复杂度。

**接受的风险与补偿**：

- 国内移动端 LCP 目标相应放宽（见第七节分端预算），**性能以真机实测为准，不追求纸面达标**
- 百度收录会弱于国内托管；但 SEO 的核心收益是"城市页与 POI 详情页能被抓到内容"，Netlify 仍直出预渲染 HTML，基础收录不受影响
- **迁移成本已锁定为接近零**：产物是纯静态文件，路径全相对、无服务端依赖、无数据库。将来若真觉得慢，换托管是**运维动作，不是重构**

> ✅ 托管方案不再纠结 —— 它不阻塞现在开工。

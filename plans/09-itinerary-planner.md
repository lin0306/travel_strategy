# 09 · 行程规划器设计（定住宿 · 选点位 · 算通勤）

> 这份文档回答的是本项目的**核心使用场景**：用户要去某个城市玩，自己定住哪儿、自己挑景点和餐厅，**系统负责算出通勤时间**。
> 它是全项目**唯一会挑战「运行时零 API 调用」这条架构前提**的功能，因此核心工作量在于：**把这个挑战化解掉**。

---

## 一、Why：用户到底要什么

先把用户的话原样记下来，因为它决定了整个设计的边界：

> 「去哪个城市玩，**我自己确定住的地方**，确定**去游玩哪几个景点**，**吃哪些东西**，需要**规划通勤时间**。」

拆成四件事，对应四个明确的产品判断：

| 用户的话 | 产品含义 | 关键判断 |
|---------|---------|---------|
| 「我自己确定住的地方」 | 住宿点是**用户自定**的，不来自我们的 POI 表 | ⚠️ 这意味着**必须支持任意坐标**，不能只在 46 个 POI 里选 |
| 「确定去游玩哪几个景点，吃哪些东西」 | 点位**由用户挑选**，我们不做推荐算法 | ✅ 我们只做「已选项的编排与计算」，不做"猜你喜欢" |
| 「规划通勤时间」 | 核心价值是**时间**，不是"最美路线" | 输出的主角是**分钟数**，路线是配角 |
| 「去哪个城市玩」 | 一次行程对应**一个城市** | 跨城联游不在范围内 |

### 1.1 一个必须承认的前提

**这不是一个"路线优化器"，是一个"行程计时器"。**

市面上多数行程工具的价值主张是"帮我排出最优顺序"。但我们不做这个 —— 见第二节的 Non-goals。理由是：

1. **用户说了顺序由他自己定**。旅游行程的顺序偏好高度个性化（有人要避开人流、有人要赶日落、有人就是想先去吃），一个算出来的"最优"很容易不是用户想要的
2. **"最优"在我们的数据条件下不可信**。真正的行程优化需要营业时间窗、预约时段、人流曲线这些我们**没有**的数据。拿不到这些就算出个"最优顺序"，是在用数学的精确掩盖信息的缺失
3. **只算时间反而是更硬的承诺**。"这三点之间要花 42 分钟"是可验证的事实；"这是最优顺序"是不可验证的主张

> 这个取舍要显式写在 UI 上：时间轴上明说「顺序由你决定，我们只算时间与总耗时」。**把不做什么说出来，比假装什么都能做更可信。**

### 1.2 目标用户与场景

| 场景 | 用户状态 | 诉求 |
|------|---------|------|
| **出行前编排**（主场景） | 已订好酒店，正在做攻略 | 「我住春熙路，想去宽窄巷子、熊猫基地、吃顿火锅，一天够吗？要几点出门？」 |
| **到达后微调** | 到酒店了，想改计划 | 「今天下午临时加一个点，得几点回来？」 |
| **分享给同行人** | 和别人一起出行 | 「把我排好的行程发给你看看」 |

## 二、范围与 Non-goals

### Goals

| # | 目标 |
|---|------|
| I1 | 用户可设置**多个住宿段**（支持中途换酒店），每天归属一个住宿段 |
| I2 | 用户可从城市 POI 库里**挑选**点位（景点/美食/网红/特色），并按天分配 |
| I3 | 用户可**自定任意住宿点**（不是只能选 POI），支持地址搜索定位 |
| I4 | 每一段通勤显示**时长 + 距离 + 方式**，支持**六种出行方式**切换：轿车 / 打车 / 公交 / 地铁 / 骑行 / 步行 |
| I4b | **每一段提供多种路线方案可选**（最多 3 条），显示各方案的距离、时长、路况与打车费，用户可切换 —— 这是"考虑堵车"的落地方式 |
| I5 | 显示**时间链**：几点出发 → 几点到达 → 停留多久 → 几点离开 → 晚上几点回到住宿 |
| I6 | 用户可**拖拽调整顺序**与**修改停留时长**，时间链实时重算 |
| I7 | 行程**可导出 / 可分享**（纯前端实现，不需要后端） |
| I8 | **地图挂掉时行程照常可用**（时间计算不依赖地图） |

### Non-goals（本期明确不做）

| ❌ 不做 | 为什么 |
|--------|--------|
| **自动排序优化（TSP / 2-opt）** | 用户明确选择自己定顺序。且缺少营业时间窗、预约时段等数据，"最优"不可信（见 1.1） |
| **跨城联游** | 腾讯公交换乘**仅支持同城**（跨城必须用驾车），跨城调度需要另一套模型。一次行程 = 一个城市 |
| **票务 / 预订 / 支付** | 与项目定位不符（见 01 文档 Non-goals） |
| **实时天气 / 实时人流叠加** | 无稳定数据源，且会引入额外的 key 与配额 |
| **账号体系 / 云端同步** | 行程存 `localStorage` + 导出文件。纯静态站不做后端 |
| **智能推荐"你应该去哪"** | 我们提供的是编排工具，不是推荐引擎。推荐是另一个产品 |
| **单次规划超过 30 个途经点** | 腾讯途经点上限 30 个。本项目**按段调用**（每段一次独立请求），实际不会触及；此项仅防止将来做"整天一条连续路线"时超限（见 5.3） |

## 三、通勤时间从哪来（本方案的技术核心）

### 3.1 问题：这功能天生要调 API

回顾架构（01 / 04 文档）：**数据在构建期固化，运行时零 API 调用**。这是"纯前端 + 开源 + 低配额风险"三件事能同时成立的原因。

但行程规划看起来必须破坏它 —— 用户选哪些点、住哪儿，都是运行时才知道的，怎么可能预先算好？

**破解思路：拆开通勤的两种类型。**

```
行程里的通勤段（Leg）只有两种：

  ① POI → POI          ← 组合数有限（46×46），且与用户无关 → ★ 可以预计算
  ② 住宿点 → POI        ← 住宿点是任意坐标 → 只能实时算
                         （但只算用户选中的那几个点，不是全 46 个）
```

**绝大多数通勤是第 ① 类。** 把第 ① 类预计算成矩阵后，运行时就只剩极少量调用：

| 通勤类型 | 数据来源 | 运行时调用量 |
|---------|---------|------------|
| POI ↔ POI（驾车/步行/骑行） | **预计算矩阵**（构建期固化） | **0** |
| POI ↔ POI（公交） | 运行时按需 | 每段 1 次（仅用户选了公交的段） |
| 住宿点 ↔ POI | 运行时按需 | 每天 1–2 次（批量接口） |
| 住宿点 ↔ POI（公交） | 运行时按需 | 每段 1 次 |

> ✅ **默认配置下运行时调用量 ≈ 0**。只有用户主动切公交、或自定住宿点时才产生调用，且都能缓存。
> 这保住了架构的"纯前端"性质：**静态数据永远可用，API 只是增强**。

### 3.2 通勤矩阵的设计

#### 存什么

```ts
// data/cities/{cityId}.json 里的 transit 字段（见 02 文档）
export interface CityTransitMatrix {
  /** ★ 必须是时间戳：驾车时长含实时路况，是"生成时刻的快照"，不是恒定量 */
  generatedAt: string              // '2026-09-18'
  /** 采样时刻说明，用于 UI 如实告知 */
  sampledAtLabel: string           // '工作日上午 · 含路况'
  /** 矩阵的 POI 顺序：与 city.pois 的下标一一对应 */
  poiIndex: string[]               // ['kuanzhai-xiangzi', 'panda-base', ...]

  /** 只存对称上三角（见 3.2.3）—— 三条矩阵通道 */
  modes: {
    driving:   MatrixChannel
    walking:   MatrixChannel
    bicycling: MatrixChannel
  }
}

export interface MatrixChannel {
  /** 距离（米），定长 base36 扁平串 */
  distance: string
  /** 时长（秒），定长 base36 扁平串。`0000` = 不适用 */
  duration: string
  /** 该方式的直线距离适用上限（米），超出即写 `0000` */
  maxStraightMeters: number
}
```

#### 3.2.1 六种出行方式 ≠ 六条矩阵通道

用户要的六种方式里，**只有三种能进预计算矩阵** —— 其余几种是从这三条派生出来的：

| 用户看到的方式 | 构建期数据源 | 进矩阵？ | 说明 |
|--------------|-------------|---------|------|
| **轿车** driving | `/ws/distance/v1/matrix?mode=driving` | ✅ | 原生支持批量 |
| **打车** taxi | 复用 driving 的时长 + `/ws/direction/v1/driving` 的 `taxi_fare` | ⚠️ **复用 driving** | 打车与轿车**走的是同一条路、时长完全一样**，差别只在"费用"。所以矩阵不重复存，打车费按需单独拉 |
| **骑行** bicycling | 矩阵 `mode=bicycling` | ✅ | ★ **腾讯原生支持骑行批量**（这是换回腾讯的最大收益） |
| **步行** walking | 矩阵 `mode=walking` | ✅ | 原生支持批量 |
| **公交** transit | `/ws/direction/v1/transit` | ❌ | 时效最强 + 无批量接口，理由见 3.2.2 |
| **地铁** subway | 同 transit（`preference=NO_SUBWAY` 的反向筛选） | ❌ | 公交与地铁在腾讯是**同一个接口**，公交方案里自动包含地铁段。UI 上的"地铁"= 只看含地铁段的方案 |

> 📌 **"打车"不是一个独立的路径规划方式** —— 它和轿车走同一条路，时长一样。它独立的意义在于**费用**：腾讯驾车接口返回 `taxi_fare.fare`，能直接告诉用户"这趟打车约 ¥18"。
> 所以矩阵**只为 driving 存一份**，打车复用；打车费在用户点开该段详情时才拉取。

> 📌 **"地铁"同理** —— `transit` 返回的换乘方案里自动包含地铁段，不需要第二个接口。用户想"只要地铁不要公交"时，对方案列表按"是否含地铁段"过滤即可。

**三条矩阵通道的构建成本**（46 个 POI）：

| 通道 | 接口 | 请求数/城 | 计算次数/城 |
|------|------|----------|-----------|
| 驾车 driving | `/ws/distance/v1/matrix?mode=driving` | 4 | ≈ 2,500 |
| 步行 walking | `?mode=walking` | 4 | ≈ 2,500 |
| 骑行 bicycling | `?mode=bicycling` | 4 | ≈ 2,500 |
| **合计** | | **12** | **≈ 7,500** |

> ✅ **这是换回腾讯最大的收益**：上一版方案里骑行**没有批量接口**，只能一对一调 1,035 次；腾讯的矩阵三种方式都支持批量，**骑行成本从 1,035 次请求降到 4 次**。

⚠️ **计量口径（最容易算错的一点）**：矩阵接口按 **"计算次数"** 计量 —— 每计算一对起终点算 1 次，**不是按请求数**。一次 25×25 的请求 = **625 次计算**。查配额时千万别按请求数估，否则会低估 600 倍。

对照腾讯日配额（**10,000 次 / 接口 / 日，按接口独立**）：单城 7,500 次计算 → 一天跑一个多城市；用阈值裁剪（3.2.5）可压到约 3,900 次 → **一天两城**。配额**每天重置**，不存在"一年用完就没了"。

**请求参数要点**：

```
GET https://apis.map.qq.com/ws/distance/v1/matrix
    ?mode=driving                                   ← driving | walking | bicycling | straight
    &from=lat,lng;lat,lng;...                       ← ★ 纬度在前！
    &to=lat,lng;lat,lng;...
    &key={TMAP_WEB_KEY}
→ result.rows[i].elements[j] = { distance(米), duration(秒) }

容量：多对多 from×to ≤ 625 且单侧 ≤ 50（即 25×25）
      一对多 1 → 最多 200
```

> ⚠️ **两个必须逐元素处理的坑**：
> 1. **坐标是 `lat,lng`（纬度在前）** —— 与绝大多数 WebGIS 习惯相反，写反了返回结果全错且不好查
> 2. **单个元素可能失败**：起终点附近 5km 内无道路时该元素返回 `status: 4`，`distance` **退化为直线距离**且**不返回 `duration`**。必须逐元素判 `status`，不能直接读 `duration`（会得到 `undefined` 而不是报错）

> ⚠️ **`duration` 单位是秒** —— 但**路线规划**接口的 `duration` 是**分钟**。两个接口单位不一致，混用会差 60 倍。

#### 3.2.2 为什么公交不预计算

三个理由，任何一个都足够：

1. **时效性最强**：地铁新开、公交改线、线路调整——公交是所有方式里变化最快的。预计算出来的公交时长**过一两个月就可能明显失真**，而驾车时长相对稳定
2. **没有批量接口**：公交路径规划是一对一接口（`/ws/direction/v1/transit`，且需要城市上下文）。46 个点全量预计算 = 1,035 次/城，是驾车矩阵（4 次）的 **259 倍**
3. **实际用得少**：用户不会给每一段都选公交。真正常见的是一天里 2–4 段用公交

**结论：公交放在运行时按需算，只算用户实际选了公交的段。** 这个决定同时省了配额、保了新鲜度、还减少了数据体积。

#### 3.2.3 只存上三角（对称性假设）

路网上 A→B 与 B→A 的时长**理论上不等**（单行道、掉头限制）。但要诚实评估差异量级：市内短途通勤的往返差异通常在 5–15%，且**用户对"42 分钟 vs 45 分钟"不敏感**。

代价对比：

| 方案 | 数字个数 | 原始体积 | gzip 后 |
|------|---------|---------|--------|
| 全矩阵（含方向） | 46×46×3×2 = 12,696 | ~51 KB | ~18 KB |
| **上三角（本项目）** | 46×45/2×3×2 = **6,210** | **~25 KB** | **~9 KB** |

**选上三角**，并把这个近似**明确写在 UI 上**（段的 Tooltip：「时长按往返均值估算」）。

> ⚠️ 若后续实测发现某些点对（如跨江、跨山的点）往返差异显著，再单独为这些点对存方向性修正值 —— 而不是退回全矩阵。

#### 3.2.4 编码方案

扁平定长 base36 字符串，`0000` 作哨兵表示"不适用"：

```
索引公式（i > j，行优先上三角）：
  idx(i, j) = i × (i − 1) / 2 + j

例：n=4，上三角 6 个位置
  (1,0)→0  (2,0)→1  (2,1)→2  (3,0)→3  (3,1)→4  (3,2)→5

读取：
  cell(i, j) = i > j ? idx(i, j) : idx(j, i)      // 对称取值

值编码：
  距离 4 位 base36（最大 36⁴ = 1,679,616 米 ≈ 1,680 km）
  时长 4 位 base36（最大 1,679,616 秒 ≈ 466 小时）
  '0000' → 不适用（该方式超出了合理距离，或接口无数据）
```

```ts
// data/_generated/ 里的读取辅助（前端与脚本共用）
const B36 = (s: string) => parseInt(s, 36)

export function readLeg(
  m: CityTransitMatrix,
  i: number, j: number, channel: MatrixChannel,
): LegEstimate | null {
  if (i === j) return { distance: 0, duration: 0 }
  const k = i > j ? (i * (i - 1)) / 2 + j : (j * (j - 1)) / 2 + i
  const ch = m.modes[channel]
  const d = ch.distance.slice(k * 4, k * 4 + 4)
  const t = ch.duration.slice(k * 4, k * 4 + 4)
  if (d === '0000' || t === '0000') return null        // 该方式不适用
  return { distance: B36(d), duration: B36(t) }
}
```

> 定长切片的读取是 **O(1) 字符串操作**，46 个点的量级下整个矩阵解析是亚毫秒级，不需要建索引结构。
> **不做 delta 编码**：当前体积（gzip 后约 9 KB）远未触顶（单城 300 KB 预算），过早优化只会增加脚本复杂度。

#### 3.2.5 阈值裁剪（省调用量 + 提升「不适用」的表达力）

步行 40 公里、骑行 30 公里这种数据**算出来也没用** —— 用户看到「步行 7 小时 52 分钟」不会有任何帮助，反而是噪音。所以在构建期就按**直线距离**（haversine，纯本地计算，零调用）裁剪：

| 方式 | 直线距离上限 | 理由 |
|------|------------|------|
| 驾车 | 无上限 | 全量计算 |
| 步行 | **3,000 m** | 步行路径通常比直线长 20–40%，3 km 直线 ≈ 4 km 路径 ≈ 50 分钟，已到步行合理上限 |
| 骑行 | **8,000 m** | 骑行路径 ≈ 10 km ≈ 40 分钟，旅游场景的合理上限 |

超出即写 `0000`。UI 侧的表现是：

```
步行 · 不适用（距离 12.3 km）
  建议：驾车 22 分钟 / 骑行 41 分钟
```

> ✅ **这个裁剪在腾讯这边依然值得做**，但**收益点变了**：换回腾讯后矩阵三种方式都是批量请求，请求数固定 4 次/通道，裁剪**不再减少请求数**。
> 它现在的价值是两条：
> 1. **减少"计算次数"**（矩阵按计算次数计费）—— 步行的有效点对通常只有全量的 20–30%
> 2. **让数据语义更清楚** —— "不适用" ≠ "算不出来"。用户看到「步行 12.3 km」不如看到「步行不适用 · 建议骑行或驾车」

#### 3.2.6 关于「时长是快照」这件事

腾讯距离矩阵对 `mode=driving` 的官方说明：

> 「支持返回实时 ETA（结合路况的预估到达时间）」「支持依据实时路况计算路线距离和耗时」

**两个直接推论**：

1. **矩阵里的驾车时长是「生成时刻的路况快照」**，不是恒定量。所以：
   - `generatedAt` + `sampledAtLabel` **必须存**，且要在 UI 上如实显示（段的 Tooltip：「基于 2026-09-18 工作日上午路况估算」）
   - 构建脚本应尽量在**工作日上午**采样（贴近旅游出行的典型时段），并把采样时间写进 label
2. **步行与骑行时长不含路况** —— 这两种方式本来就不受机动车拥堵影响，因此数据比驾车更"耐久"，不需要频繁刷新

> ⚠️ **绝不能把快照说成实时**。这是产品诚实度的底线：一个 9 月生成的矩阵，在 12 月被当成"实时路况"展示，就是在误导用户。

> 💡 **这也解释了为什么"多路线备选"必须放在运行时**：矩阵只能给一个时长（快照），**给不出"哪条路更堵"**。用户要看实时路况下的多方案，只能实时调 `/ws/direction/v1/driving`（见 3.6）。

> ⚠️ **绝不能把快照说成实时**。这是产品诚实度的底线：一个 9 月生成的矩阵，在 12 月被当成"实时路况"展示，就是在误导用户。

### 3.3 运行时的三级时间来源

```ts
/** 六种出行方式 → 三种矩阵通道的映射 */
const MATRIX_CHANNEL = {
  driving:   'driving',
  taxi:      'driving',      // ★ 打车复用驾车的道路时长，只是费用不同
  bicycling: 'bicycling',
  walking:   'walking',
  transit:   null,           // 公交不含在矩阵里
  subway:    null,           // 地铁与公共同一接口，同样不含
} as const

/** 三层解析：静态矩阵 → 本地缓存 → 实时接口 */
async function resolveLeg(from: Place, to: Place, mode: TravelMode): Promise<LegResult> {
  // ① 静态矩阵（POI ↔ POI，驾车/打车/骑行/步行）—— 零调用，同步返回
  const channel = MATRIX_CHANNEL[mode]
  if (from.isPoi && to.isPoi && channel) {
    const hit = readLeg(matrix, from.poiIndex, to.poiIndex, channel)
    if (hit) return { ...hit, source: 'matrix' }
    return { source: 'not-applicable' }          // 该方式不适用 → UI 引导换方式
  }

  // ② localStorage 缓存（住宿点相关 / 公交地铁）—— 零调用
  const cached = legCache.get(legKey(from, to, mode))
  if (cached && !isStale(cached, mode)) return { ...cached, source: 'cache' }

  // ③ 实时接口
  return await fetchLegLive(from, to, mode)
}
```

**缓存策略**（`localStorage`，键含日期）：

| 方式 | 缓存有效期 | 理由 |
|------|-----------|------|
| 公交 / 地铁 | **7 天** | 时效性最强，且用户可能在出行前几天排行程、当天重看 |
| 驾车 / 打车 / 骑行 / 步行 | **30 天** | 相对稳定 |
| 住宿点相关（任意方式） | 同上方对应方式 | 住宿点固定后，同点对反复出现（每天出门/回来） |
| **多方案路线结果** | **2 小时** | ⚠️ 含实时路况，**必须短 TTL** —— 放一整天就失去意义了 |

> ⚠️ 微信内置浏览器的 `localStorage` 配额更严（见 08 文档 6.3）。所以缓存要做**上限控制**：最多保留 300 条，超出按 LRU 淘汰。

### 3.4 实时接口的两种实现路径

住宿点相关与公交需要实时调用时，有两条路：

| 路径 | 优点 | 缺点 | 用在哪 |
|------|------|------|--------|
| **JS API 服务类**（`TMap.service.Driving` / `Transfer` / `Walking` / `Bicycling`） | 复用已加载的 SDK，无额外 HTTP 往返；**能直接拿到解压后的 `polyline` 用于画折线**；同样支持 `get_mp` 多方案 | 依赖地图 SDK 已加载（但我们要求"地图挂了行程也能用"，所以不能只靠它） | **首选** |
| **Web 服务 API**（`/ws/direction/v1/*`、`/ws/distance/v1/matrix`） | 不依赖 SDK，可用 key 直接 HTTP；**矩阵的批量能力只有这一条路** | 需要 Web 服务 key 也暴露在前端；多一次往返；`polyline` 要自己解压 | **降级后备 + 构建期专用** |

**结论**：首选 JS API 服务类；SDK 未加载或失败时，退化为 **Web 服务 API**；两者都不可用时，退化为**直线距离 × 方式系数估算**并标注「估算」。

```ts
// 住宿点 → 当天所有点：一次批量拿全（矩阵接口的"一对多"能力）
async function fetchStayToDay(stay: Stay, points: Place[], mode: TravelMode) {
  const channel = MATRIX_CHANNEL[mode]
  if (!channel) return null                       // 公交/地铁不走矩阵

  // ★ 一对多：1 个起点 → 最多 200 个终点，当天点位远少于 200 → 一次调用搞定
  const to = points.map((p) => `${p.lat},${p.lng}`).join(';')     // ★ 纬度在前
  const url = `https://apis.map.qq.com/ws/distance/v1/matrix` +
              `?mode=${channel}&from=${stay.lat},${stay.lng}&to=${to}` +
              `&key=${webKey}`
  const res = await fetch(url).then((r) => r.json())
  if (res.status !== 0) throw new Error(res.message)

  return res.result.rows[0].elements.map((el: any) => {
    // ⚠️ 单个元素可能失败（附近 5km 无道路）→ distance 退化为直线距离且无 duration
    if (el.status === 4 || el.duration == null) return { source: 'unavailable' as const }
    return { distance: el.distance, duration: el.duration, source: 'live' as const }
  })
}
```

> 💡 **一对多在这里省了一次批量**：住宿点 → 当天 8 个点，逐段算要 8 次；用一对多**只要 1 次**。
>
> ⚠️ 注意矩阵的 `from` / `to` 是**方向性**的：上面只算了「住宿点 → 各点」。若需要「各点 → 住宿点」，要把 `from`/`to` 反过来再调一次。由于我们只存上三角做往返均值，住宿点相关的段**建议两次都调**，取均值后写入缓存 —— 反正一对多很便宜。

### 3.5 配额账本（必须做，不能只靠控制台）

因为**运行时的 key 可能是内置的受限 key**（见 07 文档第八节），必须在前端自带一层"消费上限"，防止被单点滥用把配额打满：

```ts
// app/itinerary/quotaLedger.ts
interface QuotaLedger {
  date: string                     // '2026-09-18'
  counts: Record<TravelMode, number>
  /** 多方案路线单独计数 —— 它比单段查询贵（一次拿 3 条方案） */
  routeOptions: number
}

/**
 * 单日上限（前端自设，远低于腾讯的 10,000/接口/日）
 *
 * 设这么低不是为了"省"，而是为了**防单点滥用**：
 * 一个用户正常一天最多排几十段，300 已是很宽松的余量；
 * 若某天突然接近 300，说明要么有 bug 在循环调用，要么有人在爬。
 */
const DAILY_CAP: Record<TravelMode, number> = {
  driving: 300, taxi: 200, transit: 300, subway: 300, bicycling: 200, walking: 100,
}
const ROUTE_OPTIONS_CAP = 100      // 多方案查询：更贵，上限更低
```

| 触发 | 行为 |
|------|------|
| 单日某方式累计 > 上限 | **停止实时调用**，退化为估算，并在行程面板顶部提示「今日实时路况额度已用完，时长改为估算值」 |
| 多方案查询 > 100 次/日 | 停止自动拉多方案，仅保留用户手动点开时拉一次 |
| 使用**用户自备 key** | 账本照常记录，但**不设上限**（配额是他自己的） |

> 这个账本还兼一个作用：**让用量可观测**。开源项目最怕"不知道谁把配额刷没了"，本地账本 + 腾讯控制台的配额告警构成双保险。
>
> 💡 **腾讯的配额模型让账本更好设计**：日配额按接口独立，所以"驾车用超了"不会影响"公交可用"，各方式的计数天然隔离。

### 3.6 多路线备选（"考虑堵车"的落地方式）

**用户的原话是："这些应该是都要多种路线可选的，毕竟要考虑堵车的情况。"**

这句话拆开是两件事，腾讯分别有对应的能力：

| 用户要的 | 腾讯的能力 | 参数 |
|---------|-----------|------|
| **多种路线可选** | 一次请求返回**最多 3 条备选方案** | `get_mp=1` |
| **考虑堵车** | 返回**路况配速**（哪段堵、堵到什么程度） | `get_speed=1` |
| （隐含）参考实时路况算时长 | 默认策略即参考实时路况 | `policy=LEAST_TIME` |

#### 3.6.1 为什么矩阵给不了多方案

**这是必须理解的一点**：预计算矩阵只存 `distance` + `duration` 两个数，**存不了"有哪些路线可选"**。而且矩阵里的驾车时长是**生成时刻的路况快照**，给不出"现在哪条路更堵"。

所以多方案**只能在运行时拉**。这带来一个必须处理的成本问题：

```
朴素做法（错）：
  一进行程页 → 把所有段的 3 条方案都拉了
  → 一天 8 段 × 3 条 = 24 次调用，用户可能根本不会看大部分段

正确做法：
  默认只用矩阵的时长做汇总展示
  用户【点开某一段】时才拉该段的多方案 → 1 次调用
```

| 时机 | 行为 |
|------|------|
| 进入行程页 | **不拉**多方案。时间轴显示矩阵时长（标注"路况快照"） |
| 点开某一段 | 拉该段的 3 条方案 → 展开方案卡片（**1 次调用**） |
| 切换方案 | **不重新请求**（3 条已在手），只切换地图高亮与时间链取值 |
| 关掉该段 | 结果留在缓存（**2 小时 TTL**，因为含实时路况） |

#### 3.6.2 请求与展示

```ts
// app/itinerary/routeOptions.ts
async function fetchRouteOptions(from: Place, to: Place, mode: TravelMode) {
  // 公交/地铁走 transit 接口（也有多方案，但参数不同）
  const endpoint = mode === 'transit' || mode === 'subway' ? 'transit' : 'driving'

  const url = `https://apis.map.qq.com/ws/direction/v1/${endpoint}` +
              `?from=${from.lat},${from.lng}&to=${to.lat},${to.lng}` +   // ★ 纬度在前
              `&get_mp=1` +                 // ★ 多方案（最多 3 条）
              `&get_speed=1` +              // ★ 路况配速
              `&policy=LEAST_TIME` +        // 默认：参考实时路况，时间最短
              `&key=${webKey}`

  const res = await fetch(url).then((r) => r.json())
  if (res.status !== 0) throw new Error(res.message)

  return {
    routes: res.result.routes.map((r: any) => ({
      distance: r.distance,             // 米
      duration: r.duration,             // ⚠️ 分钟（矩阵是秒，别混）
      polyline: r.polyline,             // 压缩点串，需解压后才能画线
      toll: r.toll,                     // 过路费（元）
      tags: r.tags,                     // ['LEAST_LIGHT'] 等方案特色标签
      restriction: r.restriction,       // 限行信息
    })),
    taxiFare: res.result.taxi_fare?.fare,   // ★ 打车费（元）
  }
}
```

**方案卡片要展示什么**：

| 展示项 | 来源 | 说明 |
|--------|------|------|
| 时长 | `routes[i].duration` | 主角，字号最大 |
| 距离 | `routes[i].distance` | 次要信息 |
| 方案标签 | `routes[i].tags` | 如「少红绿灯」「少收费」，作为副标题 |
| 过路费 | `routes[i].toll` | 有值才显示 |
| 打车费 | `taxi_fare.fare` | **仅在方式 = 打车时显示**，且必须标「预估」 |
| 拥堵 | `get_speed=1` 返回的道路速度 | 把速度低于阈值的路段在地图线上**用醒目的颜色标出** |

```
┌─ 第 2 段 · 驾车 ────────────────────────────────────┐
│ ● 方案 A   23 分钟 · 5.2 km    [少红绿灯]   ← 选中   │
│ ○ 方案 B   28 分钟 · 6.8 km    [少收费]             │
│ ○ 方案 C   31 分钟 · 4.1 km    [避堵] 过路费 ¥10    │
│                                                     │
│ 路况：2 处缓行 · 预计最慢路段 18 km/h                │
│ [ 换成打车 ]  打车约 ¥18（预估）                     │
└─────────────────────────────────────────────────────┘
```

#### 3.6.3 三个必须注意的点

1. **`get_mp=1` 不保证一定返回 3 条** —— 有些点对可能只有 1 条可行路线（或返回 `SHORT_DISTANCE` 策略下恒为 1 条）。UI 必须能优雅处理「只有 1 条方案」的情况，**不能假设一定是 3 条**
2. **打车费必须标「预估」** —— 它不含动态调价、不含拥堵时长溢价。**把它显示成准确值就是误导**
3. **路况是查询时刻的，不是行程当天的** —— 用户上午排晚上的行程，看到的路况是上午的。段的 Tooltip 要如实写「基于查询时刻路况」，不能暗示"出发时就是这样"

> ⚠️ 这三条都指向同一个产品原则：**这个功能能给"参考"，不能给"承诺"**。措辞上一律用「预计」「约」「预估」，不用「将」「会」。

## 四、数据模型

### 4.1 三张核心结构

```ts
// shared/schema.ts（与静态数据结构对齐；行程本身不入仓库，只存 localStorage）

/** 住宿段：支持中途换住宿（用户明确选择"多日、可中途换住宿"） */
export interface Stay {
  id: string                       // 本地生成，如 'stay-1'
  name: string                     // '春熙路某酒店' 或用户自填
  lng: number
  lat: number
  /** 来源：从 POI 里选 / 用户搜索地址（走地理编码）/ 地图上点选 */
  source: 'poi' | 'geocoded' | 'picked'
  /** 若来自 POI 或地理编码，留一份原始信息便于展示 */
  ref?: { poiId?: string; address?: string }
  /** 归属天数区间（闭区间，从第 1 天计） */
  fromDay: number                  // 1
  toDay: number                    // 2
}

/** 一天 = 一个有序点位列表 + 该天的起点终点（由 Stay 决定） */
export interface ItineraryDay {
  /** 归属的住宿段 id —— 支持"前几天住 A 区、后几天住 B 区" */
  stayId: string
  /** 出发时间，'09:00' */
  startTime: string
  /** ★ 有序列表：顺序完全由用户决定，系统不重排 */
  items: DayItem[]
}

export interface DayItem {
  /** 本地唯一 id（同一 POI 可在同一天出现两次，如两次经过某地） */
  uid: string
  poiId: string                    // 指向 city.pois
  /** 停留时长（分钟）。默认取 poi.practical.durationMinutes，用户可改 */
  dwellMinutes: number
  /** 到下一个点的交通方式。最后一项不需要 */
  modeToNext?: TravelMode
  note?: string                    // 用户备注，如"这里想多待一会儿"
}

export type TravelMode = 'driving' | 'taxi' | 'transit' | 'subway' | 'bicycling' | 'walking'
/** 矩阵只覆盖这三种通道（taxi 复用 driving、transit/subway 不预计算） */
export type MatrixChannel = 'driving' | 'walking' | 'bicycling'
```

#### 4.1.1 住宿点的三种输入方式（用户原话："自己在地图上标，或者接入地图 API 的搜索"）

住宿点是行程的锚。它的特殊性在于：**不在我们的 POI 表里**，可以是任何坐标。所以必须支持三种输入：

| `source` | 交互 | 依赖 | 配额消耗 |
|----------|------|------|---------|
| `'poi'` | 从城市 POI 列表里选一个（比如直接选"春熙路"作为落脚点） | 无 | **0** |
| **`'picked'`** | **在地图上点一下 / 拖动 marker 微调** | 需要地图 SDK | **0**（纯前端拿坐标） |
| **`'geocoded'`** | **输入关键词搜索**（"成都东站附近酒店"），从候选里选 | 需要 `TMap.service.Suggestion`（输入提示）+ `Search`（地点搜索） | ⚠️ **消耗搜索接口配额** |

**为什么三条路都要有**（它们覆盖的是不同精度需求）：

```
用户已经想好了住哪个酒店，知道名字  → 搜索（geocoded）最准
用户只知道"想住在春熙路一带"        → 搜索"春熙路" 再选，或直接地图点选
用户看着地图觉得"这个位置不错"      → 地图点选（picked）最直接
```

**两个必须注意的点**：

1. **搜索会消耗配额** —— 腾讯的个人开发者配额是日 10,000 次/**接口**。搜索走的是搜索类接口。虽然日配额不低，但**必须在配额账本里单独计一档**（见 3.5），并做防抖（用户每打一个字就搜一次会很快烧掉）
2. **地图 SDK 挂了不能导致住宿点不能设** —— `'picked'` 依赖地图。地图不可用时**必须降级到 `'geocoded'`**（走 Web 服务 API，不依赖 SDK），或让用户手动填经纬度。**不能让"设置住宿点"这个功能整体失效** —— 它是行程规划的前提

```ts
// app/itinerary/StayPicker.tsx 的三路降级
const canPick = mapReady                                  // 地图可用 → 支持点选
const canGeocode = hasWebServiceKey                       // 有 Web 服务 key → 支持搜索
const canUsePoi = true                                    // 永远可用（纯静态数据）

// 至少要有一种可用，否则给"手动输入经纬度"的兜底表单
```

> 💡 **`'picked'` 的体验细节**：地图点选时给一个**可拖动的 marker**，而不是"点一下定死"。用户点完之后几乎总想微调几十米，直接定死会让他反复重选。

### 4.2 一个必须补的数据字段

**问题**：POI 数据里已有 `practical.duration`，但它是**自然语言**（"建议 3-4 小时"），**不能直接参与计算**。

**解决**：在 `PoiSchema.practical` 中新增**结构化**的停留时长（与现有字段并存，不替换）：

```ts
practical: z.object({
  duration: z.string().optional(),              // 现有：'建议 3-4 小时'（给人看）
  /** ★ 新增：结构化停留时长，给行程规划算时间用 */
  durationMinutes: z.tuple([z.number(), z.number()]).optional(),   // [180, 240]
  // ...
})
```

**取默认值的三级降级**：

```
① poi.practical.durationMinutes[0]         ← 数据里有就用（景点这类最需要）
   ↓ 没有
② 按分类的默认值（写在配置里，不是硬编码在组件里）
      scenic  120 min   景点
      food     60 min   美食
      hotspot  45 min   网红打卡
      culture  45 min   城市特色
   ↓ 用户手动改
③ 用户设定值（存在行程里，覆盖上面两者）
```

> ⚠️ **默认值必须显式可见**。时间轴上用一个淡色标记「默认 120 分钟 · 点击修改」，让用户知道"这个数字是系统猜的"，而不是把它当成事实。

### 4.3 存哪里

| 数据 | 存放 | 理由 |
|------|------|------|
| 通勤矩阵 `transit` | **进仓库**（`data/cities/{id}.json`） | 构建期生成，与用户无关，是全站公共资产 |
| 城市 / POI | 进仓库 | 同上 |
| **Stay / ItineraryDay / DayItem** | **`localStorage`** | 是用户的个人产物，且纯静态站无后端 |
| `legCache`（实时结果缓存） | `localStorage` | 同上传，带上限与 LRU |
| `quotaLedger` | `localStorage` | 用量记账 |
| 分享链接 | URL hash（`#itin=<base64>`） | 纯前端可解，无需后端。见第八节 |

## 五、时间链推导

### 5.1 模型

用户自己排顺序，所以推导逻辑是**一条直线**，没有任何搜索或优化：

```
Day 的完整链条（以 1 个住宿点 + 3 个点位为例）：

  09:00  住宿点出发
          │ Leg 1：驾车 18 分钟 · 4.2 km
  09:18  到达 宽窄巷子
          │ 停留 90 分钟
  10:48  离开 宽窄巷子
          │ Leg 2：步行 12 分钟 · 0.9 km
  11:00  到达 人民公园
          │ 停留 60 分钟
  12:00  离开 人民公园
          │ Leg 3：步行 8 分钟 · 0.6 km
  12:08  到达 某火锅店
          │ 停留 75 分钟（午餐）
  13:23  离开 某火锅店
          │ Leg 4：驾车 26 分钟 · 8.1 km
  13:49  到达 大熊猫基地
          │ 停留 180 分钟
  16:49  离开 大熊猫基地
          │ Leg 5：驾车 32 分钟 · 11.4 km
  17:21  回到住宿点

  在途 96 分钟 · 停留 405 分钟 · 合计 8 小时 21 分钟
```

```ts
/** 纯函数：给定一天的计划 + 矩阵，推导完整时间链 */
export function buildTimeline(day: ItineraryDay, stay: Stay, ctx: LegContext): Timeline {
  const stops = [
    { kind: 'stay' as const, place: stay },
    ...day.items.map((it) => ({ kind: 'poi' as const, item: it, place: poiOf(it.poiId) })),
    { kind: 'stay' as const, place: stay },      // ★ 末段回到住宿
  ]

  let t = parseTime(day.startTime)
  const legs: LegResult[] = []

  for (let i = 0; i < stops.length - 1; i++) {
    const mode = day.items[i]?.modeToNext ?? ctx.defaultMode
    const leg = resolveLegSync(stops[i].place, stops[i + 1].place, mode, ctx)
    legs.push(leg)
    t += leg.duration

    // 到达后加上停留（末段的"到达"是回住宿，无停留）
    if (stops[i + 1].kind === 'poi') t += stops[i + 1].item.dwellMinutes
  }

  return { startAt: parseTime(day.startTime), endAt: t, legs, /* ... */ }
}
```

**关键性质**：`resolveLegSync` 对矩阵命中的段是**同步纯函数**。这意味着拖拽排序时**可以每帧重算**，交互是零延迟的。只有遇到需要实时调用的段（公交 / 住宿点相关）才异步补齐 —— 实现上先用缓存值或占位，异步结果回来后重算一次。

### 5.2 过载提示（这是"算时间"最有价值的地方）

时间链算完，能给出**基于事实**的产品提示：

| 判断 | 提示 |
|------|------|
| 结束时间 > 22:00 | 「行程排到 22:47，可能过晚 · 建议减少 1 个点位」 |
| 在途时间 > 停留时间的 50% | 「路上耗掉 2 小时 40 分，接近游玩时间的一半 · 建议把相近的点位安排在一起」 |
| 单段通勤 > 60 分钟 | 「第 4 段需 68 分钟，是全天最长的一段 · 考虑换个顺序」 |
| 某方式不适用导致绕远 | 「步行不适用（12.3 km）· 已按驾车估算，或考虑删掉该点」 |

> ⚠️ **这些提示都是"陈述事实 + 给建议"，不是"替你决定"**。措辞上避免祈使句（"建议"而不是"应该"），因为顺序的决定权在用户手里 —— 这跟 1.1 节的取舍一脉相承。

### 5.3 关于途经点上限

腾讯途经点上限 **30 个**（加起终点共 32 个节点）。而且本项目**按段调用** —— 每一段 Leg 是一次独立的路线请求，本来就不会把整天打包成一次调用。所以**实际上永远不会触及上限**。

这个约束只在一种未来场景下才需要处理：如果将来要做「整天一条连续路线」（一次请求画完整天的路径）。那时：

```
若 stops.length > 31：
  按 30 个途经点一段切开，逐段调用，把结果首尾相接
  → 提示用户「行程较长，已分段计算，总时长可能略有偏差」
```

> ⚠️ 即便如此也要防住 —— 不能把超限请求直接发出去（腾讯会返回参数错误）。但**现阶段不需要实现这段逻辑**，记录在此备查。

#### 6.3.1 拥堵怎么在地图上表达

`get_speed=1` 返回的是**道路速度**，需要映射成视觉：

| 速度区间 | 表达 |
|---------|------|
| ≥ 40 km/h | 畅通 —— 用该段的基准色 |
| 20–40 km/h | 缓行 —— 橙色描边 |
| < 20 km/h | 拥堵 —— 红色描边 |

**做法**：同一条路线画**两条线** —— 底层是基准色粗线，拥堵路段在**上层叠一段红色细线**。比给整条线换色更准确（用户能看出"堵的是哪一段"）。

> ⚠️ **不要把拥堵路段做成动态流光的"蚂蚁线"** —— 那是导航 App 的语言，会让人误以为这是实时导航。我们给的是"查询时刻的快照"，静态描色更诚实。

## 七、数据采集侧（与 04 文档配套）

通勤矩阵的生成属于构建期流水线，新增为 **step6_transit**。要点在此列出，完整实现见 04 文档。

| 项 | 要点 |
|---|------|
| 接口 | `/ws/distance/v1/matrix`，按 25×25 分块，三条通道（`mode=driving` / `walking` / `bicycling`）各 4 次请求 |
| 触发时机 | 在 step3 地理编码**之后**（必须有最终坐标才能算通勤） |
| 采样时段 | **工作日上午**（贴近旅游出行典型时段，且驾车含路况） |
| **并发控制** | ⚠️ 腾讯并发限制 **5 次/秒** —— 请求必须**串行 + 退避**，不能并发轰炸 |
| 断点续跑 | 每完成一个目的地就落盘一次，中断后从 `_generated/transit.progress.json` 续 |
| 用量记账 | ⚠️ 按 **"计算次数"** 记账（不是请求数）；**超过 12,000 次/城时告警**（防脚本 bug 打满配额） |
| 幂等性 | 已存在的 `transit` 且 `generatedAt` 在 180 天内 → 跳过（避免重复计费） |
| 质量校验 | 覆盖率（驾车通道非 `0000` 的比例应 > 95%）、`duration` 无 0、`distance` 与直线距离的比值在合理区间（如 1.0–3.0 倍）、**逐元素检查 `status ≠ 4`** |

**刷新策略**：通勤矩阵**只在 POI 集合变化或每年一次**时重算，不做定期刷新（时长是快照，刷新频率高没有意义，反而消耗配额）。

## 八、导出与分享（纯前端）

| 能力 | 实现 |
|------|------|
| 导出 JSON | 序列化 `{ stays, days, cityId }` → `Blob` → 下载 `我的成都行程.json` |
| 导入 JSON | 文件选择 → Zod 校验 → 合并（同 uid 覆盖，不冲突的新增） |
| **分享链接** | 行程参数 → JSON → `LZ-string` 压缩 → base64 → `location.hash = '#itin=...'` |

```ts
// 分享链接是纯前端可解的，不需要任何后端
const payload = { c: cityId, s: stays, d: days.map(compact) }
const hash = `#itin=${LZString.compressToEncodedURIComponent(JSON.stringify(payload))}`
```

**为什么可行**：我们已经在城市页用 URL 承载状态（`/city/:cityId/poi/:poiId`）。分享链接是同一思路的延伸 —— **URL 是可分享状态的唯一载体**，而这恰好不需要后端。

> ⚠️ 链接长度要控制：12 个点位 + 2 个住宿段压缩后约 600–900 字符，可接受。若超 2,000 字符，退化为「导出 JSON」并提示用户改用文件分享。

## 九、降级策略（必须逐条实现）

| 场景 | 表现 |
|------|------|
| **未配置任何 key** | 矩阵仍可用（静态数据），行程规划**主体可用**。仅「自定住宿点（搜索/点选）」不可用（**降级为从 POI 里选**，见 4.1.1）与「公交/地铁」不可用（自动切驾车并标注） |
| **地图 SDK 加载失败** | 时间轴与时间链**照常完全可用**（矩阵不依赖地图实例）；地图区显示降级卡片；连线不显示；**住宿点的"地图点选"降级为"关键词搜索"**（走 Web 服务 API，不依赖 SDK） |
| **矩阵里该点对为 `0000`** | 该方式灰掉 + 提示可用的其他方式（见 3.2.5 的三通道对照） |
| **多方案查询失败 / 只返回 1 条** | 方案卡片降级为「仅一条路线」的紧凑展示，不报错、不空白（见 3.6.3 第 1 点） |
| **打车费（`taxi_fare`）缺失** | 隐藏该行，**不显示"费用未知"** —— 无信息比坏信息好 |
| **实时接口失败 / 超时（> 8s）** | 退化为「直线距离 × 方式系数」估算，段上标注**「估算」**（不能和真实值混在一起显示） |
| **配额账本超上限** | 停止实时调用，退化为估算 + 面板顶部提示「今日额度已用完」 |
| **localStorage 不可用**（隐私模式） | 行程改为内存态，提示「本次会话有效，关闭后将丢失 · 建议导出 JSON」 |
| **分享链接解析失败** | 提示「链接已失效或格式不兼容」，并给出「手动添加点位」的入口，不显示空白页 |

> 🔑 **底线**：**地图挂掉绝不能导致行程不可用。** 时间计算与地图是解耦的（矩阵是纯数据），实现时要守住这个边界 —— 不要把矩阵读取写成依赖地图实例的代码。

## ★ 行程的存储换地方了（2026-09-26，plans/13 §3.4）

| | 以前 | 现在 |
|---|---|---|
| 落到哪 | `localStorage[chexing:itin:<cityId>]`（一城一份） | **IndexedDB 的 `plans` store** 里"当前打开的那条规划" |
| 粒度 | 一座城市一份 | 一份**全局列表**，每条带自己的 `cityId` |
| 这一页渲染谁 | 路由参数 `:cityId` 指向的那座城 | **`planStore.activeId` 指向的那条规划** |

**没变的**：`days` / `stays` / `DayItem` / `chosenOption` 的结构**一字未改**，
时间链推导、过载提示、分享导出照旧吃这份数据。

**几条要注意的**：

- `useItineraryStore.init(cityId)` **已删**，改成 `attach(plan, rev)`。
  两道跳过守卫缺一不可：同一条规划且 `rev` 没变 ⇒ 不做（否则每次重渲染都会把
  `activeDay` / `activeLeg` 重置）；`rev === ownRev` ⇒ 不做（否则每敲一下输入框就重装一次，光标跳走）。
- **没有"打开任何规划"是一个正常入口态**：直接从收藏夹进 `/city/x/plan` 时 `activeId` 是空的，
  此时给的是一张"请先选一条"的引导屏（`PlanMissing`），**不是空行程** —— 后者会被读成"我的行程被清了"。
- `?add=<poiId>` 那条通路整条删掉：四个加点入口统一走 `useAddToPlan` —— **不换页**，
  而是弹一个「加到哪个组？」的窗（含新建组）。★ **每次点都弹**，没有「猜你要加到哪」的短路。
- 城市页那两个「我的行程」/「去排行程」入口也撤了：顶栏有全站的「路线规划」，做的是同一件事。

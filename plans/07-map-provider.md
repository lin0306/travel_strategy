> **本文件已两次反转结论，这次转回腾讯。必须把三次调整的脉络写清楚，否则后来者会以为方案在反复横跳。**

| # | 版本 | 结论 | 首要判据 | 触发原因 |
|---|------|------|---------|---------|
| 1 | 初版 | **腾讯** | 免费政策的长期性 | 需求只有"地图展示 + 地理编码"，腾讯免费无期限 |
| 2 | 上一版 | 高德 | 路线规划能力 | 新增行程规划，且**当时认为腾讯缺少批量距离测量** |
| 3 | **当前版** | **腾讯** | **批量矩阵 + 区划下钻 + 多方案路线** | ① 用户判断"高德麻烦"（`securityJsCode` 明文 + 1 年免费期）② **复核发现上一版的事实依据是错的** |

### 0.1 必须承认的错误

上一版第 2 节写了：

> 「腾讯位置服务……但缺少**批量距离测量**这类能一次性压掉上千次调用的接口形态」

**这句话是错的。** 腾讯位置服务有 `/ws/distance/v1/matrix`（距离矩阵），而且能力**强于**高德的 `/v3/distance`：

| | 高德 `/v3/distance` | **腾讯 `/ws/distance/v1/matrix`** |
|---|---|---|
| 单次容量 | 100 个坐标对（`origins` → 单个 `destination`） | **25 × 25 = 625 对**（多对多）；或 1 → 200（一对多） |
| 出行方式 | 直线 / 驾车 / 步行 | 直线 / 驾车 / 步行 / **骑行（bicycling）** |
| 实时路况 ETA | 驾车含路况 | ✅ 驾车含实时 ETA |
| 跨城 | 支持 | ✅ 支持跨城远距离 |
| 计量口径 | 按调用次数 | **按"计算次数"**（每对起终点计 1 次） |

**这个错误的后果很大**：上一版据此算出「骑行矩阵 1035 次/城（高德没有骑行批量，只能一对一调）」，并把这条列为方案的**最大成本痛点**。而在腾讯这边，骑行**有批量接口** —— 这个痛点根本不存在。

> ⚠️ **教训**：上一版的选型是拿"某一家缺什么"来论证的，但那个"缺"是**从二手文章的印象里来的，没有回到官方接口文档逐条核对**。凡是"某家没有 X 能力"这种判断，必须能在官方文档里找到**反面证据**（接口列表、参数表），否则不能作为选型依据。

### 0.2 这次变更的双重理由

用户提出换回腾讯，给了两点：**"高德麻烦"** + 要加**三级地图下钻**。复核后发现这两点技术上都成立：

1. **高德确实更麻烦**：额外一层 `securityJsCode`（且官方首选方案是服务端代理，我们无后端）、免费配额仅 1 年 → 换回腾讯直接消除这两个代价
2. **下钻需求也指向腾讯**：三级下钻需要行政区划边界，腾讯 District 服务返回的每个区划**自带 `location` 中心点**（省了自己算质心），生态更顺

> 结论不是"用户想换就换"，而是：**上一版的核心论据被证伪后，原来的权衡表格子里的数字全变了，重算一遍结论就是腾讯。** 下面第 2 节给出重算后的完整判据。

## 三、配额（腾讯官方口径）

### 3.1 个人开发者默认配额

| 项 | 值 |
|----|----|
| 日调用量 | **10,000 次 / 日** |
| 并发限制 | **5 次 / 秒** |
| 计费方式 | **按接口独立计算** —— `/ws/geocoder/v1`、`/ws/place/v1/search`、`/ws/distance/v1/matrix`、`/ws/direction/v1/*`、`/ws/district/v1/*` **各有各的 10,000/日** |
| 免费期限 | **未设期限** |
| 提额 | 个人开发者不提额；企业认证后可申请 |

> 来源：腾讯位置服务官方 FAQ「如何成为腾讯位置服务开发者」`mapapi.qq.com/web/lbs/wechatOfficialAccount/wxArticles/newFaq/quota_faq.html`

**这与高德是完全不同的模型**：

| | 腾讯 | 高德 |
|---|---|---|
| 周期 | **日**（每天重置） | 月（一年内累计） |
| 池子 | **按接口独立** | 路径规划与地理编码**共享**一个池子 |
| 期限 | **永久** | 认证起 1 年 |

> 💡 **"按接口独立 + 日重置"对我们其实是好事**：通勤矩阵用的是 `/ws/distance/v1/matrix`，地理编码用的是 `/ws/geocoder/v1`，**两者不抢配额**。而高德那边它们是共享的 —— 采集期密集跑地理编码会挤掉矩阵的额度。

### 3.2 距离矩阵的计量口径（最容易算错的一点）

官方原文：

> 「本接口按距离的**计算次数**计量（非接口请求次数）：每计算一对起终点距离，计为 1 次。
> 例如：一次接口请求计算 10 个起点到 10 个终点，计算次数为 100 次。」

⚠️ **所以"1 次请求"可能是"625 次计算"**。按请求数估配额会低估 600 倍。下面的成本账全部按**计算次数**算。

## 四、这个选择没有代价吗？有，但比高德小

### 4.1 代价一：标注避让要自研（唯一的能力短板）

高德把避让做成了图层级开箱特性（`collision` + `rank`），腾讯没有。46 个 POI 在 zoom 12–14 会大面积叠字。

**这不是"做不到"，而是"要自己做"**：按 `popularity` 分层 + 按 zoom 档位控制显示密度 + 高优先级点常显。方案见 [03 文档第三节](./03-map-interaction.md)。

> 权衡：**用一个自研的 50 行避让逻辑，换掉一整套安全密钥机制 + 1 年的免费期悬崖**，这笔交易是划算的。

### 4.2 代价二：日配额 + 并发 5/秒

- **日配额**：单接口 10,000/日。矩阵跑一个城市的三种方式约 7,500 次计算 → **一天跑不完两个城市**（如果都走矩阵接口）
- **并发 5/秒**：构建期不能让脚本并发轰炸

**对冲手段**：
1. **断点续跑**（每完成一批落盘，允许跨天接着跑）
2. **阈值裁剪**：步行只算 ≤3km 的点对、骑行只算 ≤8km —— 用本地 haversine 预筛，只把符合条件的点对塞进请求
3. **幂等跳过**：已有 `transit` 且 `generatedAt` 在 180 天内 → 跳过，不重复计费

详见 [04 文档第六节](./04-content-pipeline.md)。

### 4.3 代价三：矢量样式定制弱于高德

腾讯的个性化地图是在控制台编辑（绑 `mapStyleId`），元素粒度不如高德的 GeoHUB（42 类）。

**判断**：本项目需要的只是"低饱和暖调底图 + 弱化 POI 文字，让 marker 成为视觉焦点"。腾讯完全能做，差距落在极致定制上，而我们的需求并不极致。

### 4.4 相比高德省下来的两件事

| 高德的负担 | 腾讯 |
|---|---|
| `securityJsCode` 必须明文放前端（官方标"不建议生产使用"），因为纯静态站无后端可代理 | **不需要第二把密钥**，只有 key + Referer 白名单 |
| 个人认证免费月配额**自认证起仅 1 年**，到期需付费或引导用户自备 key | **无期限** |

> ✅ 这两条正是上一版方案里用"用量小到代价可承受"来**勉强接受**的东西。现在不用接受了。

## 五、修正后的成本账（通勤矩阵）

### 5.1 为什么矩阵成本是本次选型的关键

行程规划要算「POI ↔ POI」的通勤时长。46 个点位两两组合的上三角是 **1,035 对**。三种方式（驾车/步行/骑行）合计 **3,105 对**。

| 做法 | 请求数 | 计算次数 | 说明 |
|------|-------|---------|------|
| 一对一循环单次 | 3,105 | 3,105 | 新手写法，网络往返 3,105 次，并发 5/秒 → 至少 10 分钟 |
| **腾讯矩阵（25×25 分批）** | **12** | **≈ 7,500** | 每方式 4 次请求（46×46 分 4 块，含冗余）；网络往返降到 12 次 |
| 腾讯矩阵（对 / 多，阈值裁剪后） | ~96 | ≈ 3,900 | 驾车全量 + 步行/骑行只算阈值内点对 |

**关键**：请求数从 **3,105 → 12**。并发限制是 5 次/秒，一对一写法要跑 10 分钟以上且极易触限流；矩阵写法**秒级完成**。

### 5.2 三个城市的实际用量

```
单城（46 POI，三种方式）：
  驾车矩阵   4 次请求 ≈ 2,500 计算次数
  步行矩阵   4 次请求 ≈ 2,500 计算次数（可阈值裁剪至 ~500）
  骑行矩阵   4 次请求 ≈ 2,500 计算次数（可阈值裁剪至 ~900）
  ────────────────────────────────────────
  合计       12 次请求 ≈ 7,500 计算次数

10 城合计    120 次请求 ≈ 75,000 计算次数
```

**对照配额**：矩阵接口 **10,000 计算次数/日**（日重置）。

> ⚠️ **一个诚实的结论**：**10 个城市无法在一天内跑完**（75,000 / 10,000 ≈ 8 天）。但这不是问题，因为：
> - 采集本来就是**增量 + 断点续跑**的，新增城市自然分散在不同日期
> - 阈值裁剪能把它压到约 3,900/城 → **一天能跑 2 个城市**
> - 日配额**每天重置**，不存在"一年用完就没了"

**对比高德**（上一版的账）：骑行没有批量 → 1,035 次一对一请求/城。同样是 10 城，请求数从 **12 次/城 → 1,127 次/城**，差 **94 倍**。

### 5.3 运行期用量

**默认零调用** —— 通勤时长读预计算矩阵。

只有两种情况实时调：

| 场景 | 方式 | 说明 |
|------|------|------|
| **用户自定住宿点** ↔ 当天点位 | `/ws/distance/v1/matrix` 一对多 | 住宿点不在 POI 表内，无法预计算。1 次请求覆盖当天全部点位 |
| **公交 / 地铁** | `/ws/direction/v1/transit` | 时效敏感且无批量接口，只对相邻点对算 |

两者都带 `localStorage` 缓存，且都受日配额 10,000 保护 —— 正常使用**远远用不到**。

## 六、能力细节（写代码时要用到的）

### 6.1 距离矩阵

```
GET https://apis.map.qq.com/ws/distance/v1/matrix
    ?mode=driving                            ← driving | walking | bicycling | straight
    &from=lat,lng;lat,lng;...                ← 多对多时 from×to ≤ 625 且单侧 ≤ 50
    &to=lat,lng;lat,lng;...
    &key={WEB_KEY}
→ result.rows[i].elements[j] = { distance(米), duration(秒) }
```

- **一对多**：`from` 1 个 → `to` 最多 200 个
- **多对多**：`from×to ≤ 625`，单侧 ≤ 50（即 25×25）
- ⚠️ **坐标格式是 `lat,lng`（纬度在前）** —— 与绝大多数 WebGIS 习惯相反，写反了返回结果全错且不好查
- ⚠️ **单个元素失败**：起终点附近 5km 内无道路时该元素返回 `status: 4`，`distance` 退化为**直线距离**且**不返回 `duration`**。必须逐元素判 `status`，不能直接读 `duration`
- `duration` 单位是**秒**（注意：路线规划接口的 `duration` 是**分钟**，两者不一致）

### 6.2 驾车路线规划（多方案 + 路况 + 打车费）

```
GET https://apis.map.qq.com/ws/direction/v1/driving
    ?from=lat,lng&to=lat,lng
    &get_mp=1            ← ★ 返回多方案（最多 3 条）
    &get_speed=1         ← ★ 返回路况配速
    &policy=LEAST_TIME   ← 默认，参考实时路况
    &key={WEB_KEY}
→ result.routes[] = { distance(米), duration(分钟), polyline, tags, toll, taxi_fare, restriction }
```

| 参数 | 取值 | 用途 |
|------|------|------|
| `policy` 策略（四选一） | `LEAST_TIME`（默认，参考实时路况）/ `PICKUP` / `TRIP` / `SHORT_DISTANCE`（不参考路况、仅一条路线） | 决定算路偏好 |
| 单项偏好（可多选，逗号分隔） | `REAL_TRAFFIC` / `LEAST_FEE` / `HIGHWAY_FIRST` / `AVOID_HIGHWAY` / `HIGHROAD_FIRST` / `NAV_POINT_FIRST` | 微调 |
| `get_mp` | `0`（默认，一条）/ `1`（**最多 3 条备选**） | **"多种路线可选"就靠它** |
| `get_speed` | `0` / `1`（返回路况） | **"考虑堵车"的可视化依据** |
| `waypoints` | 最多 30 个 | 行程里的多点多段 |
| `avoid_polygons` | 最多 32 个区域 | 手动避堵 |

**返回里与产品直接相关的两个字段**：
- **`taxi_fare.fare`** —— 估算打车费（元）→ **"打车"这个出行方式原生就有数据**，不需要自己按里程猜
- **`tags`** —— 方案标签（如 `LEAST_LIGHT` 少红绿灯）→ 可作为方案卡片的副标题

### 6.3 公交 / 地铁

```
GET https://apis.map.qq.com/ws/direction/v1/transit
    ?from=lat,lng&to=lat,lng&policy=LEAST_TIME&key={WEB_KEY}
```

- **公交与地铁同属 `transit`** —— 返回的换乘方案里会自动包含地铁段，不需要单独接口
- `policy`：`LEAST_TIME` 较快捷 / `LEAST_TRANSFER` 少换乘 / `LEAST_WALKING` 少走路
- `preference`：`NO_SUBWAY` 不坐地铁 → **"只要公交不要地铁"就是它**
- ⚠️ **仅支持同城**，跨城必须用驾车

### 6.4 骑行 / 步行

```
GET https://apis.map.qq.com/ws/direction/v1/bicycling   ← 骑行
GET https://apis.map.qq.com/ws/direction/v1/walking     ← 步行
```

腾讯还有 `ebicycling`（电动自行车）—— 本项目暂不需要，但可作为将来扩展。

### 6.5 行政区划（三级下钻的基础）

```
GET https://apis.map.qq.com/ws/district/v1/list              → 全国三级区划列表
GET https://apis.map.qq.com/ws/district/v1/getchildren?id=110000&get_polygon=1
                                                             → 子级区划 + 边界点串
GET https://apis.map.qq.com/ws/district/v1/search?keyword=北京&get_polygon=1
                                                             → 关键词匹配单个区划 + 边界
```

返回结构（每个区划）：

| 字段 | 说明 |
|------|------|
| `id` | adcode，6 位 |
| `name` / `fullname` | 简称（"内蒙古"）/ 全称（"内蒙古自治区"） |
| **`location`** | **中心点经纬度** —— 直接可用作"各省景点数"的标注锚点，**不需要自己算质心** |
| `level` | 几级区划 |
| `polygon` | 轮廓面点串（需 `get_polygon=1`） |
| `cidx` | 子级在下级数组中的下标位置 |

**adcode 规则**：

```
前 2 位 = 省（一级）      130000 = 河北省
中 2 位 = 市 / 地区（二级） 130600 = 河北省保定市
后 2 位 = 区县（三级）     130681 = 河北省保定市涿州市

⚠️ 特例：
  · 直辖市（北京/上海/重庆/天津）与港澳：省级下直接是区级，没有二级结构
  · 省直辖县：第 3、4 位为 90（如 419001）
  · 中国范围内非行政区划区域：999999（如东海）
```

**JS API 侧封装**：`TMap.service.District`，配 `POLICY_CONTAIN_CHILDREN` 可一次拿到子级。

> 🚨 **合规红线（本章最重要的一条）**：三级下钻的边界**只能来自腾讯 District 服务**。**绝对禁止**自己找第三方 GeoJSON 来画中国地图 —— 这是国家版图完整性问题（台湾、藏南、南海诸岛的表达），第三方数据极易出错且违反《地图管理条例》。详见 [10 文档](./10-map-drilldown.md) 第九节。

## 七、申请 Key（写进 README）

1. 打开 <https://lbs.qq.com> → 注册（QQ / 微信 / 手机号均可）
2. 完善**个人开发者**信息（真实姓名 + 手机 + 邮箱）→ 配额生效
3. **应用管理 → 我的应用 → 创建应用 → 添加 Key**
   - **Web 端（JavaScript API GL）**：不需要勾选任何产品权限，直接创建即可用
   - **必须配「域名白名单」**（填站点域名及其子域；微信内需额外加 `servicewechat.com`）
4. **再建一个 Key，勾选「WebService API」**，给构建期脚本用（地理编码 / 距离矩阵 / 区划）—— 建议同时配 **IP 白名单**或开 **SN 签名校验**
5. 填入环境变量：

```bash
# .env.example
# 前端（必然可见，护城河是域名白名单 + 配额告警）
VITE_TMAP_KEY=请到腾讯位置服务申请 JavaScript API GL key 并替换此占位符

# 仅构建期脚本用，永不进浏览器产物
TMAP_WEB_KEY=请另建一个勾选了 WebService API 的 key
```

> 💡 **两个 Key 的分工**：JS key 给浏览器（配域名白名单）；WebService key 给采集脚本（配 IP 白名单或 SN 签名）。分开的好处是**用量能分别统计**，且脚本 key 泄露不影响线上。

### 7.1 关于 key 泄露（把事实说清楚）

> 腾讯官方明确提示：「请尽量避免在网页端直接调用 WebService API，因为 Key 作为请求参数容易被抓取，被盗用的风险较高。」

但 **JS API 的 key 在浏览器里必然可见**，这是浏览器机制而非平台缺陷。护城河只有两样：

1. **Referer 域名白名单**（必配）
2. **配额告警**（异常流量能及时发现）

**腾讯相比高德的优势**：只需要保护**一把** key。高德还要额外暴露 `securityJsCode`，且服务端调用不受 Referer 约束 —— 暴露面大一倍。

### 7.2 多域名 / 预览站的坑

Netlify 的 Deploy Preview 会生成随机子域名。若不在白名单里，预览站地图会报错。两种处理：

- 把预览域名加进白名单（域名白名单支持子域）
- 或接受"预览站地图不可用"，靠 `MapFallback` 降级卡片兜住（列表与详情仍完全可用）

## 八、开源使用者的 key 策略：双 key 模式

### 8.1 问题

**纯静态 + 开源**这个交集下没有完美解：

- 内置维护者的 key → 全站共享一份配额，且被盗刷风险由维护者承担
- 完全不内置 → clone 后必须自己申请 key 才能看到地图，传播体验差

### 8.2 方案：内置「受限 key」+ 允许使用者覆盖

**运行时 key 解析优先级**（高 → 低）：

```
① localStorage 里用户自填的 key            ← 使用者自备，配额与风险都在他自己账号
② 构建期注入的环境变量 key（内置受限 key）  ← 兜底，开箱即用
③ 都没有 → 不初始化地图，走 MapFallback     ← 绝不能白屏
```

```ts
// app/map/tencent/config.ts
/** 三层 key 解析：用户自填 > 构建期注入 > 缺失降级 */
export function resolveTmapKey(): string | null {
  const user = localStorage.getItem('tmap:userKey')      // 使用者自备
  if (user?.trim()) return user.trim()

  const key = import.meta.env.VITE_TMAP_KEY
  if (!key || key.startsWith('请')) return null          // 占位符 = 未配置
  return key
}
```

**「受限 key」是什么意思**：内置 key 只配**域名白名单**、不开任何提额、开启**配额告警**。它的定位是"让 clone 者打开就能看到效果"，不是"给所有人免费用"。

**提供设置入口**：设置浮层里给一个「使用我自己的腾讯地图 Key」输入框，填写后写入 `localStorage` 并提示刷新。

> ✅ 比起高德，腾讯这边这个机制简单得多 —— **没有安全密钥要用户也一起填**，一个输入框就够。

### 8.3 开源仓库的纪律

- ❌ **绝不把可用的 key 提交进仓库**。`.env` 进 `.gitignore`，只提交 `.env.example`
- ✅ README 写清「如何申请 + 如何替换」，让 fork 者 5 分钟跑起来
- ✅ 生产 key 只从 CI / 托管平台的环境变量注入

## 九、适配层契约与「再换平台」成本

效果与生态差异是真实的，所以要给"将来换平台"留后路。但**不要现在就写多套实现** —— 接口存在的意义是"换的时候不用重写业务"，不是"提前支持多家"。

### 9.1 三个接口契约

```ts
// app/map/provider/types.ts
// 业务代码只依赖这些接口，不直接 import 任何地图 SDK
export interface MapProvider {
  readonly id: 'tencent' | 'amap' | 'baidu'

  mount(el: HTMLElement, opts: MountOptions): Promise<void>
  setBaseMap(kind: 'vector' | 'satellite'): void
  onZoomChange(cb: (zoom: number) => void): () => void
  setPois(pois: Poi[]): void
  focus(poi: Poi): void
  destroy(): void
}

// app/map/provider/route.ts —— ★ 路线规划独立成第二个接口
export interface RouteProvider {
  readonly id: 'tencent' | 'amap' | 'baidu'

  /** 单次路线查询（起终点 + 途经点 + 出行方式）—— 运行时按需用，返回多方案 */
  route(req: RouteRequest): Promise<RouteResult[]>

  /** 批量「多对多」距离与时长 —— 构建期生成通勤矩阵用 */
  batchDistance(req: BatchDistanceRequest): Promise<LegEstimate[][]>
}

// app/map/provider/district.ts —— ★ 行政区划独立成第三个接口（本轮新增）
export interface DistrictProvider {
  readonly id: 'tencent' | 'amap' | 'baidu'

  /** 全国三级区划树（不带边界，体积小，构建期固化） */
  list(): Promise<DistrictNode[]>

  /** 指定区划的子级 + 边界点串（按需拉取，带缓存） */
  children(adcode: string, withPolygon: boolean): Promise<DistrictNode[]>
}

export type TravelMode = 'driving' | 'taxi' | 'transit' | 'subway' | 'bicycling' | 'walking'
export interface LegEstimate { distance: number; duration: number }   // 米 / 秒
export interface RouteResult extends LegEstimate { polyline?: string; toll?: number; taxiFare?: number; tags?: string[] }
```

`app/map/tencent/tmapProvider.ts` / `tmapRoute.ts` / `tmapDistrict.ts` 是唯一实现。UI 层只认接口。

### 9.2 假如要换到高德，要改什么

| # | 变更点 | 成本 |
|---|--------|------|
| 1 | 坐标系 | **不用改**（同为 GCJ-02），现有 POI 坐标与通勤矩阵都可用 |
| 2 | SDK 加载 | `map.qq.com/api/gljs` → `webapi.amap.com/maps?v=2.0`；**并新增 `securityJsCode` 这套机制** |
| 3 | 底图切换 | `setBaseMap(BaseMap)` → 图层叠加 `map.add/remove(TileLayer)` |
| 4 | 标注 | `MultiMarker` + 自研避让 → `LabelsLayer` + `LabelMarker({collision})`（**反而变简单**） |
| 5 | 视野适配 | `fitBounds({padding})` → `setBounds(bounds, immediately, avoid)`（**也变简单**） |
| 6 | **批量距离矩阵** | `25×25` → `origins≤100 → 单 destination`，**且失去骑行批量** → 骑行矩阵需 1,035 次一对一调用 |

**第 6、8、9 条是换回高德的真实代价** —— 那正是我们这次离开它的理由。

> 适配层的价值：真要换时只改这几个 provider 文件，不动 UI、数据结构与业务逻辑。

## 十、触发重新评估的条件

出现以下任一情况时，重新跑一次本节的评估：

- **腾讯的距离矩阵接口变更为收费 / 下线**（会直接推翻第 1 条判据）
- 腾讯日配额（10,000/接口）被下调，或新增"免费期限"限制
- 项目需要商用（腾讯商用授权需另行申请）
- 需要**跨城公交路线**（腾讯 `transit` 仅支持同城）→ 可能需要补第二家
- 城市规模增长到单城 POI > 300（矩阵计算次数会以平方增长）
- 高德的 `securityJsCode` 出现纯静态替代方案（如纯 Referer 校验）且免费期取消

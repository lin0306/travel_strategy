## 二、对既有设定的调整（**不是推翻**）

> ★ 2026-09-25 用户确认：「**规划最开始的方案是保留的**，我现在提的是在旧的基础上丰富」。
> ⇒ **`stays`（住宿段）/ `days`（天数）/ `timeline`（时间链）三件套全部保留**，
> 本方案**一行都不删**，只在它们上面加：多记录 / 历史列表 / 双浮层 / 自由取点 / 真实折线 / 折线落盘。

要调的只有两处，且都是**顺应你新需求**的，不是否定原设计：

### 2.1 「详情只留一块浮层」→ 左右双浮层

现在 `check_app.py` **Y⑧** 要求「点景点弹出来的**只有一块浮层**」（原型阶段的结论：多一块既是遮挡、又是第二个出口）。  
你的新形态**明确要求两块**（左景点详情 + 右路线规划）。所以：

- Y⑧ 的判据从「恰好 1 个 Overlay」改成「**恰好这些**：详情 ≤1 且（有规划面板时）规划 ≤1」——即**两类各最多一个**，  
  继续禁的是「同一次点击弹出两块同类浮层」那种真重复。
- **连带必须改**：`map/tencent/fitView.ts` 的浮层实测。它是"把点框进没被浮层盖住的地方"，  
  依据是页面上**所有** `data-overlay` 元素算空闲矩形。左右两块一起占位之后，  
  城市页的取景要重新验一遍（否则点位会被右侧面板盖住，而这**不报错**，只是"看着偏了"）。
- 文档：`plans/03`（6.x 浮层章节）· `plans/05`（浮层清单与宽度 token）· `plans/09`（6.1 双视图）。

### 2.2 「多方案结果不落盘」→ 落盘，但**只落几何与耗时**

09 文档 §4.3 的原判断是：路线结果含**实时路况**，2 小时 TTL，落盘会让用户第二天看到昨天的快照。  
这条判断**没错**，所以不是简单推翻，而是拆开：

| 落盘                               | 不落盘           |
| -------------------------------- | ------------- |
| 折线几何（`path`）· 距离 · 耗时 · 用户选的那条方案 | 「此刻哪条路堵」的实时结论 |

配套三条硬约束（都要进 UI）：

1. 每条路线**必须带计算时刻**（沿用 `routeProvenanceNote()` 的措辞：「路况为 xx:xx 查询时刻的快照」）；
2. 详情面板上&#x6709;**「重新规划」**&#x6309;钮，一键重算；
3. 超过 TTL 的路线在界面上**降级显示**（灰一档 + 一句「已过期，建议重新规划」），而不是默默当作最新。

> 这才是"省调用次数"的正确形态：**不重算的是几何**（几何不会变），该重算的是**实时耗时与路况**。

## 三、数据模型

### 3.1 现状的容器

```
STORAGE_KEYS.itinerary(cityId)   →  { stays, days, defaultMode, chosenOption }
它是「一座城市一份行程」：按天的点位表 + 住宿段 + 时间链
DayItem = { uid, poiId, dwellMinutes, modeToNext?, note? }   ← ★ 只有 poiId
```

### 3.2 新增：规划记录（Plan）

```ts
export interface RoutePlan {
  id: string
  name: string                 // 默认「未命名规划」，可改
  cityId: string               // 属于哪座城市（打开它 = 切到该城地图 + loadCity）
  createdAt: number
  updatedAt: number            // ★ 记录列表按它倒序（= 你说的"最近规划时间"）
  mode: TravelMode             // 整条统一；逐段覆盖见 §3.4
  chosenOption: Record<string, string>  // 逐段选中的备选方案（uid → 'A'|'B'|'C'）
  stays: Stay[]                // ↓ 与旧行程同构，一字未改
  days: ItineraryDay[]
  route: PlanRoute | null      // 算过才有；没算过 / 算失败 = null
}
```

> ### 修订（2026-09-25 落地时，与上面初稿的两处不同）
>
> **① 没有 `stops` 字段 —— 途经点序列是「算出来的」，不是「存的」。**
>
> 初稿把它列成一个字段（`stops: PlanStop[]`）。落地时看清楚了：`stops` 与
> `days[].items` 表达的是**同一个东西**（前者按天序摊平），存两份就必须在每次换序时
> 同步两处 —— 而"双源不一致"是这个项目吃过最多的一类亏。
> 现在它是一个派生函数 `planStopItems(plan)`：天序 × 天内顺序。
>
> 顺带落定 `PlanStop` 的字段放哪了：`kind` / `name` / `lng` / `lat` / `cityId`
> 全部加在 **`DayItem`** 上（都是 optional ⇒ 老数据依然合法）。
> 这样"一个点位"在行程里和路线里是**同一个对象**，不需要两套类型 + 一个转换函数。
>
> **② 多了 `chosenOption`（初稿漏了，会丢用户数据）。**
>
> 旧行程里存着"这一段的备选我选的是 B"，它是**用户意图**而不是结果 ——
> 备选路线随时能重拉，但"我选了 B"丢了就是丢了。迁移时原样带过来
> （`planMigrate.ts` 逐字段核对，运行时验收里专门有一条断言）。
>
> ---
>
> ⚠️ `PlanStop` 这个名字**没有消失**，但它现在指的是"一个落了坐标的点位"这个语义，
> 在代码里的实际载体是 `DayItem` + `path` 上的 `MapPoint`（折线顶点，故意不带
> `coordSystem` —— 一条折线 500~2000 个点，每点带一个字面量是纯浪费）。

```ts
export interface PlanRoute {
  at: number                   // ★ 计算时刻（§2.2 的三条约束靠它）
  path: MapPoint[]             // 解压后的整条折线（MapPoint = { lng, lat }）
  distance: number             // 米
  duration: number             // 秒
  taxiFare?: number
  legs?: Array<{ fromUid: string; toUid: string; distance: number; duration: number; path: MapPoint[] }>
  note?: string                // 降级说明（直线估算 / 仅一条 / 超 15 途经点已分段拼）
}
```

**为什么"一站"要自己带坐标**（而不是像旧 `DayItem` 只存 `poiId`）：

1. 自由取点**没有** poiId —— 这是你第 8 条要求的直接后果；
2. 跨城规划时不该为了画一个点去 `loadCity`；
3. 旧 `DayItem` 只有 `poiId`，所以**顺带解决了另一个隐患**：城市数据重建后 poiId 变了，行程就静默丢点。
4. `legs` 用 `fromUid` / `toUid` 而不是下标 —— 用户换序之后，下标会指到别的段上（**静默错位**），uid 不会。

### 3.3 自由取点（你的第 8 条）

沿用**住宿点已有的那套**（`Stay.source: 'poi' | 'geocoded' | 'picked'`，`usePlanView.onUseMapCenter` 已在用）：

- 入口：规划详情面板里一个「在地图上取点」按钮 → 进入**取点模式**（地图光标变十字 + 顶部一条提示「点地图上任意位置添加」+ Esc 退出）
- 落点：`kind: 'point'`，名字默认「地图取点」（可改）；不调地理编码反查地址（**那要花配额，且不是必须**）
- 取消：取点模式下点空白不落点（避免误触）
- ⚠️ 取到的点大概率**不在路上**——腾讯驾车接口会「吸附就近道路」，**20 公里内无路直接算路失败**（官方原话）。  
  所以：算路失败要**明确说是"这个点周围 20 公里内没有可通行道路"**，而不是笼统的「查询失败」。

### 3.4 与现有「行程（按天 / 住宿 / 时间链）」的关系：**同一条，只是从"一城一份"变"多份"**

**保留**：`stays` / `days` / `ItineraryDay` / `DayItem` / `timeline` 推导 / 过载提示 / 分享导出 —— 全部不动。

**变化**：容器从「一城一键」变成「**一份全局列表，每条记录带自己的 `cityId`**」：

| | 现在 | 方案 |
|---|---|---|
| 存储键 | `chexing:itin:<cityId>` | IndexedDB 的 `plans` store（主键 `id`，索引 `updatedAt`），**一份全局列表** |
| 数量 | 一城一份 | 多份（可同城多份，也可不同城） |
| 列表 | 不存在 | 右上角按钮打开，**跨城可见**、按 `updatedAt` 倒序 |

**为什么列表要做成全局的**（而不是"本城的规划"）：
① 入口按钮在顶栏（任意页可见，包括首页全国视角）—— 那里没有"当前城市"；
② "按最近规划时间排序"这个诉求本身就暗示了**它们被放在一起比**；
③ 用户完全可能同时在排成都和重庆的两条线。

**但一条规划仍然属于一座城市**（`plan.cityId`）：因为时间链要靠**该城的通勤数据**算，
住宿段也是城内的锚；跨城通勤我们既没有矩阵也不该现算（配额）。
⇒ 打开一条规划 = 切到那座城市的地图 + `loadCity` 该城数据 + 现有行程页照常渲染。

**旧数据迁移**：`chexing:itin:<cityId>` → 该城一条规划（名字「<城市> · 我的行程」，
`updatedAt` 取迁移时刻）。**只迁一次**（写 `chexing:plans-migrated` 标记）、**不删旧键**（留作回滚）。

> ⚠️ 一处要改的推导：现在 `usePlanView` 用路由参数 `:cityId` 取城。
> 改成从**当前打开的规划**取 `cityId`，路由建议 `?plan=<id>`（或 `/plan/:planId`），
> 让"打开某条规划"可以直接分享 / 刷新不丢。

## 四、存储：IndexedDB（你问的这个）

### 4.1 为什么不能继续用 localStorage

|          | localStorage                                       | IndexedDB     |
| -------- | -------------------------------------------------- | ------------- |
| 容量       | ~5MB（微信 WebView 更小）                                | 通常磁盘的 10%~60% |
| 写入       | **同步**，阻塞主线程                                       | 异步            |
| 单条折线体积   | 一条 6 点的市内路线解压后 **500~2000 个点**，JSON 约 **30~150KB** | —             |
| 多条 × 多方案 | 10 条规划 × 3 方案 × 100KB ≈ **3MB**，直接顶到上限             | —             |
| 事务       | 无（并发写互相覆盖）                                         | 有             |

⇒ **折线这层必须离开 localStorage**。

### 4.2 只有「可用 / 不可用」两态，**没有降级链**

★ 2026-09-25 用户定：「indexeddb 不能用时，在规划的时候**提示用户不可用**，而不是再退回 local，
这样得写两套逻辑，会变复杂」。

| 情况 | 行为 |
|------|------|
| IndexedDB 可用（绝大多数浏览器，含无痕模式） | 正常 |
| IndexedDB 不可用（被策略禁用 / 极老的 WebView） | **规划功能不可用** —— 入口按钮点开就是一句明确说明：「当前浏览器不允许使用本地数据库，路线规划无法使用」+ 为什么 + 怎么办（换浏览器 / 关掉无痕 / 查站点权限）。**不退回 localStorage、也不进内存态** |

**为什么不写第二套**：退回 localStorage 要维护两条持久化路径（读写 / 上限 / 清理 / 迁移各两遍），
换来的只是极少数环境下一个「存不下折线」的残缺版本 —— 复杂度是实的，收益是负的。
顺带一提，现有 `isPersistAvailable()` 的「退回内存态」是同一种复杂度，本次一并收掉：
**要么能用，要么如实说不能用**。

**摆放（统一进 IDB，不搞混合）**：

| 数据 | 放哪 | 备注 |
|------|------|------|
| 规划记录：`stays` / `days` / `stops` / 名称 / 时间 | **IndexedDB** 的 `plans` store | 见 §3.4：一条规划就是**一份行程** |
| 折线 `route.path` + 距离 / 耗时 / 计算时刻 | **IndexedDB**（同一条记录里） | 体积大头在这里 |
| `quota` / `basemap` / `tmapKey` | **仍 localStorage** | 与规划无关、小而同步，不动 |
| 旧 `chexing:itin:<cityId>` | 迁移进 IDB 后**保留不删** | 见 §3.4 |

> ⚠️ **代价要说清**：迁移之后，规划的**唯一**存储是 IDB。所以 IDB 不可用时，用户不仅看不到新规划，
> 也看不到迁移进去的旧行程。这是「两态」设计的必然代价，判断是：**现代浏览器 IDB 可用性极高，
> 这个代价远小于两套逻辑的维护成本**。若你更想保住「行程永远看得见」，备选是把 `stays/days` 留在
> localStorage、**只把折线放 IDB**（退化更小，但数据分两处，以后做「规划导入 / 导出」更绕）—— 一个字就能切。

### 4.3 首屏的异步代价（要认）

现在 `store.init(cityId)` 是**同步**的（`readJson`），所以路由能立刻渲染。  
规划记录改异步读之后，会有一次"还在读记录"的中间态 —— 现有 `PlanRoute` 已经有  
`view.store.hydrated === false → <Placeholder>` 的处理，**复用同一个占位屏**即可，不要新造一个。

### 4.4 旧数据迁移 —— ✅ 已落地（2026-09-26）

`chexing:itin:<cityId>` → 一条规划（`name` 取城市名 + 「我的行程」，`updatedAt` 取迁移时刻）。  
迁移**只做一次**（迁移后写一个 `chexing:plans-migrated` 标记），且**不删旧键**（留作回滚）。

**实现**：`common/logic/itinerary/planMigrate.ts`。落定时补了四条约束，每条都对应一个真实会踩的坑：

| # | 约束 | 不这么做会怎样 |
|---|---|---|
| 1 | 只做一次，落标记 | 每次启动都扫一遍 localStorage |
| 2 | **不删旧键**（迁移 = 复制，不是搬走） | 丢了回滚点；且 `itinerary/store.ts` 切完之前还在读写它 |
| 3 | id 用**确定式** `legacy-<cityId>` | 标记位万一丢了要重迁，结果是**越迁越多**，列表里堆出一串同名记录 |
| 4 | **有写失败就不落标记** | 出现"标记已迁、数据其实没进去"——静默丢用户数据 |

**空行程不迁**：用户可能只是打开过某城的行程页（`init()` 会落一个空壳），那不该变成一条记录。
判据 = `stays` 为空**且**每天都没有点位。有住宿点但还没排点算劳动成果，要迁。

> 🚨 **落地时探针抓到的一个真 bug**（静态检查、类型检查、人工读代码全都查不出）：
> `idb.ts` 的 `getPlan()` 注释写着「`null` = 读不了**或**不存在」，实现却是直接
> `return withStore(...)` —— 而 **IndexedDB 对不存在的键给的是 `undefined` 不是 `null`**。
> 于是上面约束 3 的幂等检查 `!== null` 把**每一条不存在的记录都判成"已经迁过"**：
> 首次迁移的真实表现是「迁 0 条、跳过 2 条、**照样落下已迁移标记**」
> ⇒ 用户的旧行程**一条都不会被迁走**，还被告知"迁完了"，全程零报错。
>
> 已在 `idb.ts` 把 `undefined` 归一成 `null`（改在源头，而不是调用处打补丁）。
> 反向陷阱：`delete()` / `clear()` 成功时 `result` **本来就是 `undefined`**，
> 若也归一化则删除永远报失败 —— 源码注释里点明了。
> 判据见 `_tmp/cdp_planstore_verify.mjs`（种 3 条旧数据 → 跑迁移 → 逐字段核）。
> ⚠️ **以后动存储层，必须跑这个探针** —— 这一条只有真浏览器能验。

## 五、接口与折线（技术核心）

### 5.1 接口选型：**继续用 WebService 直连**（已实测定案）

★ 2026-09-25 实测结论（零配额，读 SDK 源码 + 带不同 `libraries` 抓包）：

| 事实 | 证据 |
|------|------|
| 当前 GL SDK（`libraries=geometry`）**不含服务类** | 包里 0 个 `waypoints` / `get_mp` / `ws/direction` |
| 带 `libraries=service` 才有 | 出现 `waypoints`×5 · `get_mp`×1 · `ws/direction`×4 · `Geocoder` |
| **服务类 = 同一个 WebService 的薄封装** | SDK 内部：`apiUrls.driving = "https://apis.map.qq.com/ws/direction/v1/driving/"`；`search(t)` 里 `Object.assign({from,to},t)` 后 `delete from/to`，**其余参数原样拼进 URL** |
| 服务类**也不解析折线** | 包里 `polyline` 的 3 次命中**全是 WebGL shader 名**（`instance-polyline-*-shader`），没有任何解析逻辑 |

⇒ **上一个版本的方案（改走服务类）是错的**，纠正如下：

| | 服务类 | **WebService 直连（选它）** |
|---|---|---|
| 本质 | 同一下游接口的封装 | 同一个下游接口 |
| 参数拓展性 | 透传（但依赖逆向 `servicesk` 签名机制） | **完全可控**（官方文档全参数） |
| 返回字段 | 原始 JSON | 原始 JSON（含 `polyline` / `get_speed` 速度数组 / `taxi_fare` / `routes[].tags`） |
| 折线 | **仍要自己解码** | 仍要自己解码 ⇒ 两条路的"难"是同一个 |
| key | `VITE_TMAP_KEY`（+ SDK 内部签名） | `VITE_TMAP_WEB_KEY` |
| 新增工作量 | 改 loader 一行 + 摸清 SDK 封装结构 + 错误形态 | **现状 `routeOptions.ts` 已实现**，只补：key 一行、解码、`waypoints` |
| 是否依赖 SDK | **是**（SDK 挂 → 连路线都查不了） | **否**（与现有降级链一致：地图挂了照样能规划路线） |

**结论：走 WebService 直连。** 三条理由：
1. **拓展性两者完全一样**（它就是同一接口的封装，不存在"服务类能多拿什么"）；
2. **"简单"这一项 WebService 反而占优** —— 调用与映射**已经写好了**（`itinerary/routeOptions.ts` 442 行），
   要补的只有三件小事；换服务类要重写调用、还要逆向 SDK 的签名与错误形态；
3. **不依赖 SDK**，地图加载失败时路线规划仍然可用。

> ⚠️ 顺带纠正 `map/tencent/config.ts` 的一句注释：「主路径是 JS API 服务类……**还能直接拿到 polyline**」——
> 实测**服务类也不给已解析的折线**（它只是同一接口的壳）。这句注释误导了上一版方案，要改。

#### 🚨 落地时发现的第二件事：**"直连"只能是 JSONP，`fetch` 根本不通**（2026-09-26）

第一次真跑链路时，请求发出去了却报 **`Failed to fetch`**。查下来是这个原因：

| 尝试 | 结果 |
|------|------|
| 浏览器 `fetch(url)` | **`Failed to fetch`** |
| **同一个 URL 用 Node 直连**（无 CORS 约束） | `status: 0`、520 个折线值 ⇒ **接口本身完全正常** |
| 看响应头 | **没有 `Access-Control-Allow-Origin`** ⇒ 纯跨域问题 |
| 加 `output=jsonp&callback=__cb` | 返回 `__cb&&__cb({...})`，`Content-Type: application/javascript` ⇒ **可用** |

⇒ 「WebService 直连」在浏览器里**只有 JSONP 这一种形态**。实现落在 `itinerary/jsonp.ts`
（自带超时、abort、以及**每条出口都清理**：删 `window` 上的回调 + 摘掉 `<script>`；
回调名带随机段，否则并发时结果会串到另一条请求上）。

★ 顺带修掉一个**一直存在但从未暴露**的缺陷：`routeOptions.ts` 里那段也是 `fetch` ——
它从来没在浏览器里成功过。没暴露的原因很讽刺：WebService key 压根没配到前端，
所以它永远停在"未配置 key"那一步，连这次失败都没机会发生。

> ⚠️ JSONP 的代价要写在代码里：它把远端返回**当脚本在本页的源里执行**，
> 只对**可信的固定域名**用（这里是 `apis.map.qq.com`，与加载它的 SDK 同一信任级别）。

**要补的三件事**（都不大）：

| # | 事项 | 说明 |
|---|------|------|
| 1 | 配 key | ★ **原方案说要加 `VITE_TMAP_WEB_KEY`，落地时发现不必** —— `resolveWebServiceKey()` 现在三级解析：使用者自备 → `VITE_TMAP_WEB_KEY` → **回落到 `VITE_TMAP_KEY`**。腾讯一个应用的 key 默认同时可用于 JS 与 WebService，所以`.env.local` 里已有 `TMAP_WEB_KEY`（无 `VITE_` 前缀、前端读不到）这件事**不再阻塞**，但那个键仍然是死的、容易被下一个人误以为在生效 |

| 2 | 实现 `decodePolyline` | 见 5.2 —— **两条路都躲不掉这一步**，这是本方案唯一的真未知数 |
| 3 | 加 `waypoints` | 见 5.3 |

### 5.2 折线解码 —— ✅ **已实测确认**（2026-09-25）

**结论：不存在「解码算法」这件事。** 腾讯的 `polyline` 是**数值数组**，不是压缩字符串：
格式 `[lat1, lng1, dlat2, dlng2, …]`，**首点未压缩**、之后用**前向差分**，
解压 `coors[i] = coors[i-2] + coors[i]/1e6`（官方文档原话，实测印证）。

实测数据（成都 宽窄巷子 → 大熊猫繁育研究基地，`_tmp/probe_polyline.py`，消耗 1 次配额）：

| 项 | 结果 |
|---|---|
| 类型 / 长度 | `number[]`，**566 个值**（不是字符串） |
| 解压后 | 283 个点 |
| 首点偏差 | **9 米**（请求点 → 吸附到道路，正常） |
| 末点偏差 | **4 米** |

实现落在 `itinerary/polyline.ts`：`decodePolyline()` + **硬编码自检样本**（`POLYLINE_SAMPLE`，30 个真实值）
+ `selfCheckPolyline()`。自检**在真模块上跑过**（`_tmp/cdp_polyline_selfcheck.mjs` 借 Vite 转译直接
`import()` 编译后的代码 —— 避免"手抄一份算法自己验自己"这种假验证）。

边界（已实测）：空数组 / 单元素 → 0 点；**含非数字 → 截断**（差分是累加的，一个脏值会污染它后面
**每一个**点，截断只是少画一截，跳过会让整条线变 NaN 而完全不画）。

> ⚠️ 网上流行的 `charCodeAt(i) - 63` 那套是**微信小程序地图组件**的 polyline 格式，与 WebService 无关。
> 照抄进来会得到一堆乱坐标，而且**不报错** —— 只是路线被画到别的地方去。

**顺带纠正的两处旧认知**（都已在代码里改正）：

1. `routeOptions.ts` 里 `RouteOption.polyline` 的类型标注原本是 `string | null`（**错的**）→ 已改 `number[] | null`，
   判空也从 `typeof === 'string'` 改成 `Array.isArray`。
2. **拥堵区间不用推算**：`speed[]` 每项自带 `polyline_idx: [from, to]`，直接就是这段在折线上的下标区间
   —— 不需要"先解出折线再回头找对应段"（`polyline_idx` 是**下标**不是坐标个数：实测最后一条 step 的
   `[560, 565]` 对上 566 长的数组）。

### 5.3 途经点上限 → 超过就分段拼

腾讯 driving 的 `waypoints` **最多 15 个**（官方）。所以：

- 一条规划 ≤ 17 个点（起 + 15 途经 + 终）→ **一次调用算完整条**；
- 超过 → 按 16 点一段切开，**分段请求后拼接**（每段结果是真实折线，拼起来仍然真实），  
  并在 UI 上如实说明「本次规划分 N 段计算」。
- **不用** `waypointOrder`（那是"自动排最顺路"= TSP，红线 5 禁止）。途经点顺序**就是你排的顺序**。

### 5.4 多方案的两个层次（别混）

| 层次       | 是什么               | 怎么拉                                      |
| -------- | ----------------- | ---------------------------------------- |
| **整条规划** | 这条规划从起点到终点的一条完整路线 | 一次调用（带 waypoints），**只取最快一条**（`get_mp=0`） |
| **单段备选** | 点开某一段时看 A/B/C     | 保持现有行为（`get_mp=1`，点开才拉）                  |

理由：整条路线取 3 条方案 = 3 条长折线，体积与耗时都不划算，而用户真正会挑的是**某一段怎么走**。

| 面板开着（`planUi.panelOpen`） | 没开 ⇒ 用户没在看任何一条 |
| 处于**详情态**（`planStore.activeId` 非空） | 列表态没有"当前这条"可言 |
| **与景点同城**（`plan.cityId === cityId`） | 那条规划的时间链靠该城的通勤矩阵算，跨城的点会让它算不出来 |

命中时：文案改成「**添加到当前行程**」；点击**不出选组弹窗**，
直接 `addStopToPlan(plan.id, stop, detailDay - 1)`（重复校验照样走）。

**它为什么不算违反 §6.5 那条规矩**：那条规矩反对的是"**同一个按钮在不同状态下干不同的事、
而用户看不出区别**"。这里**按钮上的字跟着变**（`addToPlanLabel()`）—— 用户看得见
"这个按钮会把点加进右边开着的那条"，所以不存在"偷偷干了别的事"。

★ 两条实现纪律（护栏 **Y⑭** 守）：

1. **短路只写在 `useAddToPlan.run()` 一处** —— 四个入口（城市页清单 / 首页 / 省级页 /
   景点详情页）自动全部生效，不必在每个按钮里各判一次；
2. **文案只来自 `addToPlanLabel()`** —— 四个按钮里写死「添加到当前行程」会被护栏打回：
   判据改了而某处文案忘了跟着改，就是"按钮说一套、做另一套"。

★ 顺带把"当前天"收成一份（`planUi.detailDay`）：以前「挑景点」自己存了一份 `day` 快照、
切天时再单独同步，等于同一个概念两份状态 —— 那正是用户说的"逻辑上重复"。
现在由 `PlanDetailView` **单向**广播，三个消费方（天数标签栏 / 挑景点清单 / 添加到当前行程）
读同一个值。

★ 这一串改动要透传一个字段：三个页面（城市 / 首页 / 省级）对外多暴露一个
`selectedCityId`（选中的景点归属哪座城，可能是搜索命中的别城点）——
`PoiDetailOverlay` / `PoiDetailSheet` 收了它才能问出"是不是正在看这座城的规划"。

验收 = `_tmp/cdp_detailadd_verify.mjs`：面板没开（弹窗）/ 同城详情态（不弹窗 + 第 1 天）/
切到第 2 天（加进第 2 天）/ 面板退回列表态（弹窗）/ **别城**（弹窗且库不变）。

### 6.6 ★ 详情态 = **完整行程**（2026-09-26 用户定，本节是最大的结构变化）

> 用户原话：「点列表进详情，应该是显示那个**完整行程里的内容**，现在你又加了一个新弹窗，
>   把旧的完整行程的内容，**搬到现在的行程详情弹窗里**」
> 另一条：「新建组为什么是不可点击的，这个应该是**不管什么情况下都能点击**才对」

#### 6.6.1 详情态 = 旧「完整行程」页的全部内容

点一个组进详情，看到的是旧 `/city/:cityId/plan` 那一页的**全部内容**：
降级条 + 时间链（住宿 / 多方案 / 超载警告）+ 导入导出分享。
**不是**上一版另起炉灶的"简化途经点列表" —— 那是与"完整行程"并存的第二套行程 UI。

| 层 | 来源 | 说明 |
|----|------|------|
| 推导 | `usePlanView.useItineraryView(cityId, { mapLayers })` | 从页面钩子里抽出来，**面板与深链共用同一份** |
| 内容 | `PlanPanel` + `DegBars`（`compact=false`） | **同一份**完整时间轴 |
| 地图侧 | `usePlanRouteLayer` | **整条沿路折线**（⇠ 面板专属；逐段那条要逐段 `path`，"整条一次规划"算不出来） |

**连带的结构变化**：

- `/city/:cityId/plan` **不再是另一套 UI**：`DesktopPlanView` / `MobilePlanView` 删了，
  这条 URL 变成「**渲染城市页 + 把面板开在这座城最近改过的那条组上**」的深链
  （保留它是因为收藏夹 / 分享里还有；预渲染清单里的 12 条渲染出来的就是城市页 HTML）。
- `--panel-itinerary`(420) **删了**（删浮层不删 token = 留一份没人用却仍被守着的规格）；
  `--panel-plan` 360 → **420**（详情态现在是六列的完整时间链，360 塞不下）。
- 行程的推导钩子从 `usePlanView`（读 `useParams`）拆成 **`useItineraryView(cityId, opts)`**
  —— 面板挂在外壳上，不在 `/city/:cityId` 路由内部，`useParams()` 是空的，
  城市必须由调用方给。`opts.mapLayers=false` 让逐段连线不挂在面板上
  （两套线叠一张图 = 同一趟行程画两条线）。
- `/city/:cityId/plan` 的 effect **依赖里不能放 `plans`**：往面板加一个点 `plans` 就变，
  那条 effect 会把"当前打开的组"抢回"最新的一条"，用户的选中被悄悄覆盖。

**算路的判据是明细数，不是时间链的段数** —— 住宿点只影响"时间链"（几点出发/几点到），
**不影响路线本身**（折线穿的是明细点位）。第一版错绑在 `timeline.legs` 上，
结果是"没设住宿点就永远点不了规划路线"，而这是两件独立的事。

#### 6.7 ★ 「添加行程」的弹窗是棵树：**组 → 天**（2026-09-26 定；09-27 改样式）

> 用户原话（09-26）：「一级是组，二级是哪一天，**添加行程是添加到那一天里面**」
> 用户原话（09-27）：「新建规划的按钮，样式改一下，用**虚线边框，圆角，文字居中**；
>   **规划列表的展开收起功能没用，需要修复，默认是收起状态**；
>   **新的一天按钮不需要**，在**组右侧增加一个添加按钮**，点击就往后加一天」

```
┌ 把「大熊猫基地」加到哪个组？────────────┐
│  ▸ 成都三日              3 条明细    ＋ │  ← 一级：点组名展开/收起 · 右侧 ＋ = 往后加一天
│  ▾ 成都四日              1 条明细    ＋ │
│        第 1 天             1 条         │  ← 二级：点它 = 加进那一天
│        第 2 天             0 条         │
│  ┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈ │
│              ＋ 新建规划                │  ← 虚线边框 · 圆角 · 文字居中
└────────────────────────────────────────┘
```

#### ★ 默认收起 —— 以及原来"展开收起没用"的原因

`null` 必须是**合法的"都收起"状态**。原来写的是：

```ts
const expanded = expandedId ?? candidates[0]?.id ?? null   // ← 错
```

拿"第一个候选"当缺省，于是**点第一个组想收起会被立刻兜回去**（`setExpandedId(null)`
→ `?? candidates[0].id` 又给出了它）—— 用户看到的现象正是「展开收起功能没用」。

★ 教训：**"缺省值"和"用户选的值"混在同一个 `??` 里，那个"选择"就永远无效**。
要区分就得让"没选"是一个**显式的合法值**（这里是 `null` = 全收起），不是"用另一个值兜底"。

#### 两个动作拆成两个按钮

不能把一个 `button` 嵌进另一个 —— **非法 HTML**，浏览器会把内层挤出去、点击判定跟着乱。
所以组行是 `div` 里两个 `button`：左边一大块 = 展开/收起（点组名本身，符合直觉），
右边「＋」= **往后加一天**：

```ts
await store.update(planId, { days: appendDayToPlan(plan) })   // 只加空天，不碰明细
setExpandedId(planId)                                         // 并展开它，让新的一天立刻可见
```

原来那行"展开后在列表最下面出现的『新的一天』"已删 —— 入口挪到组行右侧，
不用先展开再找。★ 它同时**顺手修掉一个隐性成本**：旧入口在"组是天数很多"时要滚到底才看得到。

#### ★★ 「＋」只加天，**不碰这个景点**（2026-09-27 修，第一版错在这）

> 用户原话：「我点组的添加，不应该是**添加天的数据**吗，怎么说重复添加景点」

第一版把它写成"加一天 + 把这个景点放进新的一天"（`appendStopToPlan(plan, stop, plan.days.length)`），
于是点 ＋ 也会走唯一写入口的**重复校验**，弹出「这个景点已经在里面了」——
**用户在建结构，系统却在跟他讨论景点**，语义完全错位。

现在 `＋` 只加天，**由用户点新出现的「第 N 天」把地点排进去**（那才是"添加行程"）。
三条附带的好结果：

| 附带效果 | 为什么重要 |
|---|---|
| 弹窗**不关** | 你点的是结构操作，屏幕不该清空；新出现的「第 N 天」就是下一步落点 |
| 那个组**自动展开** | 不然"加了一天"在界面上没有任何可见的变化（点了像没反应） |
| **不清 `route`** | 折线穿的是明细点位，空天不改变这个序列 —— 已算的路线仍然有效（对比 `appendStopToPlan` 必须清） |

#### 「新建规划」按钮：虚线边框 · 圆角 · 文字居中

虚线是"这里可以**长出**一样新东西"的通用语汇（新建文件夹 / 新建标签页 / 新建看板都是它），
比实线描边更能说明"点它是**建**，不是**选**" —— 它上面每一条都是"选"，只有它是"建"。

#### 其余契约不变

- `addStopToPlan(planId, stop, dayIndex)` —— **天由弹窗给**（用户点的就是某一天）；
  地图取点没有弹窗 → 落到最后一个非空天（`appendStopToPlan` 的缺省）。
- 指定的天越界（只有 1 天却点了"第 3 天"）→ **补空天**到那一天为止。
- 候选含**城市未定**的组（`cityId === ''`）—— 它加第一站时才认领城市。
- 底部的草稿行有 **✓ 和 ✕ 两个动作**（`showCancel`）：弹窗里没有明显的 `Esc` 入口，
  得有看得见的退路。✕ 的 `aria-label` 是「**取消新建**」，不与弹窗头部的「取消」撞名。

### 6.8 ★ 闭环：**加了必须看得见**（2026-09-26 用户报的真正问题）

> 用户原话：「如果右侧打开了规划面板，而且还是当前加的规划，右侧的面板需要更新，
>   我现在加完，右侧没有任何的显示」

**根因**：时间链**锚在住宿点上**（它是行程的起终点，没有它"几点出发/几点到"算不出来）
—— 所以刚加完点、还没设住宿点时 `timeline` 是 `null`，
完整时间轴那一块**什么都不显示**（不是没加上，是没地方显示）。

**解法（§6.6 的布局再收一步）**：详情态的内容分两态

| 状态 | 显示 |
|------|------|
| `timeline` 有值（已设住宿点） | 完整时间轴（`PlanPanel`，带时间） |
| `timeline` 为 null（还没设住宿点） | **按天分组的明细列表**（每条可删）+ 一行「设好住宿点之后，这里会变成带时间的行程」+ [设置住宿点] |

⇒ 加的每一条**立刻可见**，并说清差的只是住宿点。

#### ★★ 按天列表必须按 `plan.days` 走 —— **空天也出一节**（2026-09-27 修）

> 用户原话：「怎么景点详情添加行程弹窗的天数和右侧路线规划详情的天数数据不一致，
>   我左边弹窗里加到了第四天，**没有绑定景点**，右侧还是只显示第一天」

第一版是从 `stops`（**有明细的点**）反推分组的 —— 于是**空天那一节整体消失**：
弹窗里明明有「第 2/3/4 天」，右侧列表还是只有「第 1 天」。

★★ **真源是 `plan.days`，它允许有空天**（"留一天"是正常意图）——
展示层必须**如实反映**，而不是"只画有东西的那几天"。
空天那一行的右侧写「还没有安排」（原来的版本是一片沉默，看着像数据丢了）。

★ 顺带把头部天数从 `view.store.days.length` 换成 `plan.days.length`：
`view.store` 要等 `attach` 追上（它的守卫是"`rev` 变了才重装"），
用它偶尔会显示成**加天之前**的天数。

★ 连带验过的一个副作用：**删掉某条明细不会把空天冲掉**（删明细改的是内存里的
`store.days` 再落盘，如果它比 `plan.days` 旧，整份天就会被覆盖回去）。

**布局（按用户指示收掉中间块）**：顶部两个按钮（添加景点 / 地图上取点）保留；
**路线摘要 + 规划路线按钮整块去掉**（路线规划后面重新设计）；底部导出/导入/分享保留。

—— 与「添加景点」要用 `closePagePoi` 是同一类问题。走这条信道还有个白捡的好处：

2. **✓ 的职责是"收起"**（写库只是顺带）—— 第一版点 ✓ 时"没改动就什么也不做"，

1. **只渲染当前这一天**（`days[activeDay - 1]`），**空天照样出内容** —— 换成一句

### 6.12 ★ 「点标题 → 地图居中并放大」用的是**指定缩放**，不是 fit

`fitBounds` 对**单点**只能从退化框 + padding 反推级别，实测落到 **13.99** ——
而 `FitOptions.minZoom` 是"**收缩框**"、不是硬钳位，单点这条路上给不出保证。
"看一个景点"要的是**确定的**级别 ⇒ 新增 `panTo.focusPointTo(map, point, zoom, opts)`：
`setZoom(目标)` + `setCenter`（同一个 tick 里发出，腾讯合成一次动画），
中心**按目标缩放**算（`屏幕x = world_z(点) − world_z(中心) + 容器半宽`）。
落点仍是**扣除浮层后的可视区中心**，与 `panPointToCenter` 共用同一份 `freeRect`。
实测 `zoom: 15`、`__mapPan.dx/dy` 是"点相对容器中心的偏移"。

`STOP_FOCUS_ZOOM = 15`（`POI_REVEAL_ZOOM` 是 12 —— 那是"景点开始出现"的阈值，
不是"看一个景点"的阈值）。

  但**缩略图与所在区只长在 POI 上**，新数据不查就双双为空（列表全是灰占位块、第二行只剩省市），
  而且**不报错**。现在只要有 `poiId` 就查（`loadCity` 有缓存）。

  拆到 `storeDays.ts`（`makeDayActions(set, get, persist)` 工厂展开进 store）。

### 6.6.2 「新建组」**永远可点** + 「城市未定」的组

> 「新建组为什么是不可点击的，这个应该是不管什么情况下都能点击才对」

原来有两处禁用，各自的解法：

| 原来的禁用 | 现在 |
|---|---|
| **没有城市上下文**（首页 / 省级页，URL 里没有城市） | 允许先建一条「**城市未定**」的组（`cityId === ''`），**由它的第一条明细认领城市**（判据在 `planStore.update`：`cityId` 只许"从空设成非空"）。因为"我在哪座城"完全可以等加第一个景点时再定，不该由按钮逼用户现在决定 |
| **正在新建**（草稿行开着） | 不新建第二条，改成**把草稿输入框重新整段选中** —— 有反应，且不丢已经打进去的名字 |

**城市未定的组在详情态显示的是引导**（"加第一个景点时它会自动归到那座城"），
而不是一套空行程 —— 空行程会被读成"我的行程被清了"。

#### 6.6.3 ★ 这一套改在**面板**上，不在弹窗里（2026-09-26 补，改错地方的教训）

> 用户：「我知道了，我说的地方和你改的地方不是同一个，
>   我说的是**右上角点路线规划出来的那个弹窗**」

上一轮把「新建规划」改名/加取消/收样式**全加在了「加到哪个组」弹窗里** ——
而用户指的是**面板列表态右上角**的那个按钮。两处都要：
- `PanelHeader` 的按钮：`新建组` → **`新建规划`**，实心主色 → **描边**
  （用户反馈"有点突兀"：它只是列表里的众多动作之一，不该是整块浮层里最响的元素）；
- 列表态的草稿行：加 **✕ 取消**（`showCancel`，Esc 不够明显）；
- 空态按钮/文案同步（`建一个规划…`）。
- 弹窗那边上一轮改的也保留（两处现在叫同一个名字、同一种交互）。

**教训：用户说"X 界面的 Y"时，改之前先确认是哪一个 X** —— 这个项目里
"路线规划的弹窗"有**两个**（右侧面板 / 加到哪个组的选择器），同名按钮有**三个**。


### 6.5d 重复校验：「已经在里面了，还要再加吗？」（2026-09-26 用户要求）

> 用户原话：「还有个重复性校验，需要提示用户，重复了，是否还需要添加，
>   如果确定就继续添加，否则就不添加」

**为什么值得拦**：用户在两个地方翻景点、或点两次「添加行程」时，很容易把同一个点
排进同一条组里。加了两次的后果**不是"多一份"这么轻** —— 路线会折返回去
（A→B→C→A→B），**距离与时间都被算成两倍**，而排出来的行程看着完全正常。

**为什么两头都不许静默**：

| 做法 | 后果 |
|------|------|
| 静默拒绝 | 重复点**有时候是故意的**（同一个地方去两次：白天看展、晚上看灯）⇒ 用户没法表达"我就要两次" |
| 静默添加 | 用户永远不会发现自己的路线被自己排成了一个圈 |

⇒ 只有"问一句"两边都成立。确认卡的默认焦点落在**「取消」**上（回车不会误加）。

**判据（"同一个地方"对两种点意味着不同的事）**：

| 类型 | 判据 | 为什么 |
|------|------|--------|
| 景点（`poiId` 非空） | `poiId` 相等 | 同一个景点就是同一个地方，与坐标无关（坐标是抓来的，可能重采样） |
| 地图取点（`poiId` 空） | 坐标相差 < 1e-5（≈1 米） | 取点**没有 id**，"同一个"只能是同一个坐标 |

★★ **确认卡的「取消」= 关掉卡片 + 把「加到哪个组」弹窗还回来**（2026-09-27 修）：

> 用户原话：「这个重复添加景点弹窗，关闭后，**原本显示的行程规划弹窗，不显示了**」

原因是选组弹窗在"选定某个组"那一刻就关了（它把活交给确认卡）——
于是取消之后**一个浮层都不剩**。而用户说的"取消"是"**换个地方放**"，不是"这趟算了"。
所以那一颗按钮现在叫「**换个落点**」，行为是 `closeDupConfirm()` + `openAddPicker(dup.stop)`
（点卡片外面也一样）。弹窗会以**默认收起**的全新状态出现，这也正是"重新挑一次"该有的样子。

**落点：唯一的写入口** `useAddToPlan.addStopToPlan(planId, stop)`
（`itinerary/planStops.findDuplicateStop`）。四条添加路径全部经过它：
城市页清单 / 景点详情 / 首页 / 省级页 → 弹窗选组；面板「地图上取点」；
弹窗里的「新建组」（新组一定是空的，但还是走同一个入口，免得以后给它加行为时绕过校验）；
以及确认卡的「仍然添加」（**唯一**刻意绕过校验的那一个）。

★ **提示要说清"它现在是第 N 条明细"**，不能只说"已存在"—— 那样用户还得自己去列表里找是哪一条。

★ 两张卡**互斥**：弹窗选完组就关，由确认卡接管。同时开着用户不知道该点哪一张。

### 6.5c ★ 常驻浮层的「门 / 内容」分家（2026-09-26，从一次真 bug 里总结的）

`AddToPlanPicker` / `RoutePlanPanel`（桌面与移动）都挂在**外壳**上、常年存在，
靠「没有 payload 就 `return null`」表示"关着"。而 `return null` **只是不渲染内容，
组件实例还在** —— 它内部的 `useState` 会一直活着。于是：

> 用户原话：「我新建组后，再点添加行程出现的弹窗，弹窗内容没恢复到之前的状态，
>   还是显示了个输入框，而是按钮」

**纪律**：门只判断开不开（**零状态**），状态住在「内容」那一半（它随开关真正挂载/卸载）。

| 门（导出，零状态） | 内容（内部，持有状态） |
|---|---|
| `AddToPlanPicker` | `PickerBody`（草稿行状态） |
| `MobileRoutePlanPanel` | `PlanSheet`（Sheet 档位） |
| `DesktopRoutePlanPanel` | —— 无状态，不需要拆 |

★ **补 `useEffect` 去重置是错的解法** —— 那是跟在 bug 后面跑：以后再加一个局部状态
就又要记得重置一次。分家之后「关掉再打开回到初始态」是**结构保证**。

★ 连带修掉一处冲突：弹窗里的草稿行自己也吃 `Esc`，而 `useDismiss` 的 `Esc` 挂在 `document` 上
—— 两个都响应会让「放弃这行草稿」变成「关掉整个弹窗」。`useDismiss` 现在有 `opts.esc`，
语义是「**`Esc` 关掉最里面那一层**」。

★ 判据：静态 **AF**（门里不许有 `useState`/`useRef`/`useEffect`；有状态就必须是两个组件）
+ 行为 **`_tmp/cdp_planflow_verify.mjs` 的 ⑧″ 段**（开 → 改态 → 关 → 重开，必须回到初始态）。

### 6.6.1 ★ 序号标记**顶替**停靠点上的景点圆点（2026-09-28 用户定）

> 「打开规划详情之后，地图会显示点位顺序，有些点位是标在景点上的，**会出现两个点位**，
>   没办法打开景点详情，而且现在的效果是**盖在景点的点位上的，而不是替换**，就会有很多的问题」

**当时的地图**：规划那层（`usePlanRouteLayer` → `createMarkerLayer`，z-index **32**）给每个
停靠点画一枚序号圆点；景点图层给同一枚景点也画一枚（圆点 20 / 名字 21 / 选中 22 / 聚合 20）
⇒ 同一坐标两枚叠着，序号圆点在上。**而它建的时候没给 `onClick`** ⇒ 那一下命中的是一枚
"没有处理器的覆盖物"，景点圆点的回调根本没机会跑 ⇒ **点不开详情**。

**现在（方案：规划层接管）**：

| 谁 | 做什么 |
|----|--------|
| 外壳（`routes/map-shell.tsx`） | `claimedPoiIds()`：**面板开着 + 详情态**时，把这条规划所有 `poiId` 组成"认领名单"，写进 `ViewportEnv` 随视野重刷发出去（打开/关面板**不是数据变化**，只能靠这条广播让图层重算） |
| 景点图层（`poiLayer`） | 名单里的景点**不画圆点、也不交给聚合**（否则气泡数字会把它们算进去）；**名字留着** —— 编号旁边仍看得见是哪个景点 |
| 规划那层（`usePlanRouteLayer`） | 那个位置上只剩序号标记 ⇒ 它**接住点击**：景点 → `loadCity` + `shell.setSearchPick` 开详情（三页通用）；「地图取点」没有详情可开 → 居中放大 |

★★ 两个坑（都在探针里留了判据）：

1. **打开详情必须延后一拍**（`setTimeout(0)`）。腾讯点中覆盖物时**地图自己的 click 照样派发**，
   而那条路会被判成"点了空白"⇒ 把详情收起来；同步打开会被它当场关掉（"闪一下没了"，不报错）。
   两处回调在**同一个任务**里派发 ⇒ 延后一拍的打开必定在它们之后。
2. **标记画在 canvas 上，DOM 里查不到** —— `document.querySelectorAll('.map-layer img')` 里只有
   logo，所以"屏幕上有几枚""点它有没有反应"只能靠**截图 + 逐像素**（`_tmp/find_blobs.py` /
   `_tmp/png_node.mjs`）+ **墨卡托投影**（`__tmap` 的 center/zoom 反算屏幕坐标）来验。

验收：`_tmp/cdp_planclaim_verify.mjs` —— 图层读数（候选 57 → 准入 **54**）· 屏幕上**恰好 1 枚**

景点圆点照旧点得开。护栏 **Y⑯**（4 条判据），反证 `falsify_y.py` 的 Y⑯a / Y⑯b。

#### 6.6.2 ★ 序号标记的尺寸：**不许挡住景点的名字标签**（同日第三轮）

> 「还有这个标记，会挡住景点的**标签**，这个标记缩小一点试试」

|---|---|---|---|
| 30（旧） | 26 | −13 | **压过去 4px** —— 就是用户看到的"挡住" |
| **20（现在）** | **18** | **−9** | **刚好齐平**，名字文字离圆顶还有 **7px** |

★ 可见直径 < `SEQ_DOT_PX`：描边以圆周为中心画，**向内吃掉一半**（2px 描边 ⇒ 可见半径 10−1=9）。

  护栏 **Y⑰** 把「可见半径 ≤ 标签盒底边到坐标的距离」写成**不等式**，
  谁单独动标记或动标签（`DOT_SIZE` / `LABEL_GAP_PX` / `LABEL_BOX_PX`）都会被拦住。

量法（都在截图上逐像素 —— SDK 画的东西 DOM 里查不到）：`_tmp/cdp_planclaim_verify.mjs` 的 ②′

### 几个**与初稿不同**的决定

1. **内容与容器分家**：`common/` 不许 import `desktop/`、`mobile/`（W 项）。
   所以面板内容在 `common/ui/plan/RoutePlanPanelBody.tsx`，容器两端各一个。
2. **移动端是底部 Sheet，不是右侧浮层**：`--panel-plan` 是 360px，
   而手机竖屏才 360~430px —— 铺上去等于整屏被盖住，而这一页的价值恰恰是"看着地图改顺序"。
3. **城市页那两个入口撤了**（桌面「我的行程」/ 移动「去排行程」）：
   顶栏现在有**全站**的「路线规划」，两者做的是同一件事；
   而且"我的行程"在多规划之后是歧义的（一座城可能有好几条）。
4. **`/city/:id/plan` 改成"看当前打开的那条规划"**：`itinerary/store.ts` 的落盘从
   `localStorage` 换成 `planStore.update()`（**不双写**），`init(cityId)` 直接被
   `attach(plan, rev)` 取代。`?add=` 那条通路整条删掉（四个入口都走 `useAddToPlan` 了）。
   ★ `planStore.rev` 就是为这条同步加的：**行程页要能看见"在右侧面板里改动"**

### 三个**只有真跑才暴露**的 bug（都已修，判据在 `_tmp/` 的探针里）

| # | 现象 | 根因 |
|---|------|------|
| 1 | 请求发出去了却 `Failed to fetch` | 腾讯 WebService **不带 `Access-Control-Allow-Origin`** ⇒ 浏览器里只能走 JSONP（§5.1） |
| 2 | 94.7 km 的路线显示成「**2 分**」 | `direction` 的 `duration` 是**分钟**，而 `PlanRoute.duration` 约定是**秒** —— 差 60 倍且不报错 |
| 3 | 控制台 8 条 `MultiPolyline.styles …属性无效` | 腾讯要求 `width` / `borderWidth` 是**整数**，`3.5 / 5.5 / 2.5 / 1.6` **全部被静默换成默认值**（`routeMode` 里一直是这样，只是从没在浏览器里渲染过折线） |

外加一条 React 报的 hydration 错：`<li>` 套 `<li>`（`StopRow` 自己渲染 `<li>`，外面又包了一层）。

### 还没做（明确记下来，别以为做完了）

- **规划导出 / 导入**（`share.ts` 那条）：`RoutePlan` 还没有对应的导出载荷。
- **拥堵描色**：`routeLayer` 支持 `jams`，`speed[].polyline_idx` 也自带区间，

  `VITE_TMAP_KEY`，所以功能可用；但那个键没有 `VITE_` 前缀 ⇒ 前端永远读不到，
  容易被下一个人误以为在生效。要么加前缀，要么从"前端配置"里摘出去。
